# Design of the shipped library

**Purpose:** say what the shipped library's mechanisms do now and why, for whoever changes them next. **Audience:** a session or person opening code here that points at one of these sections. **Success:** that reader finds the reasons behind the code here, complete, without the issue that built it or any decision record.

The decision log stays in the practice's own repository and doesn't ship, so this document is where a reader of the library finds the reasons, and each section states its reasons whole. The decisions in force are named by their decision-log ids for a maintainer searching the log; they are not pointers a reader follows. Code added under the code-reasons standard opens with a pointer to its section; existing code is brought in by the repository's catch-up.

## The cold reader

**What it does now.** Once a builder turn exists for a change, `run cold-reader` builds an isolated reading tree from the change set. The tree carries every changed regular file, whatever its contents, and a change holding a file the tree can't carry, such as a symlink, is refused as `cold-reading-tree-refused`, naming the path; for each file the reading covers, the Markdown file each `path#anchor` pointer in it names; and the files linked inside that anchored section. A first reading covers every changed file, and a reread covers only the files it owes, though it still carries the rest for reference. All of it is verified against its committed blobs in one neutral detached commit; the archive ignores the machine's line-ending settings, so any repository builds, while an attribute the repository itself sets that rewrites committed bytes, such as `eol=crlf`, still does and is refused. A tree that names the change's branch is refused before launch, and issue or pull-request numbers in any carried file are counted as residue. One fresh read-only seat, on Claude unless the change names another, reads the tree against the code-reasons standard and returns an account in a fixed form, ending with a capped handful of excerpts it nominates as worth a look. The stage checks only that form, including that each flag names a file the tree carries other than the diff file. A flag's location gives its path and, optionally, one line, one range, or a comma list of either; any other malformed flag line refuses the whole return.

The holder posts the account whole in one `open` comment with its own review against the brief beneath it. In that review it accepts any flag it judges not worth another round, one `Accepted:` line per flag with a one-line reason; an acceptance that names no single flag sets the comment aside. An acceptance names a list flag by its whole list, the same items in the same order whatever the dash or comma spacing, and one naming part of a list names no flag. An `open` quoting a return the form check refuses is set aside with that return's first form error, and one quoting no retained return is set aside as differing. An accepted flag doesn't stand and owes no reread, and a `Can tell: no` can't be accepted. The resumed builder reviews the account and fixes what the holder routed. A later `clean` comment closes the reading. It counts only when posted after the builder's review of the latest `open` reading, or after that `open` itself where the acceptances leave nothing standing or owed, at the current head, with nothing below still owed; on every hold the gate returns, a `clean` posted after the latest `open` is set aside as invalid, while one posted before it closed an older reading and is left alone. Until a current `clean` stands, the entrance's decision holds readiness, use, proof and the release report, and it asks only once the change's floor has passed:

- a reading is current per changed file, by the file's blob and the blobs of the document its pointer names and the files linked inside that section;
- a flag the holder didn't accept stands until a later reading that read its path, or a document or record a path it read depends on, no longer raises it; once nothing in the change reaches its path, the reread of what changed answers for it;
- after the builder's review, a reread covers every stale file and every changed file that a standing flag names, or whose pointer reaches the document or listed record it names;
- a `Can tell: no` stands until a later reading of the whole change says `yes`;
- a damaged record holds the gate as unverifiable rather than vanishing;
- only this pull request's readings count: a reading records its branch and pull request, and one recorded without them counts only when this change's history holds the head it read;
- the builder is resumed only for what the latest `open` routed to it, a flag left unaccepted or a `Can tell: no`, and only a turn that returned something counts as its review;
- an `open` carries the head its reading read;
- `run ready-reviewers`, `run use`, `run proof` and `run release-report` refuse while the gate holds, because naming a stage skips the decision the gate sits in; each reports its own refusals first, since a repair those owe would stale the reading anyway.

The reader launches on its role's vendor and records a same-vendor reason whenever it lands on the builder's vendor, fallback included, and it never starts until a build bundle or the builder's session marker proves which vendor built the change.

The reading tree is built in a temporary folder of its own, holding only the tree and outside the entrance's records, which keep the reading's record and diff, written as consumer trees' records are, and its prompt. The gate finds a reading's record there or, for a reading recorded before the records kept it, where that reading left it, beside its tree; a record found in neither place is reported at its path in the records. The tree itself is kept after the run; a tree whose record could not be written is removed, with any diff written for it, because no reading can be judged without its record.

**Why.**

- A reader who saw the brief can't show what the code alone explains, so the reader never sees the issue, brief, pull-request text or branch name.
- The entrance, not the holder, chooses the inputs and composes the prompt, because whoever holds the brief could aim the reader through them.
- The tree follows only `path#anchor` pointers, never a file a changed file merely mentions, because that is the one route the code-reasons standard gives from code to its reasons, and a pointer that doesn't resolve then reaches the reader as the dead end it is rather than being patched by whoever built the tree.
- Every link inside a pointed section is carried, not only its decision records, because the entrance can't tell a decision record by its path.
- The holder's review rides in the `open` comment because a change on the mechanical lane has no holder reading to carry it, and one marker with `open` and `clean` serves every lane alike.
- The builder reviews each posted reading that leaves anything standing or owed, because the builder holds the reasons it decided while building and is the one who fixes what the reading finds; a reading the holder's acceptances leave with nothing to fix closes without that turn, so the loop can end on the holder's judgement, and the holder's own review against the brief still looks for misreadings.
- Every changed path is read, with no classifier deciding what counts as code, because a classifier would be configuration every adopting repository owes.
- Blob identity is what the entrance can compare, and counting the pointed document's blobs rereads a file whose fix landed only in its document.
- A flag must name a file the reading held, and a standing flag owes a reread of what reaches it, so that every flag has a way out through a reading the gate orders.
- The holder takes the owner's release report's excerpts worth a look from the reader's nominations, and the report shows only a few, so the reader nominates only a few.
- The gate waits for the floor because a repair the floor still owes would change the files a reading has just read.
- The reader takes the setting the owner ruled for fresh judging seats, so a reading costs and judges like the other cold seats it sits beside.
- The holder can accept a flag, because a bar that only a reading with no flag can clear has no guaranteed end; the acceptance carries its reason and the release report lists every one, so the owner judges each from what the holder wrote.
- An acceptance must name exactly one flag of its reading, so a mistyped line fails rather than accepting nothing.
- A flag may list several lines or ranges of its file, because a reader names one finding at several places that way, and the gate holds and clears a flag by its file, never by its lines, so a list owes nothing more. The reader is told the forms the check takes, so it isn't refused for one nobody stated.
- An acceptance naming part of a list names no flag, because the gate keeps no record of a flag's separate places; accepting some would need a second kind of flag, so a holder accepts or routes a list flag as one unit.
- The gate judges every stored return with the current form check each time it runs, and the stage's verdict at the time is kept nowhere, so a return refused only for a form the check now takes counts as a reading from then on, and its change owes its post if it is the newest.
- An `open` quoting a refused return says so, with that return's first form error, because a holder told only that its quote differs goes looking for a copying error instead of running the reading again.
- A `Can tell: no` can't be accepted, because why the change was made must reach the record that outlives it.
- There is no round cap, because every flag is either judged by a later reading or accepted with a reason, and a cap would let a change close over a flag nobody judged. A flag that keeps coming back ends when the holder accepts it or names it a false claim about the tree, which is probed; a passage of the wrong shape, which is restated whole; or a fork, which is put to the owner.
- Every judgement fails closed, so a `clean` can't pass over a flag, a reading or a record the gate can't see.
- The reader works in its tree's folder, so that folder holds the tree alone; a record or prompt there would name the change.
- A reading recorded before the records kept it still counts, because pull requests open when that layout changed hold such readings.
- The reading tree is kept after the run, though the gate needs only its record, so that what the reader saw can still be inspected when a holder disputes a flag.

**Decisions in force:** D-795, seat defaults follow the owner's rulings; D-944, code carries its reasons; D-952, the cold reader reads each change for its reasons; D-968, a consumer tree keeps its record elsewhere; D-997, a flag may name several lines.

## The cloud route

**What it does now.** For a repository with an entry in the machine switch `~/.tradecraft/cloud-builds.json`, the Claude implementer's launches run as a Claude Code cloud session fired through that repository's routine, and a Codex launch is untouched. The route carries the artifact, build, review-disposition and floor stages; any other Claude implementer stage, such as a source-verification account, stays local. A resume follows its session, so the switch has two exceptions: a session started locally before the repository was set up resumes locally, and a `cse_` cloud session resumes in the cloud after the switch entry is removed (`cloud_build.py`); both are transitional. A cloud review-disposition returns its replies, which the holder posts (`work.py`). The launcher reads the routine's token from the file the entry names, moves the shared practice pin forward to the installed plugin's commit when it is behind, writes the task to a report branch in one `[skip ci]` commit, and fires the routine with a short header naming the work, checkout, practice commit and report branch. The run checks its practice clone first (`hooks/cloud.py`, as a prompt hook and as the saved prompt's first command; the second still stops a run whose practice hooks didn't load, such as one in an environment without the plugin directory set, where the prompt hook never runs), does the task, and pushes its report and the list of instruction files it loaded. The practice's `Stop` hook totals the session's usage over distinct message ids across the main and subagent transcripts, records the main session's model, effort and permission mode, copies the practice check, and pushes `usage.json`; a `usage.json` naming the pushed report's blob is the finish signal. The launcher then checks the report branch (the practice check, `[skip ci]` on every commit, the session's `environment` settings, its permission mode, for a build that the change branch advanced, and that the local tree followed it), keeps the report as the published output, posts it on the issue, deletes only the report branch it named, and fast-forwards the local tree. A revision or repair is a follow-up message into the same session, on the version that session loaded. Setup (`cloud_setup.py`) writes the routine's create body and compares every read-back with it.

**Why.**

- The route gives the implementer a machine that can't reach the owner's, so a failed launch refuses and never falls back to a local builder, and the before-and-after comparison of the owner's machine has nothing to compare.
- The task travels on the report branch because a composed prompt is larger than the fire accepts; the fire carries only the header.
- The report comes back on a branch because a run's own issue comments are refused by its safety screen, and a message to another session elevates the run.
- The practice pin follows the plugin install record's commit, never a checkout's `HEAD`, so it moves once per plugin update and never on a merge, and a reload clears an older launcher's refusal.
- A started session can't load a newer practice, so a follow-up keeps its session's version and records both commits; a new session loads exactly the installed one.
- The practice clone excludes the practice repository's own `CLAUDE.md`, `AGENTS.md` and `.claude/`, so its repository doctrine never governs a product build; a clone holding one is treated like a clone at the wrong commit.
- The cost comes from a hook the runtime runs, not from the builder's own counting, and the launcher re-checks the hook's ledger without the transcript; a ledger it can't stand behind makes the cost unknown and leaves the attempt's work alone.
- The attempt checks (practice, `[skip ci]`, `environment`, permission mode, change branch and local tree) reuse the launch-findings hold, so a failure shows to the holder without discarding the report. The local-tree hold alone is released only by the tree containing the returned branch tip, never by a launch account: an account can't make a stale tree current, and the use stage builds its consumer tree from that tree. A run stopped by a practice mismatch did nothing, so its record carries only the mismatch.
- The ledger re-check names each fault by its check: `sums` (the ledger's per-model sums equal the totals), `repeated id` (no message id counts twice), `earlier ledger` (a follow-up's ledger keeps every earlier row unchanged), `deltas` (the recorded deltas sum to the running total) and `unread files` (every listed transcript file was read). The same names reach a cost recorded as unknown.
- A cloud session's environment belongs to its routine, so D-924's two settings are set once, as environment variables on the cloud environment, rather than per launch: background tasks off, and a fixed command ceiling no longer than the shortest stage limit. `cloud_setup.py profile` prints both. The `Stop` hook records the values it saw, and the attempt's `environment` check passes when background tasks are exactly off and the ceiling is positive and no longer than that limit; anything else fails it and holds the next stage like the other attempt checks. A shorter ceiling passes, so a stage limit that later grows isn't a failure; one that shrinks needs the environment's ceiling lowered to match. The routine also disallows the tools a local launch excludes (`Monitor`, `ScheduleWakeup`, `CronCreate`, `Workflow`), and `verify` checks them in the read-back.
- The registered hooks run in every session that loads the plugin, local ones included, so each command is guarded in the shell by `CLAUDE_CODE_REMOTE` before any interpreter starts: a local session starts no Python, and a machine without `python3` on its path shows no error. Each hook names `bash` as its shell, because the guard is POSIX syntax and Claude Code otherwise runs a hook through PowerShell on a Windows machine without Git Bash; the practice needs Git, and Git for Windows installs Git Bash. Codex loads the same manifest and runs a hook through PowerShell on Windows, ignoring `shell`, so each command opens with a line that both shells accept: PowerShell reads the rest as a block comment, and bash never reaches its close.
- The route carries the stages that write the change and the repairs that continue its session (artifact, build, review-disposition, floor); any other Claude implementer stage, such as a source-verification account, writes nothing to the change and starts no session a repair would continue, so it stays local, where D-939's guard and comparison still fence it.
- Both resume exceptions stand because the alternative either starts a fresh builder, losing the session that holds the change's context, or stalls the change.
- A cloud review-disposition posts nothing and returns its replies for the holder to post, because a cloud run's own GitHub posts may be refused by its safety screen. The entrance names the holder's step while a returned reply isn't on the pull request: a thread reply counts once a marker producer has replied in that thread after the run, and a conversation reply once its text is posted, since a conversation comment has no thread to tie it by. A missing or malformed reply block names the step with its fault, because a run that broke its return contract is the holder's to see before anything is re-dispatched. A thread the run left without a reply still goes back to the builder through the thread check.
- That a cloud session loads the product clone's own `CLAUDE.md` and `AGENTS.md` natively is untested, so the cloud preamble tells the run to read them itself, and the run's own `instructions.md` reports which instruction files it loaded.
- The practice's own repository is refused, because its product and practice clones would share one folder and its committed guard would govern a single-source build.

**Decisions in force:** D-938, a set-up repository's Claude implementer runs as a cloud session with no local fallback, its cost counted by the shipped `Stop` hook and re-checked against its ledger, and the practice's own repository refused; D-938 narrows D-939 for cloud launches, which have no local file-tool guard, no before-and-after comparison and no memory setting, and which the owner's global instructions don't reach; D-938 narrows D-924 for cloud launches in that the command ceiling is fixed on the cloud environment rather than set per launch, its notice travels in the cloud task's preamble, and the stream check reads not applicable; the hook manifest is exempt from the harness-token rule of D-156, D-222 and D-618, because it must name the plugin root; D-938 narrows D-911 for cloud launches, which use no `--add-dir` or shim, are told to read the product clone's own `CLAUDE.md` and `AGENTS.md`, and record the instruction files from the run's own `instructions.md`, because the launcher can't read a cloud transcript.

## The launch's working copies and branches

**What it does now.** A local Claude author or builder launch keeps its helpers in its own tree. Its own instruction file, written for every launch and loaded through `--add-dir` (`dispatch_implementer.py`), opens with the rule: run helpers in this tree, give no `Agent` call an `isolation` value, don't use `EnterWorktree`, and make no other working copy or branch from the shell. The launch's pre-tool check (`tree_write_guard.py`) refuses an `Agent` or `Task` call that sets any `isolation` value, one whose type's definition sets `isolation`, one whose type it can't find, and every `EnterWorktree` call. It looks a type up in the user's agents, the tree's `.claude/agents`, the launcher plugin's and each built-in plugin's, and allows a type no definition names only when it is in `BUILTIN_SAFE_TYPES`. A definition it can't read with certainty refuses the call: one it can't decode or finish, or one that sets `name` or `isolation` in any form but a plain top-level `key: value` line. The launch reads every definition before it starts, so such a file fails the launch rather than a helper call mid-turn. Each refusal says what was asked, why, where to work and what to use instead, and lands in the run record's guard refusals beside the file-tool ones. A copy made by a shell command such as `git worktree add` is not refused, because the check sees only tool calls; the comparison below finds it.

The comparison of a Claude launch (`launch_bound.py`) also reads, before and after the run, each covered repository's working copies (`git worktree list`) and local branches with their tips, plus how it found the default branch: the remote's `HEAD`, from `origin` or the only remote; for a repository with no remote, its main working copy's branch; and none where a remote has no `HEAD`, so a named change on whatever branch the main copy has checked out holds. Every covered repository is compared, the run's own included. Only the copy at the run's root and its checked-out branch are the run's own; the root copy of another overlapping recorded run and its branch are attributed to that run. A branch change checked out at a changed copy is folded into that copy's entry. An entry holds only when the run's own record (its stdout stream) names it in a tool call's input, by the recipient or a helper: a branch by its whole name or as the last part of a path, as `git worktree add ../x` names the branch `x` it makes; a copy by a path at or inside its top in no deeper known copy, quoted and escaped paths read whole, absolute or relative to one of the calling agent's bases (its root and every directory it named in `cd`, `pushd`, `Set-Location` or `git -C`). Every other entry is `listed` without holding. The default branch's own entry, and a copy whose only change is a default-branch tip, are always listed. `finish` raises on a refs plan given no record, which the launch records as `unrecorded`; a record it can't read holds every entry except the default-branch ones. Working out each repository's copy and branch entries, reading the run's record and matching it run inside the comparison's allowance (below), checked between repositories but never inside one. When the allowance ends first, the record reads `not-read`, a repository whose entries were not all attributed or classified reads `uncompared` with how many were examined, its default-branch entries still listed, and a changed repository whose entries were never worked out reads `uncompared` too, with none of its working copies and branches examined. A final line left unfinished, even cut inside a character, is skipped, because a stopped launch leaves one. Nothing is ever removed: the comparison runs only `rev-parse`, `worktree list` and `for-each-ref`.

**Why.**

- An instruction alone competes with an owner's rule to give each helper its own copy and can lose; a refusal alone leaves the recipient guessing. Until a refused call stops discarding a launch's return, each refusal costs that launch its report, so the instruction keeps refusals rare.
- Every `isolation` value asks for a copy other than this tree, so none is allowed.
- A definition's `isolation` can't be seen in the call, so a type is allowed only when it is known to take no copy, and an unknown type is refused until a live launch confirms it.
- `EnterWorktree` with a path moves the session to another copy, where the file guard refuses every edit anyway.
- The pre-tool check can't stop a copy made from the shell, and the tree walk stops at every nested copy, so only the refs comparison sees one.
- Holding on every new copy would hold on the sessions and helper copies others start during a long build; the run's record logs every helper's shell commands, so holding on the ones it names finds the run's own leftovers.
- A whole-name or deepest-copy match keeps a prefix or part of a name from holding. Relative paths resolved against every base an agent named can hold more often than exact working-directory tracking, never less. Every string in a tool call's input counts, text written into files included, so a common branch word or a `..` in file content can hold too; holding too often is the safe direction.
- Nearly every record names the default branch and other sessions move it, so it never holds, even when the record can't be read.
- A copy can hold the only record of a helper's work and a branch can belong to another session, so cleanup is the owner's decision.

**Decisions in force:** D-996, the comparison's allowance, inside which the record is read and matched; D-987, a launched Claude author or builder is told to keep helpers in its tree and refused any helper copy, and its comparison holds only on the working copies and branches its record names; D-939, the launch's file-tool guard and before-and-after comparison, which this section extends; D-911, the launch's instruction loading through `--add-dir`, which this section widens to every Claude launch.

## The launch comparison's crediting and allowance

**What it does now.** After a writing Claude launch's after-walk, `compare` (`launch_bound.py`) first sorts every change in memory. An edit inside the run's own tree is its own work. A change no other run could account for is a finding at once: an item the walk could not compare, a changed dispatch record, own request or registry file other than one of its rows, or any change when the run's window can't be read. Only if a change remains that another recorded run could account for, or a covered repository's copies or branches changed beyond the run's own, does it read the dispatch store. It reads it once and works out once which other recorded runs overlapped this run's window (`overlapping_runs`). Every path credit, registry-row credit and working-copy or branch attribution uses that one list, and only what is still unattributed meets the default-branch rule. From the walk's end the comparing gets an allowance: two minutes (`COMPARING_SECONDS`), or until the launcher must begin its final recording (`Deadline.final_write_at`, an eighth of the reserve before the entrance stops waiting at `Deadline.wait_end`), whichever comes first. It is checked after each run record read and each overlap decision, after each change examined, after each repository's copy and branch entries are worked out, and after each line of the run's stream, each event turned into tool calls and each tool call matched. When it ends, nothing more is examined. Each covered item with a change not yet examined is recorded `uncompared`, and its reason names the allowance and how many of that item's changes were examined. Findings and attributions already made stay, an entry still unattributed on the default branch is listed as the default branch, the run's record reads `not-read`, and the comparison reads `findings` whenever an item was left unexamined. Where the allowance ends with nothing left unexamined, as during the read of the run's record when no copy or branch entry waits on it, the comparison stays `clean`, because nothing went unexamined. A comparison that finishes inside the allowance records what it recorded before the allowance existed.

**Why.**

- Working out the overlapping runs for every changed path re-read each recorded run's launcher process once per path, hours for a build that deletes tens of thousands of files. The overlap rule is unchanged; it is only applied once. A run that stops while crediting is under way stays credited, because the window being compared closed when the walk ended.
- The step between the walk and the final record had no limit, and a launcher still in it when the entrance stopped waiting left no final record, its return included. `uncompared` is what the walk already records when it runs out of time, so the entrance already holds on it and the holder already inspects the item it names.
- An unexamined change is never recorded credited or clean, because that would hide damage. Listing is not crediting, and the default-branch rule needs neither the list nor the record, so it still lists when the allowance ends.
- The sort in memory comes before the store read, so a slow read never marks the run's own tree `uncompared` for its own edits.
- The final write keeps an eighth of the reserve, the same gap the entrance leaves between its wait's end and stopping the launcher. After a ceiling stop whose walk used its whole window, that leaves the comparing an eighth of the reserve, 7.5 s at the 60 s reserve of a default stage limit.
- A single step that itself hangs, such as one file read, is not interrupted; the entrance's wait still ends that launch.

**Decisions in force:** D-996, one overlap list and one allowance between the walk and the final record; D-939, the launch's before-and-after comparison, which this section bounds; D-987, the working-copy and branch check, whose two steps run inside the allowance.

## Launch accounts

**What it does now.** A launch whose comparison found changes, or whose cloud attempt check failed, holds the change until the holder accounts for every finding in `launch-account` comments for that launch (`work.py`). The comments that count are a trusted producer's well-formed issue comments for that launch's dispatch, each posted after its findings exist and naming only findings that launch flagged; the hold releases once together they name every finding. Where two of them name one finding, the one posted later governs it. A failed local-tree check is released only by the tree containing the returned tip. While held, the report lists the findings still owed and every comment concerning the launch that didn't count, with its reason.

**Why.**

- An account can run across comments because one comment has a byte ceiling and a launch's findings don't; several comments keep the marker's form, so every account posted earlier reads as before.
- A comment naming a finding its launch didn't flag counts for nothing as a whole, because it was most likely written for another launch and counting part of it would be a guess.
- The later naming governs, because a correction or a retried post is the likely repeat, and treating it as a fault would hold a released change again with only an edit or deletion as a way out; the record stays append-only. Inside one comment a repeat is a writing error, so that comment counts for nothing.
- Posting order is when a comment was created, never when it was edited, so editing an old comment can't take governance back.
- Comments only add names and the flagged set comes from the run record, so nothing posted after a release can hold the change again.
- A failed local-tree check counts as flagged even once the tree has released it, so a comment that named it while it was owed keeps counting.
- An account posted before its findings exist counts for nothing, because finding ids are predictable.
- A comment from another launch is listed on a held launch only when it names one of that launch's findings, so the holder sees a misdirected post without every other launch's accounts.
- A `names-unflagged` reason lists at most ten of the ids, with their count, because a comment written for another launch could name thousands.
- `governing` lists only findings named more than once, because listing every finding would double a flood's report.
- Any comment's text is read, an untrusted author's included, so whatever reading one payload raises makes that comment unread or malformed and never the whole report unreadable, which would refuse every next stage on one stranger's post.
- A comparison that isn't clear holds even when it lists no findings, until a counting comment for its launch exists, because a comparison the entrance can't read as clear is held rather than passed silently.
- The entrance only reads accounts and never posts one, so it checks no comment size; GitHub's limit is 262,144 UTF-8 bytes, which an account of a few thousand findings outgrows.

**Decisions in force:** D-939, a Claude launch's writes stay in its tree and an unattributed change holds until the holder accounts for it; D-988, a launch's account may run across several comments, the later naming governing a repeat; D-988 narrows D-939's single exact account to the comments that count together.

## Consumer trees

**What it does now.** `work.py tree` builds a use consumer's tree from committed bytes: a new repository with one neutral detached commit, no remote and no shared history, holding only the declared job paths and loading surfaces, each file proved against its committed blob. Its record of the tree names the change, the source checkout and revision, what was excluded and every carried file, under a digest. `tree` writes that record whole to the entrance's own records, under `trees/`, in a file named by a digest of the tree's resolved path, prints the path as `tree_metadata`, and leaves nothing but the tree in the folder the tree sits in. `run use` takes that path, proves the record's integrity, re-proves the source revision, the neutral repository and the tree's bytes, and launches the consumer with the tree as its root. The cold reader's reading tree is recorded the same way.

Before anything is built or launched:

- `tree` refuses an output that exists, one inside the source, one inside the entrance's records, and one whose folder holds those records at any depth;
- `tree` refuses an output whose folder holds an entrance tree record file, `<tree>.tradecraft-tree.json` for this tree or any other, naming that file and saying to remove it;
- `tree` refuses an output whose own name, or the name of the folder it sits in, carries the change's issue number or an open pull request's number as a whole run of digits, checking the issue number first, without the network; a merged pull request's number is not checked, folders higher up are not examined, and when the issue, its comments or its pull requests can't be read, `tree` refuses;
- `run use` refuses a tree whose folder holds such a record file, naming the file and saying to remove it and rebuild the tree it records, without opening it; any other file beside a tree, such as a job fixture or a second tree, is lawful;
- `run use` refuses a record that isn't at the path derived from the tree it names, one whose digest doesn't match, and every mismatch of source, revision, bytes or repository shape.

`tree` replaces a record left at its path by a tree since deleted, so a deleted tree can be rebuilt where it was; a reading's record is never replaced.

**Why.**

- The tree's folder is the consumer's working space: a consumer lists it and works in it, so a record there would tell it which change it is judging, where the holder's checkout is, and what was withheld.
- The record's name is derived from the tree's resolved path, compared as the platform compares paths, so a record still proves which tree it belongs to without sitting next to it, and one copied to another tree's path is refused.
- Only the entrance's own records beside a tree are refused, because a tree built before the record moved, or one with its record put back, keeps the exposure, while side-by-side trees and job fixtures are layouts a job needs. A sibling tree's record counts too: it names its change as plainly to a consumer listing the folder.
- `tree` refuses a path with the record file beside it, because a tree built there would meet `run use`'s refusal again; removing the file is the holder's, since the entrance never opens it to tell whose it is.
- Only an open pull request's number is checked, because an open pull request is the change under test, while a merged one belongs to work already landed, such as an earlier instalment.
- Only the tree's folder and the folder it sits in are checked for the change's numbers, because those two names appear in every command the consumer runs and are the ones a holder chooses; folders higher up are usually named by the runtime, and the random digits of a session id would refuse holders by chance.
- An unreadable pull-request lookup refuses, because a check that can't be decided would otherwise pass the path it exists to stop.
- The entrance's records may not sit in or below the tree's folder, so that nothing but the tree is there for every tree, including one built in the home folder.
- A stale record is replaced because a holder who deletes a tree can't see its record to delete it too, and a record proves nothing without its tree.
- Every record is written to a temporary file and then moved into place, so a partial record never stands.
- This keeps the record out of the consumer's folder only. A consumer whose shell reaches the rest of the machine can still find the entrance's records, which is a separate exposure.

**Decisions in force:** D-726, the entrance is the holder's instrument, which builds neutral, mode-declared, history-free consumer trees; D-736, a landed commit is a lawful consumer-tree source; D-968, a consumer tree keeps its record elsewhere.

## Pricing a run

**What it does now.** `change_cost.py report` prices each recorded run from two price files: the shipped card, `lib/rates.json`, and the repository's own `.tradecraft/rates.json` at the top level of the checkout it runs in, or of `--root`. For each model and time, a shipped row that covers the use wins; a repository row is used only where no shipped row covers it, and when both cover one model the report lists the repository entry under `repository_entries_now_shipped` as removable. Every priced share records which file priced it. A damaged repository file, or a row in it that is incomplete, still holds a `FILL` placeholder, or carries a price that isn't a finite nonnegative number, is named under `price_files` and left unused, and the report runs on; a damaged shipped card stops the report, as before. The report never writes either file.

A model that no row prices, including one whose row has ended, no longer makes its run unknown. In a dispatch, that model's share comes from the runtime's own figure when the runtime recorded one marked `costBasis: "list"`, labelled `runtime-list-price` with no card amount; otherwise the share is left out and the run's figure is a floor whose reason names the model. A Codex dispatch has no runtime figure, so its missing model is always a named floor. In a holder transcript, replies on such a model are left out, and the row's floor gives the reply count for each model; when they are the only replies, the row is known at zero. Any other fault keeps the run unknown, as before. `total.runtime_list_price_models` lists the models a runtime figure priced. A subagent's transcript replies count as covered by a dispatch only for a model that dispatch priced.

A row may carry `prompt_tiers`, each a threshold and its own classes: a request whose prompt, its input plus cache reads plus cache writes, is above a threshold takes that tier's prices, and one at or below every threshold takes the row's own. Tiers are applied where each request's counts are kept, which is each transcript reply. Where only a run's totals are kept, a tiered model is never priced from the card; it takes the runtime's list figure or a floor that says it is priced per request.

When a dispatch carries only the aggregate cache-write count, the comparison with the runtime's list figure accepts the card's figure at either the one-hour or the five-minute write price, and records which reading matched; any other difference above a cent is flagged and the card's one-hour figure used, as before.

Wherever a model has no price, whether the run ends known, as a floor or unknown, the report's `missing_prices` names it with the vendor's posted pricing page, the uses that met it, the repository file to paste into, and a ready-to-fill entry in the vendor's shape. Each price and the retrieval time in the entry is a `FILL` placeholder naming the page column to copy, `effective_from` is midnight UTC of the earliest affected use, and `new_file` gives the whole file when none exists.

**Why.**

- One unpriced helper model, under two cents, left a $3.75 author turn and a $10.32 build read unknown, so the owner's cost figures came back without their largest stage. A floor that names the model keeps every share the card prices.
- The runtime's figure is trusted only when marked as a list price, because a runtime too old to know a model charges it at another model's rates and marks that figure otherwise.
- The repository file sits in the repository, not beside the shipped card, because the shipped card lives in the installed plugin, where an entry pasted there would be lost at the next update and would show as a change to the plugin.
- A shipped row beats a repository row, because the practice checks the shipped card against the posted page and a pasted entry is checked by no one; the note says when the pasted one has served its purpose.
- A damaged repository file doesn't stop the report, so a half-filled paste can't take away every other figure, and the guidance still shows how to finish it.
- The guidance is built from where a missing price was met, not from the run's final status, so a run that ends unknown for another reason still says how to price the model.
- Tiers are not applied to totals, because totals can't show which requests crossed the threshold, and pricing them at the lower tier would understate them by up to five times.
- A helper subagent writes five-minute cache and a main conversation writes one-hour cache, while `modelUsage` reports only their sum. Without the second reading, every recorded helper share would be flagged against a runtime figure that was right.
- No reading of the live page while a report runs and no command that writes an entry, because the owner chose report guidance for adding a model.

**Decisions in force:** D-936, price every model a run used and say how to add a missing price.
