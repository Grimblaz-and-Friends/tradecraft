# Design of the shipped library

**Purpose:** say what the shipped library's mechanisms do now and why, for whoever changes them next. **Audience:** a session or person opening code here that points at one of these sections. **Success:** that reader finds the reasons behind the code here, complete, without the issue that built it or any decision record.

The decision log stays in the practice's own repository and doesn't ship, so this document is where a reader of the library finds the reasons, and each section states its reasons whole. The decisions in force are named by their decision-log ids for a maintainer searching the log; they are not pointers a reader follows. Code added under the code-reasons standard opens with a pointer to its section; existing code is brought in by the repository's catch-up.

## The cold reader

**What it does now.** Once a builder turn exists for a change, `run cold-reader` builds an isolated reading tree from the change set. The tree carries every changed regular file, whatever its contents, and a change holding a file the tree can't carry, such as a symlink, is refused as `cold-reading-tree-refused`, naming the path; for each file the reading covers, the Markdown file each `path#anchor` pointer in it names; and the files linked inside that anchored section. A first reading covers every changed file, and a reread covers only the files it owes, though it still carries the rest for reference. All of it is verified against its committed blobs in one neutral detached commit; the archive ignores the machine's line-ending settings, so any repository builds, while an attribute the repository itself sets that rewrites committed bytes, such as `eol=crlf`, still does and is refused. A tree that names the change's branch is refused before launch, and issue or pull-request numbers in any carried file are counted as residue. One fresh read-only seat, on Claude unless the change names another, reads the tree against the code-reasons standard and returns an account in a fixed form, ending with a capped handful of excerpts it nominates as worth a look. The stage checks only that form, including that each flag names a file the tree carries other than the diff file. A flag's location gives its path and, optionally, one line, one range, or a comma list of either; any other malformed flag line refuses the whole return.

The holder posts the account whole in one `open` comment with its own review against the brief beneath it. In that review it accepts any flag it judges not worth another round, one `Accepted:` line per flag with a one-line reason; an acceptance that names no single flag sets the comment aside. An acceptance names a list flag by its whole list, the same items in the same order whatever the dash or comma spacing, and one naming part of a list names no flag. An `open` quoting a return the form check refuses is set aside with that return's first form error, and one quoting no retained return is set aside as differing. An accepted flag doesn't stand and owes no reread, and a `Can tell: no` can't be accepted. The resumed builder reviews the account and fixes what the holder routed. A later `clean` comment closes the reading. It counts only when posted after the builder's review of the latest `open` reading, or after that `open` itself where the acceptances leave nothing standing or owed, at the current head, with nothing below still owed; on every hold the gate returns, a `clean` posted after the latest `open` is set aside as invalid, while one posted before it closed an older reading and is left alone. Until a current `clean` stands, the entrance's decision holds readiness, use, proof and the release report, and it asks only once the change's floor has passed:

- a reading is current per changed file, by the file's blob and the blobs of the document its pointer names and the files linked inside that section;
- a flag the holder didn't accept stands until a later reading that read its path, or a document or record a path it read depends on, no longer raises it; once nothing in the change reaches its path, the reread of what changed answers for it;
- after the builder's review, a reread covers every stale file and every changed file that a standing flag names, or whose pointer reaches the document or listed record it names;
- a `Can tell: no` stands until a later reading of the whole change says `yes`;
- a damaged record holds the gate as unverifiable rather than vanishing;
- only this pull request's readings count: a reading records its branch and pull request, and one recorded without them counts only when this change's history holds the head it read;
- the builder is resumed only for what the latest `open` routed to it, a flag left unaccepted or a `Can tell: no`, and only a turn that returned something counts as its review;
- an `open` carries the head its reading read;
- `run ready-reviewers`, `run use`, `run proof` and `run release-report` refuse while the gate holds, because naming a stage skips the decision the gate sits in; each reports its own refusals first, since a repair those owe would stale the reading anyway.

The reader launches on its role's vendor and records a same-vendor reason whenever it lands on the builder's vendor, fallback included, and it never starts until a build bundle or the builder's session marker proves which vendor built the change.

The reading tree is built in a temporary folder of its own, holding only the tree and outside the entrance's records, which keep the reading's record and diff, written as consumer trees' records are, and its prompt. The gate finds a reading's record there or, for a reading recorded before the records kept it, where that reading left it, beside its tree; a record found in neither place is reported at its path in the records. The tree itself is kept after the run; a tree whose record could not be written is removed, with any diff written for it, because no reading can be judged without its record.

**Why.**

- A reader who saw the brief can't show what the code alone explains, so the reader never sees the issue, brief, pull-request text or branch name.
- The entrance, not the holder, chooses the inputs and composes the prompt, because whoever holds the brief could aim the reader through them.
- The tree follows only `path#anchor` pointers, never a file a changed file merely mentions, because that is the one route the code-reasons standard gives from code to its reasons, and a pointer that doesn't resolve then reaches the reader as the dead end it is rather than being patched by whoever built the tree.
- Every link inside a pointed section is carried, not only its decision records, because the entrance can't tell a decision record by its path.
- The holder's review rides in the `open` comment because a change on the mechanical lane has no holder reading to carry it, and one marker with `open` and `clean` serves every lane alike.
- The builder reviews each posted reading that leaves anything standing or owed, because the builder holds the reasons it decided while building and is the one who fixes what the reading finds; a reading the holder's acceptances leave with nothing to fix closes without that turn, so the loop can end on the holder's judgement, and the holder's own review against the brief still looks for misreadings.
- Every changed path is read, with no classifier deciding what counts as code, because a classifier would be configuration every adopting repository owes.
- Blob identity is what the entrance can compare, and counting the pointed document's blobs rereads a file whose fix landed only in its document.
- A flag must name a file the reading held, and a standing flag owes a reread of what reaches it, so that every flag has a way out through a reading the gate orders.
- The holder takes the owner's release report's excerpts worth a look from the reader's nominations, and the report shows only a few, so the reader nominates only a few.
- The gate waits for the floor because a repair the floor still owes would change the files a reading has just read.
- The reader takes the setting the owner ruled for fresh judging seats, so a reading costs and judges like the other cold seats it sits beside.
- The holder can accept a flag, because a bar that only a reading with no flag can clear has no guaranteed end; the acceptance carries its reason and the release report lists every one, so the owner judges each from what the holder wrote.
- An acceptance must name exactly one flag of its reading, so a mistyped line fails rather than accepting nothing.
- A flag may list several lines or ranges of its file, because a reader names one finding at several places that way, and the gate holds and clears a flag by its file, never by its lines, so a list owes nothing more. The reader is told the forms the check takes, so it isn't refused for one nobody stated.
- An acceptance naming part of a list names no flag, because the gate keeps no record of a flag's separate places; accepting some would need a second kind of flag, so a holder accepts or routes a list flag as one unit.
- The gate judges every stored return with the current form check each time it runs, and the stage's verdict at the time is kept nowhere, so a return refused only for a form the check now takes counts as a reading from then on, and its change owes its post if it is the newest.
- An `open` quoting a refused return says so, with that return's first form error, because a holder told only that its quote differs goes looking for a copying error instead of running the reading again.
- A `Can tell: no` can't be accepted, because why the change was made must reach the record that outlives it.
- There is no round cap, because every flag is either judged by a later reading or accepted with a reason, and a cap would let a change close over a flag nobody judged. A flag that keeps coming back ends when the holder accepts it or names it a false claim about the tree, which is probed; a passage of the wrong shape, which is restated whole; or a fork, which is put to the owner.
- Every judgement fails closed, so a `clean` can't pass over a flag, a reading or a record the gate can't see.
- The reader works in its tree's folder, so that folder holds the tree alone; a record or prompt there would name the change.
- A reading recorded before the records kept it still counts, because pull requests open when that layout changed hold such readings.
- The reading tree is kept after the run, though the gate needs only its record, so that what the reader saw can still be inspected when a holder disputes a flag.

A builder's reading, run from inside a stretch launch's tree, adds three things: its tree is checked again when the reader returns (`cold_reader.tree_held`); its return travels in the seat launcher's frame; and its report is posted from that frame, as A builder's own checks and writes sets out. On the builder route a `clean` after its `open` needs no later builder turn, because the builder writes the `open` itself; on the relay route the rule above stands.

**Decisions in force:** D-795, seat defaults follow the owner's rulings; D-944, code carries its reasons; D-952, the cold reader reads each change for its reasons; D-968, a consumer tree keeps its record elsewhere; D-997, a flag may name several lines; D-1012, a builder's reading is checked again, framed and posted; D-1013, on the builder route the builder posts the `open` and its `clean`.

## The cloud route

**What it does now.** For a repository with an entry in the machine switch `~/.tradecraft/cloud-builds.json`, the Claude implementer's launches run as a Claude Code cloud session fired through that repository's routine, and a Codex launch is untouched. The route carries the artifact, build, review-disposition and floor stages; any other Claude implementer stage, such as a source-verification account, stays local. A resume follows its session, so the switch has two exceptions: a session started locally before the repository was set up resumes locally, and a `cse_` cloud session resumes in the cloud after the switch entry is removed (`cloud_build.py`); both are transitional. A cloud review-disposition returns its replies, which the holder posts (`work.py`). A cloud prompt carries its route's GitHub write allowance sentence, and the cloud run record's `github_write_bound` reads `not-run` (`cloud_build.py`). The launcher reads the routine's token from the file the entry names, moves the shared practice pin forward to the installed plugin's commit when it is behind, writes the task to a report branch in one `[skip ci]` commit, and fires the routine with a short header naming the work, checkout, practice commit and report branch. The run checks its practice clone first (`hooks/cloud.py`, as a prompt hook and as the saved prompt's first command; the second still stops a run whose practice hooks didn't load, such as one in an environment without the plugin directory set, where the prompt hook never runs), does the task, and pushes its report and the list of instruction files it loaded. The practice's `Stop` hook totals the session's usage over distinct message ids across the main and subagent transcripts, records the main session's model, effort and permission mode, copies the practice check, and pushes `usage.json`; a `usage.json` naming the pushed report's blob is the finish signal. The launcher then checks the report branch (the practice check, `[skip ci]` on every commit, the session's `environment` settings, its permission mode, for a build that the change branch advanced, and that the local tree followed it), keeps the report as the published output, posts it on the issue, deletes only the report branch it named, and fast-forwards the local tree. A revision or repair is a follow-up message into the same session, on the version that session loaded. Setup (`cloud_setup.py`) writes the routine's create body and compares every read-back with it.

**Why.**

- The route gives the implementer a machine that can't reach the owner's, so a failed launch refuses and never falls back to a local builder, and the before-and-after comparison of the owner's machine has nothing to compare.
- The task travels on the report branch because a composed prompt is larger than the fire accepts; the fire carries only the header.
- The report comes back on a branch because a run's own issue comments are refused by its safety screen, and a message to another session elevates the run.
- The practice pin follows the plugin install record's commit, never a checkout's `HEAD`, so it moves once per plugin update and never on a merge, and a reload clears an older launcher's refusal.
- A started session can't load a newer practice, so a follow-up keeps its session's version and records both commits; a new session loads exactly the installed one.
- The practice clone excludes the practice repository's own `CLAUDE.md`, `AGENTS.md` and `.claude/`, so its repository doctrine never governs a product build; a clone holding one is treated like a clone at the wrong commit.
- The cost comes from a hook the runtime runs, not from the builder's own counting, and the launcher re-checks the hook's ledger without the transcript; a ledger it can't stand behind makes the cost unknown and leaves the attempt's work alone.
- The attempt checks (practice, `[skip ci]`, `environment`, permission mode, change branch and local tree) reuse the launch-findings hold, so a failure shows to the holder without discarding the report. The local-tree hold alone is released only by the tree containing the returned branch tip, never by a launch account: an account can't make a stale tree current, and the use stage builds its consumer tree from that tree. A run stopped by a practice mismatch did nothing, so its record carries only the mismatch.
- The ledger re-check names each fault by its check: `sums` (the ledger's per-model sums equal the totals), `repeated id` (no message id counts twice), `earlier ledger` (a follow-up's ledger keeps every earlier row unchanged), `deltas` (the recorded deltas sum to the running total) and `unread files` (every listed transcript file was read). The same names reach a cost recorded as unknown.
- A cloud session's environment belongs to its routine, so D-924's two settings are set once, as environment variables on the cloud environment, rather than per launch: background tasks off, and a fixed command ceiling no longer than the shortest stage limit. `cloud_setup.py profile` prints both. The `Stop` hook records the values it saw, and the attempt's `environment` check passes when background tasks are exactly off and the ceiling is positive and no longer than that limit; anything else fails it and holds the next stage like the other attempt checks. A shorter ceiling passes, so a stage limit that later grows isn't a failure; one that shrinks needs the environment's ceiling lowered to match. The routine also disallows the tools a local launch excludes (`Monitor`, `ScheduleWakeup`, `CronCreate`, `Workflow`), and `verify` checks them in the read-back.
- The registered hooks run in every session that loads the plugin, local ones included, so each command is guarded in the shell by `CLAUDE_CODE_REMOTE` before any interpreter starts: a local session starts no Python, and a machine without `python3` on its path shows no error. Each hook names `bash` as its shell, because the guard is POSIX syntax and Claude Code otherwise runs a hook through PowerShell on a Windows machine without Git Bash; the practice needs Git, and Git for Windows installs Git Bash. Codex loads the same manifest and runs a hook through PowerShell on Windows, ignoring `shell`, so each command opens with a line that both shells accept: PowerShell reads the rest as a block comment, and bash never reaches its close.
- The route carries the stages that write the change and the repairs that continue its session (artifact, build, review-disposition, floor); any other Claude implementer stage, such as a source-verification account, writes nothing to the change and starts no session a repair would continue, so it stays local, where D-939's guard and comparison still fence it.
- Both resume exceptions stand because the alternative either starts a fresh builder, losing the session that holds the change's context, or stalls the change.
- A cloud review-disposition posts nothing and returns its replies for the holder to post, because a cloud run's own GitHub posts may be refused by its safety screen. The entrance names the holder's step while a returned reply isn't on the pull request: a thread reply counts once a marker producer has replied in that thread after the run, and a conversation reply once its text is posted, since a conversation comment has no thread to tie it by. A missing or malformed reply block names the step with its fault, because a run that broke its return contract is the holder's to see before anything is re-dispatched. A thread the run left without a reply still goes back to the builder through the thread check.
- That a cloud session loads the product clone's own `CLAUDE.md` and `AGENTS.md` natively is untested, so the cloud preamble tells the run to read them itself, and the run's own `instructions.md` reports which instruction files it loaded.
- The practice's own repository is refused, because its product and practice clones would share one folder and its committed guard would govern a single-source build.
- A cloud run is told its route's allowance (push its report branch, and the change branch in a stage that changes it, and post nothing) as a local launch is told its own, because its prompt is the only bound it carries; its `github_write_bound` reads `not-run` because the launch block (the command check, the child settings and the environment) is prepared on this machine and never reaches the remote one ([The GitHub write bound](#the-github-write-bound)).

**Decisions in force:** D-938, a set-up repository's Claude implementer runs as a cloud session with no local fallback, its cost counted by the shipped `Stop` hook and re-checked against its ledger, and the practice's own repository refused; D-938 narrows D-939 for cloud launches, which have no local file-tool guard, no before-and-after comparison and no memory setting, and which the owner's global instructions don't reach; D-938 narrows D-924 for cloud launches in that the command ceiling is fixed on the cloud environment rather than set per launch, its notice travels in the cloud task's preamble, and the stream check reads not applicable; the hook manifest is exempt from the harness-token rule of D-156, D-222 and D-618, because it must name the plugin root; D-938 narrows D-911 for cloud launches, which use no `--add-dir` or shim, are told to read the product clone's own `CLAUDE.md` and `AGENTS.md`, and record the instruction files from the run's own `instructions.md`, because the launcher can't read a cloud transcript; D-986, a cloud build is told its routine's GitHub write allowance and its run record says the launch block did not run. D-1003, a cloud recipient's window opens at the send, and the route's sign-in check and pushes before it are bounded by the entrance's cap.

## The launch's working copies and branches

**What it does now.** A local Claude author or builder launch keeps its helpers in its own tree. Its own instruction file, written for every launch and loaded through `--add-dir` (`dispatch_implementer.py`), opens with the rule: run helpers in this tree, give no `Agent` call an `isolation` value, don't use `EnterWorktree`, and make no other working copy or branch from the shell. The launch's pre-tool check (`tree_write_guard.py`) refuses an `Agent` or `Task` call that sets any `isolation` value, one whose type's definition sets `isolation`, one whose type it can't find, and every `EnterWorktree` call. It looks a type up in the user's agents, the tree's `.claude/agents`, the launcher plugin's and each built-in plugin's, and allows a type no definition names only when it is in `BUILTIN_SAFE_TYPES`. A definition it can't read with certainty refuses the call: one it can't decode or finish, or one that sets `name` or `isolation` in any form but a plain top-level `key: value` line. The launch reads every definition before it starts, so such a file fails the launch rather than a helper call mid-turn. Each refusal says what was asked, why, where to work and what to use instead, and lands in the run record's guard refusals beside the file-tool ones. A copy made by a shell command such as `git worktree add` is not refused, because the check sees only tool calls; the comparison below finds it.

The comparison of a Claude launch (`launch_bound.py`) also reads, before and after the run, each covered repository's working copies (`git worktree list`) and local branches with their tips, plus how it found the default branch: the remote's `HEAD`, from `origin` or the only remote; for a repository with no remote, its main working copy's branch; and none where a remote has no `HEAD`, so a named change on whatever branch the main copy has checked out holds. Every covered repository is compared, the run's own included. Only the copy at the run's root and its checked-out branch are the run's own; the root copy of another overlapping recorded run and its branch are attributed to that run. A branch change checked out at a changed copy is folded into that copy's entry. An entry holds only when the run's own record (its stdout stream) names it in a tool call's input, by the recipient or a helper: a branch by its whole name or as the last part of a path, as `git worktree add ../x` names the branch `x` it makes; a copy by a path at or inside its top in no deeper known copy, quoted and escaped paths read whole, absolute or relative to one of the calling agent's bases (its root and every directory it named in `cd`, `pushd`, `Set-Location` or `git -C`). Every other entry is `listed` without holding. The default branch's own entry, and a copy whose only change is a default-branch tip, are always listed. `finish` raises on a refs plan given no record, which the launch records as `unrecorded`; a record it can't read holds every entry except the default-branch ones. Working out each repository's copy and branch entries, reading the run's record and matching it run inside the comparison's allowance (below), checked between repositories but never inside one. When the allowance ends first, the record reads `not-read`, a repository whose entries were not all attributed or classified reads `uncompared` with how many were examined, its default-branch entries still listed, and a changed repository whose entries were never worked out reads `uncompared` too, with none of its working copies and branches examined. A final line left unfinished, even cut inside a character, is skipped, because a stopped launch leaves one. Nothing is ever removed: the comparison runs only `rev-parse`, `worktree list` and `for-each-ref`.

**Why.**

- An instruction alone competes with an owner's rule to give each helper its own copy and can lose; a refusal alone leaves the recipient guessing. Until a refused call stops discarding a launch's return, each refusal costs that launch its report, so the instruction keeps refusals rare. A stretch launch is the exception: its run stands after a refusal it recovered from (see A builder's own checks and writes).
- Every `isolation` value asks for a copy other than this tree, so none is allowed.
- A definition's `isolation` can't be seen in the call, so a type is allowed only when it is known to take no copy, and an unknown type is refused until a live launch confirms it.
- `EnterWorktree` with a path moves the session to another copy, where the file guard refuses every edit anyway.
- The pre-tool check can't stop a copy made from the shell, and the tree walk stops at every nested copy, so only the refs comparison sees one.
- Holding on every new copy would hold on the sessions and helper copies others start during a long build; the run's record logs every helper's shell commands, so holding on the ones it names finds the run's own leftovers.
- A whole-name or deepest-copy match keeps a prefix or part of a name from holding. Relative paths resolved against every base an agent named can hold more often than exact working-directory tracking, never less. Every string in a tool call's input counts, text written into files included, so a common branch word or a `..` in file content can hold too; holding too often is the safe direction.
- Nearly every record names the default branch and other sessions move it, so it never holds, even when the record can't be read.
- A copy can hold the only record of a helper's work and a branch can belong to another session, so cleanup is the owner's decision.

**Decisions in force:** D-1013, every file-guard decision is logged with its time, so a launch's logged refusals pair in order with those its builder reports; D-1012, a stretch launch's run stands after a refusal it recovered from; D-996, the comparison's allowance, inside which the record is read and matched; D-987, a launched Claude author or builder is told to keep helpers in its tree and refused any helper copy, and its comparison holds only on the working copies and branches its record names; D-939, the launch's file-tool guard and before-and-after comparison, which this section extends; D-911, the launch's instruction loading through `--add-dir`, which this section widens to every Claude launch.

## The launch comparison's crediting and allowance

**What it does now.** After a writing Claude launch's after-walk, `compare` (`launch_bound.py`) first sorts every change in memory. An edit inside the run's own tree is its own work. A change the runtime makes in the installed plugins is released next (What a launch comparison releases, below). A change no other run could account for is a finding at once: an item the walk could not compare, a changed dispatch record, own request or registry file other than one of its rows, or any change when the run's window can't be read. Registry rows are compared without folding their roots' case, so a row change hidden behind a case-folded key is a registry finding of its own. Only if a change remains that another recorded run could account for, or a covered repository's copies or branches changed beyond the run's own, does it read the dispatch store. It reads it once and works out once which other recorded runs overlapped this run's window (`overlapping_runs`). Every path credit, registry-row credit and working-copy or branch attribution uses that one list, and only what is still unattributed meets the default-branch rule. From the walk's end the comparing gets an allowance: two minutes (`COMPARING_SECONDS`), or until the launcher must begin its final recording (`Deadline.final_write_at`, an eighth of the reserve before the entrance stops waiting at `Deadline.wait_end`), whichever comes first. It is checked after each run record read and each overlap decision, after each change examined, after each repository's copy and branch entries are worked out, and after each line of the run's stream, each event turned into tool calls and each tool call matched. When it ends, nothing more is examined. Each covered item with a change not yet examined is recorded `uncompared`, and its reason names the allowance and how many of that item's changes were examined. Findings and attributions already made stay, an entry still unattributed on the default branch is listed as the default branch, the run's record reads `not-read`, and the comparison reads `findings` whenever an item was left unexamined. Where the allowance ends with nothing left unexamined, as during the read of the run's record when no copy or branch entry waits on it, the comparison stays `clean`, because nothing went unexamined. A comparison that finishes inside the allowance records what it recorded before the allowance existed.

**Why.**

- Working out the overlapping runs for every changed path re-read each recorded run's launcher process once per path, hours for a build that deletes tens of thousands of files. The overlap rule is unchanged; it is only applied once. A run that stops while crediting is under way stays credited, because the window being compared closed when the walk ended.
- The step between the walk and the final record had no limit, and a launcher still in it when the entrance stopped waiting left no final record, its return included. `uncompared` is what the walk already records when it runs out of time, so the entrance already holds on it and the holder already inspects the item it names.
- An unexamined change is never recorded credited or clean, because that would hide damage. Listing is not crediting, and the default-branch rule needs neither the list nor the record, so it still lists when the allowance ends.
- The sort in memory comes before the store read, so a slow read never marks the run's own tree `uncompared` for its own edits.
- The final write keeps an eighth of the reserve, the same gap the entrance leaves between its wait's end and stopping the launcher. After a ceiling stop whose walk used its whole window, that leaves the comparing an eighth of the reserve, 7.5 s at the 60 s reserve of a default stage limit.
- A single step that itself hangs, such as one file read, is not interrupted; the entrance's wait still ends that launch.
- A stretch launch's comparison, and only one asked for it (`own_row_resnapshot`, which the stretch launch passes), credits one more change as the run's own: its own root's registry row when `revision_before` and `status_before` are all that differ. A stretch builder's catch-up re-snapshots that row after the landing it made, nothing in the library reads those two fields from a row, and the overlap rule can't reach a row the entrance writes in the builder's own run. A builder's own checks and writes sets out the rest of what that launch's comparison sees.

**Decisions in force:** D-1023, the release step, which runs in the sort before any change is credited or found; D-1012, a stretch launch credits its own row's re-snapshot; D-996, one overlap list and one allowance between the walk and the final record; D-939, the launch's before-and-after comparison, which this section bounds; D-987, the working-copy and branch check, whose two steps run inside the allowance.

## What a launch comparison releases

**What it does now.** In a Claude launch's comparison (`launch_bound.py`), the step after the run's own work and before any finding or crediting releases the changes the runtime makes in the installed plugins (`launch_release.py`). Only two items can release: `plugins`, the plugins folder, and `launcher-plugin`, the launcher's own plugin root when no registered checkout is that root. A registered checkout, the registry and the dispatch records never release, bytecode in a checkout included, because a write into a change's tree or the practice's own records is what the comparison exists to catch, and no session's runtime keeps files up there. Paths are read relative to the item's top, name by name, with `\` a separator only on Windows and names compared as the platform compares them; where the walk knows an entry's type, a kind that names a folder or a file releases only that type. The kinds, first match first: `bytecode`, a `__pycache__` folder or a `.pyc` directly in one; `synced-marketplaces`, a `synced` folder at the plugins folder's top and everything under it, whatever its type; `in-use-marker`, a `.in_use` folder or a file directly in it, or a `.last_inuse_sweep` file; `orphan-marker`, a `.orphaned_at` file; `usage-queue`, `store/` at the top or a `.json` directly in it; `catalog-cache`, a top-level `plugin-directory-cache*.json`; and `version-folder`, anything at or under a `cache/<marketplace>/<plugin>/<version>` folder whose own entry was added or removed in this comparison, matched by absolute path, the plugins folder's resolved path included, so that a `launcher-plugin` change under a version the `plugins` walk saw go releases too. Three exceptions read what a change is, not only where. A removed version folder whose path, under either top, is the `installPath` of any entry in the after-reading of `installed_plugins.json` does not release: its entry and each change at or under it that no upkeep kind names hold in either item, with a `reason` naming the folder and the key, scope and project of an entry that names it; where that reading failed, every removed version folder holds, its `reason` naming the failed reading. A `.orphaned_at` added or modified whose parent folder an entry names holds the same way, or, with that reading failed, one whose parent is any version folder; one removed releases, because it takes nothing from what loads and at most keeps a version from being retired. A `.pyc` added or modified directly in a `__pycache__` folder releases only when `release` read 16 bytes of it, as a regular file opened without following a link or waiting, and its flags word (bytes 4 to 8, little-endian) is 0, 2 or 3; flags 1, any higher bit, a short file or a failed read holds, with a `reason` saying which, and a file gone by the read releases. `classify` takes that read as a callable, as it takes `entry_of`, so it does no I/O itself. None of the three applies inside an update's new folder: a version folder added in this comparison that the released `install-record` change's basis names. Without install-record readings, as in `classify_recorded`, the first two don't apply, and without the read the third doesn't. `bytecode`, `in-use-marker`, `orphan-marker` and `version-folder` release in either item; `synced-marketplaces`, `usage-queue` and `catalog-cache`, which live only at the plugins folder's top, release only in `plugins`. `snapshot` reads `known_marketplaces.json` and `installed_plugins.json` at the plugins folder's top inside the item's time budget, keeping the parsed value or why it couldn't be had; only a regular file is read, opened without waiting, and a record that is a link or anything else before or after holds. A modified record releases as `install-record` when both readings parsed and the compared fields are equal (in `known_marketplaces.json`, the marketplace names and each one's `source` and `installLocation`; in `installed_plugins.json`, the plugin keys and each key's entries as `scope`, `projectPath`, `installPath` and `version`), or, for `installed_plugins.json`, when every difference is an entry whose `version` and `installPath` both moved to a version folder of that same plugin (`cache/<marketplace>/<plugin>/…`, as its `<plugin>@<marketplace>` key names) added in the same comparison. An entry is paired with its successor by scope and project, or, when one entry left and one came, with that one. A change under `marketplaces/<name>` releases as `marketplace-refresh` when both readings of `known_marketplaces.json` parsed, name `<name>` and differ in its `lastUpdated`. Every other change goes on to the crediting above. A held install-record change carries a `reason` naming each compared field that differed, with both values, or which reading failed. A released change is recorded under `released`, with an `id` made as a finding's is, its kind and, for the two content reads, its `basis`; `status` stays `findings` exactly when `findings` is non-empty, so a launch whose changes all released reads `clean`, which the entrance reads as clear. The three fixed results carry an empty `released`, and a reader treats a missing one as empty. `lib/tests/release_fixture.py` drives the real snapshot, comparison and entrance reading on a fixture home, one named situation at a time, so a holder or a use session can see what each records and how the entrance reads it.

**Why.**

- Any session's runtime, the app, and any Python process that imports the installed plugin write these files at moments no launch controls, so holding on them would hold a launch for another session's routine work.
- A released kind releases whoever made it, the launch's own commands included. A launch's commands run through most of its window, so the time of a change can't tell the runtime's work from the launch's. The upkeep kinds don't decide what loads, and a whole version folder added or removed is the change the runtime's update makes, installing one version and retiring another, so it releases whoever made it; a fence for what the builder can reach is a separate choice. What a launch could change beyond that still holds: a plugin's or a marketplace's own folder in the plugin cache (`cache/<marketplace>/<plugin>` or `cache/<marketplace>`) appearing or going, a file edited inside an installed version, a version an install entry still names removed or marked for retirement, a compiled file Python won't check against its source, a plugin installed, or an install entry pointed at a path no update in the launch added.
- A plugin's own data folder holds, though the plugin writes it at any moment, because the plugin's code reads what it keeps there, so a write there can change what the plugin does, as a marker, a queue or a cache cannot.
- None of the upkeep files decides what code loads. The bytecode an import writes into a `__pycache__` folder records its source's time and size, and Python rebuilds it when they differ, so the runtime's own bytecode follows its source, and so does one carrying its source's hash with checking on. A third kind carries a hash with checking off, and Python loads it whatever its source says; an import never writes one, and a compile step has to ask for it, so it holds, read from the first 16 bytes of each changed compiled file. The flags are read as Python's default setting reads them, because a loading process's `--check-hash-based-pycs` is its own and the comparison can't see it; under `never`, a checked-hash file would load unchecked too. A header Python refuses holds too, though Python compiles the source again rather than load it, because only the kinds Python checks release; a header that can't be read holds, because nothing shows its kind. A file made to pass the check, carrying its source's time and size over other code, still releases, as any write the comparison does not fence. A compiled file removed leaves nothing to load, so it releases unread, and so does one gone by the read. The rest are markers, stamps, queues and caches. The catalog cache is matched by its name's prefix, so a renamed catalog version still releases; it lists what could be installed, not what loads. The app's sync folder holds account data, never plugin code, so everything under it releases whatever its type, while the folder itself must be a folder. A `.pyc` elsewhere can load with no source to check it against, so it still holds.
- A whole version folder appearing or going is the runtime's update. The app retires a version only after the install record has moved off it, and marks it for retirement the same way, so a removed version, or an orphan marker on one, that an entry of `installed_plugins.json` still names after the launch is never its work, and after such a removal that plugin no longer loads; it holds. Any entry counts, whatever its key, scope or project. Whether the app would later delete a marked version an entry still names is not known, and the hold doesn't depend on it. Keying instead on whether a version of that plugin was added would hold every routine retirement, which adds none. A reading that failed after the launch can't show that no entry names a version, so every removal and every marker at a version's top holds then. `classify_recorded` has no readings, so it keeps releasing a removed version folder by name. Editing an installed version in place is never the runtime's work, so a change inside a version folder that stayed still holds, and so does a plugin's or a marketplace's own folder in the plugin cache appearing or going, because that changes what loads. A marketplace's clone under `marketplaces/` is read by its refresh instead, below.
- The two install records decide which plugin code every later session loads and where its updates come from, so a launch that changed them in any way but an update to a version folder of the same plugin still holds, but the app rewrites their time fields at every refresh. Reading only the fields that decide loading releases the refresh and keeps the change. A field the app adds later is ignored rather than held, because only the listed fields decide what loads. They are the only files read for their contents, and only the release's basis and a held change's reason carry any of it into the run record.
- A marketplace clone changes when the app refreshes it, and the refresh moves that marketplace's `lastUpdated`, so a clone change with no refresh still holds, and one with a refresh releases, the clone's own folder appearing or going included.
- A kind that names a folder or a file releases only that type where the walk knows it, because a link, or a folder named like an upkeep file, is not what the runtime writes there and could point anywhere or hold anything. A recorded finding carries no type, so `classify_recorded` reads names alone.
- An update moves a plugin to its own new version, so an entry moved into another plugin's version folder holds. An install entry is paired with its successor so that an update reads as one entry's move, which can release, and a held change can name the field that moved rather than an entry gone and another come. Scope and project identify an entry, because one plugin can be installed once per project; a lone pair is one entry, so a change of scope or project is named as that field.
- The first matching kind names a change, so each released change has one kind; every kind releases, so the order decides only the name, and an in-use marker inside a retired version is recorded as the marker it is.
- The release is made at the comparison, not at the entrance, because only the comparison has the install records' starting contents, and so a record made before releases existed keeps its findings and hold untouched; reading it under these rules would release some findings and not others.
- A released change stays in the record so a holder, or a read across changes, can see what changed and catch a kind that releases more than it should. Its `id` is made as a finding's is, so a read across launches can match it with the same change where it held elsewhere; a launch account names only that launch's findings, so it never names a released id.
- Elsewhere than Windows a backslash is part of a name, so a folder named with backslashes is one name and can't pass for an installed version's path. The launcher's root is a resolved path while the plugins folder's may run through a link, such as a linked `~/.claude`, so a version folder is matched under both. An install record or a compiled file's header is read only as a regular file because a link would let a record's contents change behind an entry the walk sees as unchanged, or point a header's read at another file than the one walked, and a pipe would stall either read past the allowance.
- Releasing is decided in memory before the store is read, so a released change never needs a recorded run and a slow store read never leaves it unexamined. The release step checks the allowance after each change like the rest of the sort, and again after each compiled file's header read, the only read it makes, because a slow disk can spend the allowance on it; so an allowance spent before the step finishes still leaves the item `uncompared`.
- `classify_recorded` applies the same rules to a finished record's findings, for measuring them against recorded launches; neither the comparison nor the entrance calls it, because a record made before releases existed keeps its hold. It reads names alone, since a record keeps no entry types or install-record contents, so install records and marketplace clones hold there.
- The comparison sees the folder before and after, not who wrote to it, so five changes a launch's own commands can make release because each can leave exactly what the app's update, refresh, import or retirement leaves, and only a fence on what a launch can write would stop them. A plugin update the launch made itself, a new version folder with that plugin's entry moved to it, releases as the app's update does, and every later session loads its code. Everything inside that new folder releases with it, compiled files and markers included, because the launch could have put any code there, and later sessions load it with the update; a newly installed plugin's first folder, or an added folder no entry moved to, is not an update's, so the holds above apply there. A marketplace's clone edited while its refresh time moves releases, and later installs and updates from it take what the clone holds. A compiled file made to carry its source's time and size releases, and every later session that imports the module runs it. A version no entry names, removed while a running session still uses it, releases as the app's retirement of an old version does, and the sessions running from it lose its files at once: an in-use marker names its process inside the file, which the comparison doesn't read, and markers of finished sessions go with routine retirements too. The work cell's launch-findings reference names all five under *What a clear launch does not prove*, because a hold keyed to what the launch's own commands name would fire on reads and prose and miss a write made from a script, and holding every update would hold the app's own.

**Decisions in force:** D-996, the comparison's allowance, which the release step checks after each change; D-1043, a named version removed or marked and a compiled file Python won't check hold, chosen over keying a removal on an added version, over holding or releasing all bytecode, and over holding an update the launch's commands name, with the five changes that still release stated instead; D-1023, what a launch comparison releases, chosen over crediting a change by whether the run's own commands were running and over fencing the builder, and reading the two install records against D-939's stat-only comparison; D-939, the launch's before-and-after comparison, which this section narrows.

## Launch accounts

**What it does now.** A launch whose comparison found changes, or whose cloud attempt check failed, holds the change until the holder accounts for every finding in `launch-account` comments for that launch (`work.py`). The comments that count are a trusted producer's well-formed issue comments for that launch's dispatch, each posted after its findings exist and naming only findings that launch flagged; the hold releases once together they name every finding. Where two of them name one finding, the one posted later governs it. A failed local-tree check is released only by the tree containing the returned tip. While held, the report lists the findings still owed and every comment concerning the launch that didn't count, with its reason. A finished `stretch` launch's findings hold the change as any builder launch's do (`LAUNCH_FINDING_STAGES`); a running one owes none yet. A change the comparison released (What a launch comparison releases) is no finding, so it owes no account.

**Why.**

- An account can run across comments because one comment has a byte ceiling and a launch's findings don't; several comments keep the marker's form, so every account posted earlier reads as before.
- A comment naming a finding its launch didn't flag counts for nothing as a whole, because it was most likely written for another launch and counting part of it would be a guess.
- The later naming governs, because a correction or a retried post is the likely repeat, and treating it as a fault would hold a released change again with only an edit or deletion as a way out; the record stays append-only. Inside one comment a repeat is a writing error, so that comment counts for nothing.
- Posting order is when a comment was created, never when it was edited, so editing an old comment can't take governance back.
- Comments only add names and the flagged set comes from the run record, so nothing posted after a release can hold the change again.
- A failed local-tree check counts as flagged even once the tree has released it, so a comment that named it while it was owed keeps counting.
- An account posted before its findings exist counts for nothing, because finding ids are predictable.
- A comment from another launch is listed on a held launch only when it names one of that launch's findings, so the holder sees a misdirected post without every other launch's accounts.
- A `names-unflagged` reason lists at most ten of the ids, with their count, because a comment written for another launch could name thousands.
- `governing` lists only findings named more than once, because listing every finding would double a flood's report.
- Any comment's text is read, an untrusted author's included, so whatever reading one payload raises makes that comment unread or malformed and never the whole report unreadable, which would refuse every next stage on one stranger's post.
- A comparison that isn't clear holds even when it lists no findings, until a counting comment for its launch exists, because a comparison the entrance can't read as clear is held rather than passed silently.
- The entrance only reads accounts and never posts one, so it checks no comment size; GitHub's limit is 262,144 UTF-8 bytes, which an account of a few thousand findings outgrows.

**Decisions in force:** D-939, a Claude launch's writes stay in its tree and an unattributed change holds until the holder accounts for it; D-988, a launch's account may run across several comments, the later naming governing a repeat; D-988 narrows D-939's single exact account to the comments that count together; D-1012, a finished stretch launch's findings hold the change as any builder launch's do, and a running one owes none yet; D-1023 narrows D-939's unattributed changes to those the comparison does not release, so a released change owes no account.

## Keeping a waiting session warm

**What it does now.** When a local Claude builder's or author's turn ends with an outcome the entrance would resume in that session, the launcher writes a spec under `~/.tradecraft/keep-warm/<session>/` and a runner (`keep_warm.py run`) is started outside every launch's process tree. About every 55 minutes after the session's last call the runner resumes the session once, with the turn's own argv changed in exactly three places (its `--settings` names the ping's settings, a fresh turn's `--session-id` becomes `--resume`, and `--no-session-persistence` is appended) and a one-line prompt. The ping's settings keep the turn's `enabledPlugins` and add one `PreToolUse` hook that refuses every tool. It runs under the turn's own environment: the runner holds the starting process's environment in memory, and the spec holds only the launch's own changes to it. Each ping's usage is read from its stream and appended to the change's `keep-warm.jsonl`, beside the holder's usage. Keep-warm for a session ends at the cap (eight hours after the turn, at most eight pings), when the next launch for that work, stage group and instalment starts its process, at that instalment's release, when the issue or pull request closes or merges, or after any ping that did not only read. The machine setting `~/.tradecraft/keep-warm.json` (`{"cap_hours": N}`, 0 off, at most 24) is read at start and before each ping, and the smaller cap holds.

**Why.**

- A one-hour cache entry that lapses makes the next turn write its whole conversation again; a resume that saves nothing reads the conversation and refreshes the entry for about a fortieth of that.
- A ping refuses tools with a hook, not a flag, because `--disallowedTools`, `--allowedTools` and `--tools` change the tool list the model is sent, so the ping would write its conversation again; a hook runs in the client.
- The runner starts outside every job and subreaper the launch runs in, or the launch's own cleanup would kill it. On Windows it is created through WMI's `Win32_Process.Create`, which no caller's kill-on-close job holds (a breakaway is refused), with the environment passed on PowerShell's stdin and `pythonw.exe` and `CREATE_NO_WINDOW` so no window opens. On Linux and macOS it is a double fork from the entrance after its own cleanup, so the runner lands inside the baseline of any later `Descendants`. The entrance starts it (`--keep-warm-starter entrance` and `start_pending`) because the launcher it runs is itself inside the entrance's containment; a launcher run directly starts it as its last act.
- Credentials never reach a file or command line: the ping runs under the account whose cache it reads, so the runner inherits the starter's whole environment in memory, and the spec records only variables the launch itself set or removed. Any other difference refuses the keep-warm. The GitHub write bound's connector switch and child settings are among the launch's own, because they shape the session a ping resumes; its removal of git's push credential is neither recorded nor refused, because it guards only commands and a ping refuses every tool.
- The stop comes when the next launch for that work and stage group starts its process (or hands itself to the cloud route), never at the stage call, because the wait between a stage call and its launch can outlast the hour, and a replacing Codex, cloud or fresh launch must still end the old session's keep-warm. A launch that ends before starting anything (refused at the entrance's cap, no executable, a failed preparation, a refused output) leaves the waiting session the one the entrance resumes next, so its keep-warm is left as it was. A resume waits on the session's `ping.lock` for a ping in flight before its recipient's window opens, and only until its spawn can still fall by the cap's end, because every recipient gets its whole limit; so no ping falls inside a turn, and the wait is the launcher's time under the cap.
- A change built in instalments keeps each instalment's sessions apart, because sibling instalments have separate builder histories and one's launch or release says nothing about another's next turn: a launch, a release and the registry's released state reach only the sessions of the instalment they name, and one that names none reaches the whole change. Closing or merging the issue or pull request still ends every session's keep-warm.
- The first ping, and the lapse guard, are timed from when the session's last call was sent, not when its output ended, because the cache entry's hour runs from the send and a final call can stream for minutes; the transcript entry that call answered is written just before it is sent.
- The cap defaults to eight hours because, counting every session nobody returned to as pinged for the whole cap, that is where a waiting session's saving was largest; the setting accepts at most a day, because a session nobody resumed within a day is not coming back.
- A ping that never reached the model spent nothing and is recorded as a known zero; a ping whose usage could not be read whole is priced unknown, so the cost report never prices a part as the whole.
- Guards run in this order before each ping: cap, lapsed (no ping once the last call is older than 57 minutes, since a ping on a lapsed cache pays the whole reload), root removed, outside use (the transcript grew), too large (a resume near the window would compact), change state (an unreadable read is retried once a minute later, then ends keep-warm), and a turn running. A ping whose first call read nothing, or wrote more than the larger of 20,000 tokens and 5% of its read, compacted or failed, is the last until a real turn, so the worst a session's keep-warm can cost is one wasted reload.
- An accepted author's copy is disposed, and its next turn runs in a new copy; a resume from another directory still reads its cache, so the ping runs from the holder checkout the next copy comes from. Every launch's own instruction file (its helper rule, and an import of `AGENTS.md` where the tree has no `CLAUDE.md`) is re-created whole for the ping alone, so the ping is sent what its turns were; where the file can't go back to its own directory, only its import line changes, to an absolute import from the ping's directory.
- A ping is never a launch: nothing it writes is under the dispatch store or named `*.request.json` or `*.run.json`, so liveness, resume selection and the launch comparison never see it, and the runner, hook and starter run with `-B` so no bytecode lands in a compared plugin tree. The setting is a covered comparison item, as the cloud switch is. A dead runner is recorded `runner-gone` by the next launch for its work or by `status`.
- The change's cost report carries keep-warm as its own line, each ping priced once on the rate card and read only after every dispatch's share is fixed, because the session's own running total leaves pings out and nothing else would count them. Beside it, the reload list names each resumed local Claude turn whose first call still wrote more than it read, with its idle time, first-call tokens and the pings sent in that gap, because that list is how the owner judges whether keep-warm works and whether its cap is right. Cloud attempts are left out of the list, since their calls are not logged on this machine.
- A stretch builder's three variables (`STRETCH_ENV_NAMES`) are neither carried into a ping nor a foreign change. They name the builder's own launch to its own session's processes, a ping starts no process that reads them, and the launch sets them itself, so listing them as foreign would refuse every stretch's keep-warm.

How a ping is priced, including one on a model with no price or one priced per request by prompt length, is in [Pricing a run](#pricing-a-run).

**Decisions in force:** D-1012, a stretch builder's variables travel to its own session only; D-993, a waiting local Claude builder or author is kept warm by an outside resume that saves nothing, capped at eight hours and one wasted reload, recorded on the change's cost records and never as a launch; D-1003, a resume's wait for a ping in flight comes before the recipient's window and within the cap, so the recipient keeps its whole limit; D-999, a ping on a model with no price is a named floor and a tiered model's ping is priced call by call; D-986, dispatched sessions make only their step's GitHub writes, whose launch variables a ping carries or leaves out as above.

## Consumer trees

**What it does now.** `work.py tree` builds a use consumer's tree from committed bytes: a new repository with one neutral detached commit, no remote and no shared history, holding only the declared job paths and loading surfaces, each file proved against its committed blob. Its record of the tree names the change, the source checkout and revision, what was excluded and every carried file, under a digest. `tree` writes that record whole to the entrance's own records, under `trees/`, in a file named by a digest of the tree's resolved path, prints the path as `tree_metadata`, and leaves nothing but the tree in the folder the tree sits in. `run use` takes that path, proves the record's integrity, re-proves the source revision, the neutral repository and the tree's bytes, and launches the consumer with the tree as its root. The cold reader's reading tree is recorded the same way.

Before anything is built or launched:

- `tree` refuses an output that exists, one inside the source, one inside the entrance's records, and one whose folder holds those records at any depth;
- `tree` refuses an output whose folder holds an entrance tree record file, `<tree>.tradecraft-tree.json` for this tree or any other, naming that file and saying to remove it;
- `tree` refuses an output whose own name, or the name of the folder it sits in, carries the change's issue number or an open pull request's number as a whole run of digits, checking the issue number first, without the network; a merged pull request's number is not checked, folders higher up are not examined, and when the issue, its comments or its pull requests can't be read, `tree` refuses;
- `run use` refuses a tree whose folder holds such a record file, naming the file and saying to remove it and rebuild the tree it records, without opening it; any other file beside a tree, such as a job fixture or a second tree, is lawful;
- `run use` refuses a record that isn't at the path derived from the tree it names, one whose digest doesn't match, and every mismatch of source, revision, bytes or repository shape.

A builder in a stretch launch's tree is refused `tree` with or without options: the tree a builder's check reads is declared by the settled artifact (see A builder's own checks and writes).

`tree` replaces a record left at its path by a tree since deleted, so a deleted tree can be rebuilt where it was; a reading's record is never replaced.

**Why.**

- The tree's folder is the consumer's working space: a consumer lists it and works in it, so a record there would tell it which change it is judging, where the holder's checkout is, and what was withheld.
- The record's name is derived from the tree's resolved path, compared as the platform compares paths, so a record still proves which tree it belongs to without sitting next to it, and one copied to another tree's path is refused.
- Only the entrance's own records beside a tree are refused, because a tree built before the record moved, or one with its record put back, keeps the exposure, while side-by-side trees and job fixtures are layouts a job needs. A sibling tree's record counts too: it names its change as plainly to a consumer listing the folder.
- `tree` refuses a path with the record file beside it, because a tree built there would meet `run use`'s refusal again; removing the file is the holder's, since the entrance never opens it to tell whose it is.
- Only an open pull request's number is checked, because an open pull request is the change under test, while a merged one belongs to work already landed, such as an earlier instalment.
- Only the tree's folder and the folder it sits in are checked for the change's numbers, because those two names appear in every command the consumer runs and are the ones a holder chooses; folders higher up are usually named by the runtime, and the random digits of a session id would refuse holders by chance.
- An unreadable pull-request lookup refuses, because a check that can't be decided would otherwise pass the path it exists to stop.
- The entrance's records may not sit in or below the tree's folder, so that nothing but the tree is there for every tree, including one built in the home folder.
- A stale record is replaced because a holder who deletes a tree can't see its record to delete it too, and a record proves nothing without its tree.
- Every record is written to a temporary file and then moved into place, so a partial record never stands.
- This keeps the record out of the consumer's folder only. A consumer whose shell reaches the rest of the machine can still find the entrance's records, which is a separate exposure.

**Decisions in force:** D-726, the entrance is the holder's instrument, which builds neutral, mode-declared, history-free consumer trees; D-736, a landed commit is a lawful consumer-tree source; D-968, a consumer tree keeps its record elsewhere; D-1012, a builder's check tree is declared by the settled artifact and built in the run.

## The GitHub write bound

**What it does now.** A dispatched session that can write (the artifact author, the builder, the use consumer) makes only the GitHub writes its own step needs, and returns any other as a request in a **Write requests** section; a session one of them starts makes none. `github_allowance.py` works out the allowance, the sentence a session is told, the launch preparation and grants; `github_write_guard.py` is the command check.

A `stretch` builder records such a write in its readiness record's `decisions` instead, because nothing returns to the holder before its ready report (A builder's own checks and writes).

- **The allowance comes from the stage.** `build` and `floor` may push the registered branch. A `stretch` builder may write to its own change's branch, pull request and issue, as A builder's own checks and writes sets out, with direct launcher calls, hand-written check reports and comment edits refused. `review-disposition` may also reply on and resolve its own pull request's threads and answer a body finding there. Every other stage, the use consumer and any started child may make none. A pushing stage launched with no registered branch, as a direct launcher call may be, also gets none: there is no ref to hold its push to, and its sentence says so before it acts. Reads (`gh api --method GET`, GraphQL queries, fetches) stay open to every step.
- **Instructions and a launch block together.** Every bounded launch is told the allowance sentence exactly once: a composed prompt carries it, the launcher's notice adds it to a dispatch that lacks it, and a dispatch stating another allowance is refused, as an unlaunched attempt in its run record. A cloud launch appends its route's sentence the same way and refuses a dispatch stating another before anything fires. The launch turns claude.ai connectors off with `ENABLE_CLAUDEAI_MCP_SERVERS=false`, names its child settings in `TRADECRAFT_CHILD_SETTINGS`, and, where the allowance permits no push, clears git's credential helpers and ssh agent.
- **Each launch proves its check before it starts.** Preparation runs a self-test: the check must allow and refuse a fixed set of commands, and one refusal (and, for the use consumer, one pass-through) runs through the entry the launch installs: the hook's command string, split as a shell splits it, or the use consumer's written wrapper file. A failed self-test refuses the launch; nothing starts. The use consumer's seat prepares its bound after its request write, so its last check against the entrance's cap leaves the self-test's processes their time before the cap's end.
- **The check runs on every shell command** it can see: `env` and a pass-through program such as `nice` or `timeout` are looked through, `env -S`'s string judged as the command it runs, its option values skipped, and a word left where its program should be is refused when the rest of the command carries a write or session-start signature. Behind a git global option the check does not read, either of the next two words may be the subcommand, so a push route or a stored alias there is refused, and a variable in program position assigned earlier on the same command line is judged as the program it names. Behind any other program but one that never runs a later word of the command as a command (`grep`, `echo`, `python` and the like), a judged program standing as its own word is judged as the command it starts, so `setsid`, `sudo` or a wrapper nobody listed carries no write past it. Text the check cannot parse (an unbalanced quote, an unterminated here-document) is refused, naming the cause. A run of shell punctuation is read as the separators it holds, `<( )` and `>( )` are judged as the commands they run, a here-string's data is its next word only, a number starting its word is a stream only when joined to the redirection after it, a `#` starting a word comments to the end of its line, and the substitutions of a here-document with an unquoted delimiter are judged, since bash runs them. Where the check cannot establish what a command runs or sends, it refuses, naming the cause: a program other than a reader behind `xargs`, which adds words the check never sees; a shell or any program it looks through under `env -i`, which clears the variables carrying the check into a session it may start; a PowerShell invocation in any form but the exact `-Command` and `-File` spellings and documented aliases it reads (an encoded, abbreviated or Windows PowerShell positional command); a git subcommand it does not build in under a redirecting option or variable, since the alias lookup reads the tree's own configuration; and a `curl`, `wget` or web-cmdlet request to a GitHub API host carrying any option or parameter the check does not read as part of a GET with no body. `GH_REPO`, set in the command or the session, chooses the repository a `gh` write is judged against, as `-R` does. A push is refused when `push.followTags` is stored (unless `--no-follow-tags`), when it carries `--recurse-submodules` with any value but `no`, or when `push.recurseSubmodules` or `submodule.recurse` is stored (unless `--recurse-submodules=no`), which pushes submodule commits to their own remotes, and a push to a URL that a stored `insteadOf` or `pushInsteadOf` rewrites is refused, because each sends more, or elsewhere, than the command names. A shell given no `-c` and no script runs what is piped into it, so text piped from earlier in the same command line is judged by its signatures; a script file read from stdin, as with `bash < script.sh`, stays out of reach like any script. Of git's routes to a remote it reads `git push` and `git-push`, a stored alias (judged as what it expands to, and refused when it runs a shell or cannot be read), and refuses `send-pack`, `http-push` and `subtree push`, which a step's own push never uses, and, even with no push beside it, `git config` writing an alias or a setting a push reads (a remote's push, URL or mirror, `remote.pushdefault`, `push.default`, a branch's remote or push remote, a URL rewrite) and `git remote set-url` or `rename`, because such a setting changes what every later push writes, in a later command, step or started session too, and a step's own work never changes one; a push made by any other program stays out of reach.
- **Where the check rides.** A Claude implementer carries it as a `PreToolUse` hook on `Bash|PowerShell`; the use consumer carries it through `CLAUDE_CODE_SHELL_PREFIX`. A refusal fails the command, not the turn, and lands in the run record's `github_write_refusals`; the run record's `github_write_bound` states the allowance and whether the check ran.
- **A child starts only under the launch's settings**: `claude --setting-sources user --strict-mcp-config --settings "$TRADECRAFT_CHILD_SETTINGS"`, without `--safe-mode`, `--bare`, `--mcp-config` or a connector change. Any other Claude start, and every Codex start, is refused. A command that starts no session (`claude --version`, `--help`, `mcp list` and `mcp get`; `codex --version`, `--help` and `execpolicy check`) passes, because nothing it runs inherits the login.
- **Codex** gets the instructions, the environment removal and the child settings, and its run record says no command check ran; the hook a Claude child of it would carry is self-tested like any Claude launch's. **A cloud run** records that the launch block did not run; its prompt's sentence, its only bound, follows its stage: a build or repair may push the change branch and its report branch, and an artifact author only its report branch, which carries its return.
- **A grant rides only a resumed, local turn**: it answers a request the step itself returned, so only that step's next turn can carry it. The launcher refuses a granted turn on the cloud route, and one that resumes no session, before it launches; the entrance checks continuity first, but an explicit restart can turn its decision fresh after that check.
- **A grant rests on the affirmed brief.** `work.py run <stage> --grant <comment id>` accepts a `write-grant` marker only from a configured marker producer (`validated_grants`), and `validate_grant` accepts it only for a resumed turn of its own stage, quoting at least `MIN_QUOTE_WORDS` whole words of the cited row of the affirmed brief, with a target in the work's own repository; a push grant allows exactly its ref, never `--tags` or another ref-wide push, and keeps git's credential for that turn, and the composed prompt and the launcher both name the grant.
- **A holder-written dispatch prints its sentence** with `work.py allowance <stage> [--implementation-root TREE] [--pull-request N] [--grant <comment id>]` (`use` for the use consumer, which takes no `--grant` because a grant reaches only a resumed turn of its own stage and the use consumer is a fresh session every time; `--cloud` for a launch the cloud route takes), which takes a pushing stage's branch from the registered implementation tree and the pull request from the issue, as the launcher does, refusing a tree or pull request other than those, and validates each grant as `run --grant` does so the sentence names the grants the launch will hold.
- **Refusals and grants are reported.** Every entrance report carries `github_write_bound` (the refusals and grants of the change's launches of every stage, or `unknown` with the error that stopped the read, including a launch that prepared a refusal log its launcher never read back: one whose launcher died, or one still running, has not yet shown what was refused, and listing no refusals for it would read as none); a refusal the log cannot take still refuses, and its message says it reached no record. `run release-report` reports through the same entrance report, so its `github_write_bound` is the list of grants and refusals the release report names.
- **Which use consumers carry it.** A Claude use consumer given a shell carries the shell-prefix check and the environment. A Claude use consumer without a shell has no tool that runs a command, and a Codex use consumer runs in Codex's read-only sandbox (`--sandbox read-only`, no network access granted), so neither carries the check.

**Why.**

- A dispatched session holds the owner's full GitHub login, and a session it starts inherits that login and the claude.ai connectors, so without a stated allowance any of them can write to a product repository before the owner authorized it. The allowance is the writes the composed prompts already ask for, so a step working as designed loses nothing.
- Instructions alone never reach a session the builder starts; only the launch environment and settings do, so both are used.
- Connectors are off because a connector is a write path the shell check never sees, and every child inherits the environment that turns them off. A child carries `--strict-mcp-config` for the same reason: without it, it loads the owner's MCP servers.
- A `git push` carrying `-c`, `--config-env`, `--git-dir`, `--work-tree` or `--namespace`, or an assignment of `GIT_DIR`, `GIT_WORK_TREE`, `GIT_NAMESPACE` or any `GIT_CONFIG*` variable, is refused rather than judged, because each can change where or what the push writes and a step's own push never needs one. A push naming no refspec is judged as `@{push}` only when no `remote.<name>.push`, `remote.<name>.mirror` or `push.default=matching` widens it.
- The `gh` login stays because every step's reads need it; the command check, not the missing login, is what refuses a `gh` write.
- The use consumer keeps `--safe-mode`, which skips settings hooks, because dropping it would change what the consumer loads; the shell prefix still runs under it.
- A child loads only user setting sources because the product tree's project or local settings could set `disableAllHooks` or an `env` block and turn its check off.
- An implementer's child carries its parent's plugin exclusions, while a use consumer's or a Codex launch's child keeps the owner's plugins: neither parent has a plugin list to hand down (the use consumer runs `--safe-mode`, Codex runs no Claude plugin discovery), and a child's GitHub bound rests on its settings' hook, its environment and `--strict-mcp-config`, not on which plugins it loads.
- The check is a tripwire on an unfenced shell, not a fence: a write from inside a script, persist-changes' own push included, is not seen, and nothing checks GitHub after a run. The run record is what makes every refusal it does see visible.
- A cloud turn cannot carry a grant because its routine's text is fixed and allows no write beyond the change and report branches; a grant it named would be a write the run is told not to make.
- A push grant names one ref, so a ref-wide push would carry refs no row named.
- A grant must rest on a brief row, not the holder's judgment that a write is reversible, because in a product repository a pushed branch can start workflows or a deploy that deleting it doesn't undo.
- The installed Codex loads command rules only from user or project `.rules` files and `requirements.toml`, so no source can be supplied for one launch without writing into the product tree, the owner's Codex home or the machine's policy.
- The self-test runs through the installed entry, the hook command or the written wrapper, because that is what the session will run; a check proved only in-process could still be missing from, or broken in, what the launch carries.
- A refusal is reported, not held: it fails the command and the turn goes on, because the check exists to make a write that didn't happen visible, not to stop work the step can finish another way.
- The allowance command takes the branch and pull request the launcher will, so the sentence it prints is the one the launch will hold; a sentence for any other allowance would be refused at launch, and so would one carrying the cloud sentence instead.
- A grant writes only to the work's own repository, because it answers a write the change's own step needs; nothing in the affirmed work provides for a grant to write anywhere else.
- A use consumer with no shell, or in Codex's read-only sandbox, carries no check because it has no route to run a GitHub write; the shell-prefix check exists for the one that does.

**Decisions in force:** D-986, dispatched sessions make only their step's GitHub writes; D-1012, a stretch builder's allowance and its tripwires; D-1013, where a stretch builder's uncovered write goes.

## A builder's own checks and writes

**What it does now.** A `stretch` launch (`dispatch_implementer.py --stage stretch`) is one Claude builder that carries a change from handoff to ready. `run handoff` composes its dispatch, unless the holder writes it with `--dispatch`, which is recorded `holder_written`. The launch requires `--holder-session-id`, `--lineage-branch` and `--work owner/name#n`. It refuses a Codex vendor, because a Codex builder is started by hand, and a repository the cloud route would take, because cloud builds keep the relay route. It refuses a `--lineage-branch` its root hasn't checked out, and, where the root has an active registration, a `--work` or branch that isn't that registration's, so its allowance never names another change; a root with no registration launches as it is, because it has no registration to disagree with, and launching one is how the stage is tried on a throwaway repository. Every refusal comes before any bundle exists. Its time limit is its own (`DEFAULT_STRETCH_TIMEOUT_SECONDS`), not cut to the build lineage's remaining budget.

- **Its writes.** The stretch allowance (`github_allowance.allowance_for("stretch", …)`) holds the repository, the branch, the issue from the work's `#n` and the lineage pull request. Its sentence names a push to the branch; opening a pull request from it, marking it ready and editing its title and body; a conversation comment and replying on and resolving review threads on that pull request; and a comment on the issue. The sentence then says how to write a thread reply's id and that checks launch only through the entrance, and ends by recording a write it doesn't cover in the readiness record's `decisions`; a hand-started builder's copy carries no Claude-session line, because it has no child settings to start one under. The command check (`github_write_guard.py`) allows exactly these:
  - `gh pr create` from the own branch, with only `--fill`, `--title`, `--body`, `--body-file`, `--base`, `--draft`, `--head` and `--repo`;
  - `gh pr ready` (and `--undo`, which turns its own pull request back into a draft), `gh pr comment`, and `gh pr edit` with only title and body options, on the own pull request;
  - `gh issue comment` and `POST …/issues/I/comments` on the own issue;
  - comments and thread replies on the own pull request, in `review-disposition`'s three forms.

  A pull request is the builder's own only when a live read (`pull_owner`) finds its head is the builder's branch in the allowed repository, the number its launch was given included; an unreadable read refuses.
- **What the check refuses besides.** For a stretch allowance only, before the inert-program shortcut, it refuses:
  - a command whose program, or whose Python interpreter's (`python`, `py`, a versioned name such as `python3.12`, or the windowless `pythonw` or `pyw`) or `uv run`'s script or module, is `dispatch_seat.py`, `dispatch_implementer.py` or `dispatch_record.py`. A command naming one only as data, such as `git add`, passes. After `uv run`'s own options the command it runs is judged as any other is; the check can't tell which of uv's options take a value, so a word after an option is read both as its value and as the program, and either reading that calls a launcher refuses; a first word with no option before it is the program. A `python -c` text is refused when it names a launcher anywhere, because a line of code can't be told data from a call. Python's options are read as Python reads them, so a joined or clustered `-m`, `-c`, `-X` or `-W` takes the rest of its word or the next word; a module runner (cProfile, profile, pdb, trace, runpy, coverage) given a launcher is a launcher call; and uv's own options before `run` are skipped to find what `uv run` starts. A Python option that takes a value (`-X`, `-W`, `-Q`, `--check-hash-based-pycs`) has its value skipped; any other option is read as taking none, so `python -u lint.py lib/dispatch_seat.py` passes;
  - a comment or reply whose body, body file or fed text carries `tradecraft:check-report` or `tradecraft:send-back`;
  - every edit or deletion of a comment.
- **A refusal leaves the run standing.** `_claude_result(…, refusals_stand=True)` lets a reported permission denial pass, and the file guard's denies no longer fail the turn. A completed call with no guard decision still fails it, and so does every other test. The run record's `refusals` has one entry per refused call, in the order the calls stand in the run's stream, naming every source that reported it in `sources` (`github-write-bound`, `file-write-guard`, `permission-denial`): a call a bound refuses is also reported by Claude as a denial, and the two reports are one entry. A call is placed by its tool-use id, or by its command or path, read with either slash and in any case, because the file guard logs the resolved path and the call carries it as written; a call takes one report from each source, so one command refused twice is two entries; reports carrying a tool-use id are placed first; one placed by its text goes to a call whose input is that text before one that only contains it, so `a.py` never lands on `a.py.bak`, and among those to a call Claude denied that its source hasn't reported, so an earlier allowed call naming the same path never takes it; calls that tie and differ leave it unplaced rather than merge two refusals; `refusals_unknown` says a refusal log could not be read. Each entry carries `at`, the earliest time any of its sources logged; Claude's denial carries none, so an entry it alone reports has `at` null. `launch_bound` and `tree_write_guard` log `at` with each refusal, so a reader of the release report can set a launch's logged refusals in order beside those its readiness record names. Every other stage, every seat (`dispatch_seat.interpret`) and every Codex path still fails on a refusal.
- **Its tree.** The launch exports `TRADECRAFT_STRETCH_DISPATCH` and `TRADECRAFT_STRETCH_WORK` to its recipient. Before its comparison's first snapshot it writes a pointer under the store's `stretch-launches/` naming the bundle, the work, the reserved session, the launcher's identity and the implementation root. The comparison covers the pointer as `own-pointer`, so a pointer removed or rewritten during the launch is a finding. A pointer outlives its launch and reads as not live once its run record completes. On Windows the launch worker (`seat_process._worker`) names its kill-on-close job `Local\tradecraft-stretch-<dispatch id>` (`launch_tree.job_name`) from `TRADECRAFT_STRETCH_JOB`, refuses a name that already exists, and drops the variable before the recipient starts. The job's name travels in a variable of its own, not in `TRADECRAFT_STRETCH_DISPATCH`, because a seat launched with the stretch's variables still set would otherwise name its own worker's job after the stretch's, find the name taken and fail to start. No keep-warm ping carries any of the three (`keep_warm.STRETCH_ENV_NAMES`). `launch_tree.stretch_holding` reads only those pointers, keeps the launches whose run isn't complete and whose launcher or recipient lives, and asks whether the current process is inside one:
  - on Windows, by opening the named job and calling `IsProcessInJob`, which counts nested jobs;
  - on Linux, by walking `/proc` parents to the recipient or launcher, each matched with its start time;
  - on other POSIX systems, the same walk through `ps`.

  It answers one holding launch, `none`, or `unknown` where a check errored. A missing job is `none`.
- **Builder mode.** `work.py run` checks first, before any other read or write:
  1. **Identity.** A holding launch makes the run a builder's, whatever the variable says. The run is refused `builder-identity-unproved` when the variable is set but no launch holds it, when the holding launch isn't the one it names or is for other work, or when a present `CLAUDE_CODE_SESSION_ID` isn't the launch's session. A hand-started record has no session of its own, so under one a present session is accepted and recorded as declared, and refused only where it is the holder session its handoff names, because the holder can't be its own builder. `unknown` refuses `launch-tree-unknown` only with the variable set. With it unset the run is the holder's, and its first output names the bundle whose check failed.
  2. **The stage table.** A builder runs only `cold-reader`, `use`, `acceptance-criterion`, `proof`, `ready-reviewers` and `catch-up`, the read-only decision, and `allowance` without a grant. Everything else, `tree` with or without options and any grant included, is refused `stage-not-the-builders`.
  3. **The root.** `--root` must be the holder checkout the registry names for the launch's implementation root, or the run is refused `builder-root-mismatch`. This check alone reads the registry, and only reads it; identity and the stage table read no registry and no GitHub.

  | A builder may run | A builder is refused |
  |---|---|
  | `run cold-reader`, `run use --job-from-artifact`, `run acceptance-criterion --criterion ID` or, on the mechanical lane, `--row N`, `run proof`, `run ready-reviewers`, `run catch-up`, the read-only decision, `allowance` without a grant | `run artifact`, `cold-seat`, `build`, `floor`, `review-disposition`, `release-report`; `tree`; `release` and `adopt`, which write the holder's registration; any grant |


  The run then removes the stretch variables from its own environment, so nothing it starts names the launch.
- **Who launched a seat.** `dispatch_seat.py` and `dispatch_record.py begin` call `launch_tree.attribution` before any bundle exists. Inside a holding launch's tree a present `CLAUDE_CODE_SESSION_ID` that is not the launch's session is refused `builder-identity-unproved`, as the entrance refuses it, except under a hand-started record, where it is recorded as declared unless it is the handoff's holder session; otherwise the request records `launched_by` (role, dispatch, session, and `identity` `proved` for the launch's session or `declared` when no session variable is present) and `dispatch_origin`, which is `entrance` only when the entrance's flags say so and proves nothing. A flag that disagrees with the holding launch is ignored and recorded in `launched_by_ignored`. Outside every tree the record carries neither field, and the entrance's flags are refused there. Where the tree check can't be made, the entrance's flags are refused `launch-tree-unknown`, as the variable is, because the check they claim would otherwise read as the holder's; with neither, the seat is the holder's as before. `dispatch_implementer.py` refuses `a builder launches no implementer` inside a tree, or with the variable set.
- **A check's instructions and inputs.** In builder mode, `run use` and `run acceptance-criterion` refuse a `--dispatch` (`builder-may-not-write-a-check's-instructions`) and a `--tree-metadata` (`stage-composes-its-own-tree`). The settled artifact supplies what they read:
  - the use job, the fenced block under its one `Use session job` heading (`artifact_use_job`);
  - each criterion, from its `**ID.**` opening to the next opening or heading (`artifact_criterion`), with its `Fresh reader:` line (`criterion_reader`);
  - each consumer tree declaration, one JSON object of `create_consumer_tree`'s caller parameters under `Consumer tree declaration NAME` (`artifact_tree_declaration`).

  `compose_check_dispatch` is their one composer. `run acceptance-criterion` is open to a holder on the relay route too, because there the holder launches a criterion's fresh reader, and this stage is how it composes that reader's dispatch from the artifact; there it posts nothing, because a holder records a seat's return itself, and the entrance posts only a builder's check, which the builder may not post. A criterion whose `Fresh reader:` line names `tree` reads the change's own tree at head, built as the cold reader's reading tree is (`_change_tree`), with the same second check.
- **Its launch comparison.** The checks and writes a builder runs through the entrance leave its comparison clean: each stage runs whole in a test between the comparison's two snapshots (`comparison_window`), and the trees, tree records and origins, reading records and seat bundles they write lie outside what it covers. `proof` and `ready-reviewers`, run whole there, write nothing the comparison covers: their writes go to GitHub, where proof's comment and its gate rerun name only the change's own pull request and its current-head run. One thing holds unchanged: `catch-up` re-snapshots the builder's own root's registry row (`revision_before`, `status_before`) after the landing it made. A stretch launch's comparison credits exactly that, a row-change of its own root in those two fields alone (`own_row_resnapshot`), and nothing else; every other comparison still holds on it.
- **What the composed check takes from today's use route.** A composed `use` is held while a clean cold reading is owed, as `run use` is. A criterion check isn't, so a builder can gather its criteria's results and the reading's flags at one head and repair once; a result counts only at the head it names. Both go to catch-up first when the branch is conflicted or behind (`_synchronization_decision`), reported as the use route reports it. It prints the use consumer's staffing plan with its fallback against the builder's vendor. It writes its own report rather than a stage decision's, because it launches one composed seat and has no recommendation to report.
- **The check's tree, built in the run.** `run use --job-from-artifact` and `run acceptance-criterion` build their consumer tree from the settled artifact's declaration at the registered root's head, into `tradecraft-tree-<letters>` inside a folder of its own, `tradecraft-check-<letters>` under the system temporary folder, names with no digits, so no change number can appear in them. That folder is the reader's working space: the composed dispatch of a check that may run commands tells its reader that the tree must stay as built, to write in the folder around the tree with shell commands and use its session scratchpad for file-tool writes, since a seat's file tools reach only its tree and its scratchpad and a refused call fails a seat's launch, that Python runs with `-B`, and that a tree found changed doesn't count. An execute check that writes into its tree reads `tree=changed` by design. The tree's own record is sealed by its digest, so what declared it (the declaration's name, artifact comment and block digest) and which launch built it (`built_by`) are kept beside it, in the records' `tree-origins/`. When the seat returns, the tree is validated again; an edit, or a commit that moved the registered root, reads `tree=changed`. A reading tree gets the same second check (`cold_reader.tree_held`).
- **The report, from the seat's own frame.** A builder-mode check runs `dispatch_seat.py --return-frame`, whose last stdout output is a header line (byte count and digest of the return, digest of the dispatch it gave the seat, outcome, staffing) and the return's bytes. The entrance captures and forwards that stdout, following the launcher's window as the inherited wait does (`run_process`'s `on_window`), so the recipient keeps its whole limit, takes the return from the frame, never from the store, and posts one comment on the change's issue, `<!-- tradecraft:check-report:v1 … -->`, a blank line and the return (or `No return was retained; see the bundle.`), in up to three attempts, because a report posted later would be read from the store, which the builder can write. A post that landed but answered with an error is posted again; the two comments are byte-identical and name one bundle, so both count or neither does, and counting a bundle's findings once is for the gates that read them. A run whose post never lands reports `check-report-unposted` and exits nonzero. GitHub refuses a comment over 262,144 bytes of UTF-8, so a report that would pass it isn't retried: the marker is posted with one line giving the return's size, the run reports `check-report-oversized` and exits nonzero, and the report doesn't count. The composed dispatch bounds the return at 240,000 UTF-8 bytes, as the artifact stage's does. `run cold-reader` frames and posts the same way in builder mode, once its reading passes the form check, so a reading refused for its form is never posted, and reads the account it checks from the frame.
- **What counts.** Every entrance report that finds a builder's check bundle or a posted report carries `builder_checks`. `check_dispatches` says, for each check bundle carrying `launched_by`, whether its `.dispatch.bin` equals the dispatch recomposed from the current settled artifact and its tree record (`use` and criteria), or from its sealed reading record, the entrance's standard and a diff regenerated from the source (`cold-reader`, whose record must name the bundle's tree, and whose covered paths must lie in the change set at its base and head): `composed` or `differs`. The diff kept beside the record is never read for this, because it sits in the store, which a builder's shell can write. `check_reports` says whether each posted report counts: its digest is the recomposed dispatch's, its bundle is a stretch builder's of this work, its stage, head, staffing and outcome are the bundle's, its tree held, the store's return equals the posted text (`store-and-posted-differ` otherwise), and its author is a configured marker producer. The builder route's use gate counts these reports, and its final pass reads the reconciliation built from them. An accounting that fails puts its error under `builder_checks` as `unknown`, so it never reads as a change with no builder checks.
- **The holds and inputs a composed check shares with a named stage.** Before it builds a tree or launches a seat, a composed check passes the launch-account hold and its stage's version requirement, and refuses a settlement whose validation failed (`artifact-source-unusable`) rather than reading the earlier settled text. A builder's check runs only on its own launch's registered root, whose instalment the run takes; a `--instalment` naming another registration is refused `builder-root-mismatch`. Its producer's vendor is the holding launch's, read from that launch's request record, because a first stretch launch has no completed bundle; a builder's `run cold-reader` takes its comparison vendor the same way, so it runs before any `builder-session` marker exists. Under a hand-started record that vendor is the one the record declares, as written, whatever its name (`_holding_launch_vendor`). The seat's own vendor and model stay the entrance's; its staffing compares them with the declared vendor ignoring case, so the same vendor is `degraded` with `--same-vendor-reason declared-builder-vendor` and any other is cross-vendor, and its request record carries `builder_vendor_source: declared` and its posted report `builder_vendor=declared`. A launched builder's seats keep `owner-selected-claude-implementer`, because its vendor is observed. Every refusal a composed check can make, the vendor's included, comes before its tree is built, so a refused check leaves no tree or origin behind. A heading, criterion opening or `Fresh reader:` line inside a fenced block is an example, not the plan's own, so `criterion_reader` searches a criterion with its fenced lines removed, as `fresh_reader_criteria` does. A use or criterion tree built from an earlier declaration of its name than the current settled artifact's reads `differs`. A posted report's same-vendor reason must be its bundle's, and absent where the bundle has none.
- **The frame and the wait.** The return frame is the first whose byte count reaches the end of the launcher's output, so a return holding a frame of its own is read as return bytes. The entrance forwards the launcher's stdout as it captures it, though the inherited wait avoids a forwarding layer: the frame can only be read from a captured stream, and what it forwards to is the builder's own tool pipe, whose timeout bounds a stalled reader. A captured launch reads its window at the 0.25-second cadence and again whenever its deadline is reached, before the old deadline stops it.
- **A reading tree's second check and its diff.** When a builder's reader returns, its reading tree holds only if its status is clean, its commit's tracked files are exactly the reading's claimed files with their modes and object ids, and each file's bytes still hash to its claimed object. A reading's diff is generated with Git's default context set explicitly (`--unified=3 --inter-hunk-context=0`), so it is the same under any Git configuration.
- **Its launch comparison's own items.** A stretch launch's own pointer is held as its request record is: a removed or rewritten pointer is a finding wherever its path lies, never credited to the launch's own root or to an overlapping run. The own-row credit is given only when the own root's row differs in `revision_before` and `status_before` alone, a field added or dropped counting as a difference, and every other registry row is unchanged, compared as The launch comparison's crediting and allowance sets out. A completed stretch launch's findings hold the change as any writing launch's do (`LAUNCH_FINDING_STAGES`); a running one owes none.
- **What its notice says.** A stretch launch's write-bound notice and instruction file say that a refused call is recorded and the turn goes on, and that a file-tool call that completed with no guard decision still fails it; every other launch's text is unchanged.
- **What the write check reads of a builder's comment and pull request.** A comment body is judged as GitHub will receive it: an `--input` request body is JSON-decoded, with `\u` escapes undone, before the report-marker scan; a body file or redirected stdin the check can't read as a regular file is refused; and a body written on the command line holding `$` or a command substitution, a piped-in body, or an unquoted here-document holding `$` or a backtick is refused with a pointer to `--body-file`. Quotes are gone before the check sees a word, so a single-quoted `$` is refused too. The `in_reply_to` reply form passes only with a literal positive decimal id. A pull request named by number is the builder's own only when a live read finds it headed by the builder's branch in the allowed repository, the number its launch was given included; one named by no number is the builder's only where the current branch is its own, Git's configuration has gh look it up as that branch, and a live read finds exactly one open pull request headed by it; otherwise the command is refused and asked to name the number. `issue_of` reads an issue only from a positive ASCII decimal suffix. A GraphQL query given as `@file` is read as a body file is and scanned the same way, and a comment carrying `tradecraft:send-back` is refused as one carrying `tradecraft:check-report` is.
- **Its sentence for a holder-written dispatch.** `work.py allowance stretch --implementation-root TREE`, or with no tree named, which takes the change's registration so a holder's shell need not name the tree its guard protects, prints the sentence the handoff carried: recomposed from the stretch request's `handoff` block, or a hand-started record's, with no pull request and the record's `hand`, because the builder received it before its pull request existed. Before any handoff, or where the record can't give it, it prints the sentence computed now, with the registered branch, the issue's pull request and the issue, and says so. It takes no grant and no `--cloud`, and the entrance runs no `stretch` stage. The sentence also tells the builder to write a body file's path out in the command, never as a variable, and to create the file in an earlier command of its own, because the command check reads only a literal path to a file that exists.

**Why.**

- The builder's step is now the whole run to ready, so its allowance grows to its own change's branch, pull request and issue, and no further. Labels stay refused at creation and in edits, because the reviewer label belongs to `ready-reviewers`.
- A builder that carries the whole run will meet refusals, and failing its launch on one would throw away its ready report. A seat keeps the old rule, because a seat refused its commands that still reported success would pass a check it never ran.
- A builder can clear a variable but cannot leave the tree its launcher holds, so the tree decides whose a process is. Today's route gains no refusal from a check that couldn't be made, because nothing on it is a stretch launch.
- A check is independent only while the party it checks can't aim it or edit it. So the builder never writes a check's instructions or chooses what it reads, and a report it could post by hand would stand in for the entrance's.
- The report is posted from the frame inside the run that launched the seat, because a post made later would read the return from the store, which the builder can write; comparing the store with the posted copy afterwards then shows an edit instead of letting it stand in for the report.
- The tree check reads a pointer directory rather than every request record, because every entrance run and seat launch makes it, and reading thousands of bundles would slow the relay route; the comparison's `own-pointer` item keeps the pointer as hard to remove unseen as the request record.
- Everything here is a tripwire and a record, not a fence. The builder's shell runs as the same user as the entrance, the launchers and the store, so a script can do what the command check never sees:
  - call a launcher, or write a bundle and a comment;
  - remove or rewrite its stretch pointer, which its launch comparison then reports, or point a run at another home;
  - write a bundle, its kept diff and a matching comment together, or edit a check's tree and restore it before the seat returns;
  - ask a process already outside the tree to start one (Task Scheduler, WMI, `systemd-run`, `at`, a running `tmux` server);
  - on a POSIX system without a Linux subreaper, double-fork out of the tree.

  A process that leaves reads as the holder's. A judging seat's own processes are inside the tree: one whose session differs is refused, and one with no session variable reads `declared`, bounded by the seat's own sandbox and `--safe-mode`. What is left is caught by the record (`launched_by`, `refusals`, the launch comparison) and the holder reading it.

**Decisions in force:** D-1017, a row reader per brief row, and seats staffed against a hand-started builder's declared vendor; D-1012, a builder's own checks and writes; D-1013, the builder route, which launches this builder; D-986, dispatched sessions make only their step's GitHub writes, which this section widens for a stretch builder; D-987, a launched builder keeps its helpers in its tree; D-939, the launch's file-tool guard and comparison.

## The builder route

**What it does now.** The entrance reads which route a change takes and reports it, decides a builder-route change's next stage from its stretch and readiness record, and refuses a holder's named stage the builder route doesn't run. It hands the change to its builder with `run handoff`. A change on the relay route runs as it did.

- **`run handoff`.** A holder stage, refused before anything is made with `route-is-relay` (with or without `--dispatch`), `plan-unsettled` (except on the `ordinary` / `mechanical` lane, which owes no plan), `brief-absent`, `brief-rows-repeated`, `builder-live`, `handoff-spent`, `handoff-in-progress`, a limit above the default without `--budget-override-reason`, or the launch-account and version holds. It holds an exclusive lock for the work, `handoff-locks/<work-hash>.lock` in the run-record store created with `O_EXCL`, from its first check until the stretch pointer or hand record exists, and releases it on every exit, so two calls made together leave one builder; a second call while it is held is `handoff-in-progress`. The lock file names its holding, and only that holding releases it, so a call never removes another's lock; the lock carries its expiry, the end of its run's cap plus the reserve (the default cap where none is declared), since until then that run can still launch; a lock past it is stale and is taken over by renaming it away, a step only one call can take, before making a fresh one, and a call that finds it moved a lock other than the one it judged stale puts that lock back and refuses. Its limit is the stretch's own 28,800 s (`DEFAULT_STRETCH_TIMEOUT_SECONDS`), not cut to the build lineage's budget, since one launch carries the build, every check and the waits. It takes the tree as a fresh `run build` does, reusing and re-publishing a registration; a refusal after that removes what the call made (worktree, local branch, registration row, and the published branch only while its tip is the one pushed) and leaves a reused registration alone. A Claude builder starts `dispatch_implementer.py --stage stretch` detached (`detached.spawn`) with the composed text, or the holder's `--dispatch` bytes recorded `holder_written`; the request record's `handoff` block keeps the brief and artifact comments, both digests, `holder_written`, `notify`, the owed checks, the limit and override reason, the floor command, and the holder and plugin roots. The launch records as its `--settings-source` the source `_implementer_vendor` gave its vendor, the machine file or the owner's override, and takes its model and effort, with their sources, as `_launch_settings` resolves them for a relay build, so an issue's model-override reaches the builder. The stage waits within the cap for the request record and pointer, prints the window line and dispatch id, and returns; a launcher that exits first is `launcher-did-not-start`. `--by-hand VENDOR:MODEL`, or a machine vendor of `codex`, starts no process: it writes a hand-started record and prints the text to paste. `--preview` makes nothing, no tree, bundle, lock, cap record or write, closes no hand record, takes no `--dispatch`, `--resume-reason` or `--ended-reason`, and prints the composed text with its branch and tree as `BRANCH` and `TREE`, the allowance sentence in that form, and the launch plan with each value's source; the `handoff-due` decision carries the same plan, so the holder sees what a handoff will spend before it spends it. `--ended-reason` closes a live hand record, printing its window line with that stage's own time (`ended-reason-is-for-a-hand-record` while a launched stretch is live). `--resume-reason` is refused `builder-not-stopped` unless the decision reads `stretch-stopped`, since a ready builder is resumed only by the send-back or a catch-up; it resumes a stopped stretch's session, takes the recovery restart where `work_recovery.restartable` accepts a launch with no session, or reopens a hand record and prints the continuation. With no `--timeout-seconds`, a resume launches with the stopped launch's `caller_limit_seconds`, and its `work: window` line is computed from that limit. Nothing resumes on its own. A lawful readiness record of either status naming a live hand record completes it (`completed_by: readiness`) at the next entrance run, so a hand builder that posts `stopped` reads `stretch-stopped`.
- **The plan the holder writes.** On the builder route the holder posts its plan as a draft marked `author=holder`, with `vendor=claude|codex`; a settlement names neither. On the relay route such a draft is invalid (`holder-draft-on-relay-route`). On the builder route a `holder-reading` is invalid (`not-read-on-builder-route`) and no `holder-read` is owed, because the holder wrote the plan. `run cold-seat` takes the producer vendor of a holder draft from its marker (`holder-written draft marker ID`), refuses `holder-vendor-disagrees` where a Claude session runs it and the marker says `codex`, and records a Claude seat on a Claude holder's plan `degraded` with `holder-written-plan`; the seat's own vendor is chosen as before, since this route leaves the entrance's model choices unchanged.
- **After the ready record.** A ready record at the head with synchronization clear continues into today's chain from `ready-reviewers` on, read for the builder: use is a counting composed use report with outcome `success`, at the head or an ancestor the use rules accept, and a `use` marker counts for nothing; a builder's `floor` marker counts without a floor bundle when, like every floor marker, it is `pass` at the current head by a configured marker producer, and its comment carries a floor command of one of the work's stretch handoffs with output beyond it; a cold-reading `clean` after its `open` needs no later builder turn; and the stretch is the builder turn for `builder-session`, the reading's due-ness and `open-pull-request`. The floor and cold-reading holds run first, as on the relay route. A stage the builder owed (`BUILDER_OWED_STAGES`) reads `final-pass` / `owed-at-ready`, so the holder is never sent to a stage that is the builder's. `_builder_route_owed` computes `owed_at_ready` at the record's head whatever GitHub's merge state, in order: the chain's first owed stage, the entry `owed-at-ready` names; `owed_unnamed`, each check the handoff's recorded `owed_checks` lists that the record's `checks` doesn't name, read from the stretch's request record or, for a builder started by hand, the hand record's handoff block; and on the mechanical lane each row with no counting `--row N` report from a reader that returned at the record's head and each row the record maps to nothing, each row listed once; each ready record is read in the release report by the reports posted before it, while the decision reads what is owed now, and a catch-up's fixed line has the builder read every row again at the new head. A merge blocked by GitHub's verdict or a required gate isn't listed, because merge readiness stays the holder's. A handoff block that can't give the owed checks leaves the list unread, never clear: the `final-pass` detail's `owed_list` reads `unknown` with that reason, beside any chain stage still owed, and row check 1.1 reads `unknown` from the same reading. The `final-pass` detail names the whole list, so a named `run release-report` made while the merge is blocked still shows it. A builder's `run catch-up` takes its holder session from its own launch and refuses one on the command line.
- **The final pass and after.** At `final-pass` a holder's `cold-seat`, `use`, `cold-reader`, `acceptance-criterion` or fresh `handoff` is refused `final-pass-launches-nothing` before any bundle, because the holder repeats no check the record shows run and launches no review after ready. `run send-back --dispatch FILE` runs once per term, because a second would rebuild the relay (refused `route-is-relay`, `with-builder`, `send-back-spent`, `not-at-final-pass`). It needs a lawful ready record at the current head, the builder ended, synchronization clear and none spent, and waits on no gate, reviewer or bought panel, whose findings are what it carries. It resumes the last stretch's session, or reopens a hand record and prints the text, with a fixed header ahead of the holder's text, and posts `<!-- tradecraft:send-back:v1 dispatch=ID -->` with that text, naming the new launch. Its launch spends it, not its marker: a `run send-back` that finds the launch made and the marker missing posts the marker and launches nothing. At the `catch-up` decision the holder's `run catch-up` merges nothing: it resumes the builder with a fixed line and no holder text and spends no send-back (`catch-up-not-due` otherwise). Both resumes default to 3,600 s, raised only with `--budget-override-reason`, and each fixed line asks for proof before a new record.
- **The release report on this route** adds `builder_route` (`route_report.builder_route`), read from the run's own decision (`WorkState.recommendation`) so the report and the decision read one state: the route, the readiness reading, the send-back, the catch-up resumes, each `--resume-reason` and `--ended-reason` with its reason, `handoff_plan`, the plan-writer launches, limits above their defaults with their reasons, the cost split, the comparison ledger, the stretch's refusals, the hand record's `ran_under`, `owed_at_ready` at the term's `first` and `last` ready records (the chain is read at the current head only, so where the term has more than one ready record `first` holds its unnamed checks and rows and `first_chain` says its chain stage wasn't read), `holder_quiet`, `holder_after_ready`, `reviewer_declines`, `stretch_seconds` (each stretch launch's elapsed seconds from its run record beside its limit, `not-applicable` for a builder started by hand, whose length the entrance never measured), and `row_checks`, each entry saying what it asserts (`ROW_CHECKS`): 1.1 holds only where `owed_at_ready.last` is empty and reads `not-occurred` with no ready record; 1.3 holds only where all three `holder_quiet` lists are empty, a message counting only where it went to the builder's session or dispatch and reading `unknown` where its recipient can't be told apart; 4.1 fails on an `other` bundle or a subagent or coding-agent session the holder's transcript shows after ready, since a stage or launcher it runs leaves a bundle of its own or none; 6.3 holds where `vendor_model` was observed, fails where it is declared beside a readable log, and reads `not-stated` with none; 7.1 holds on a `builder` route the change took by default and 7.2 on a `relay` route the owner asked for, read from the route's `chosen`, since by the report a change has launched and its route reads `in-flight`; and 5.2 pairs logged and reported refusals in order, because the record words a refused command its own way. On the mechanical lane 2.1 reads the handoff as composed from the affirmed brief, and 2.2 reads `not-applicable`, because that lane owes no use. `handoff_plan` is `composed` only where the stretch's received dispatch equals the handoff recomposed from its request's `handoff` block, with the roots it records; else `differs` (`holder-written` or `altered`), or `unknown` (`composed-by-another-version`, naming both) where the stretch's recorded producer version isn't the running one. A hand-started handoff is compared by its recorded digest, since the printed text isn't kept, and a stretch with no `handoff` block reads `differs`.
- **While a builder is live** every holder-mode `run` stage but `handoff` is refused `with-builder`, naming the dispatch, and `run handoff` refuses `builder-live` itself, `--resume-reason` included, since that is for a stopped builder; only `--ended-reason` closing a live hand record gets past it, so the holder launches and sends nothing until the ready report; the read-only decision still runs. One exception: a `run send-back` whose launch was made and whose marker is missing posts that marker while its builder works, and launches nothing.
- **The route** (`work._route`, in every entrance report as `route`). The first rule that applies decides: a repository the cloud route would take reads `relay`/`cloud`; otherwise the work's first `stretch`, `artifact` or `build` launch, in any term, reads `builder` for a stretch and `relay` for the others (`in-flight`); otherwise the latest lawful `route` marker (`<!-- tradecraft:route:v1 route=relay|builder -->` quoting the owner's words), in the issue body or a comment, a later comment governing over the body, reads `owner-asked`; otherwise `builder`/`default`, on every lane. `MARKER_REASONS` names the reasons a marker can move (`owner-asked` and `default`). `marker` names the latest lawful ask for the route the change is on, in flight too, so a release report shows it; one a rule above overrules is reported under `overruled`. A `builder-session` marker decides nothing. `chosen` says how the route was taken: the rule's own reason, or for a change in flight how its first launch took it, read from the asks the issue shows from before that launch (`owner-asked`, `overruled`, `default` for a builder launch with no ask, `unasked` for a relay launch with none). A route that can't be read is reported `unknown` with its error and the read goes on, and where the cloud switch can't be read the read-only decision is holder-owned, naming it.
- **The decision on the builder route** (`_builder_route_decision`). The `artifact` stage there launches no author: the holder posts the plan as a draft with `author=holder`. Where the relay route goes on to the governing terms and the build, the builder route takes the first that applies: a live stretch launch of the work is `with-builder` (`builder-live`), whose report also gives `if_ended`, what the decision will read once the builder ends, so the builder can repair its record or what is owed; no stretch launch in the affirmed term is `handoff` (`handoff-due`); a `stopped` readiness record is `stretch-stopped` (`cannot-launch`, or `builder-stopped` for a `shape` stop), as is a ready record not at the current head (`ready-record-not-at-head`) or no lawful record (`builder-stopped`), naming any record set aside and why; a base moved after ready is `catch-up` (`base-moved-after-ready`); otherwise `final-pass` (`ready-reported`), with the record's reconciliation.
- **Stages refused off the route** (`_refuse_off_route`). On the builder route, before any tree, bundle or write, a holder's `run build`, `artifact`, `floor` and `review-disposition` are refused `route-is-builder`, because one would move the change off its route unasked and start a second writer; `run proof` and `run ready-reviewers` are refused `stage-is-the-builders`, because the builder does both; and `run release-report` is refused `no-ready-record-at-head` until a lawful ready record stands at the current head, and once let through its detail names what the final pass reads as owed. A builder's run is judged by its stage table instead, and the relay route refuses nothing here. Each refusal, and the relay route's `route-is-relay`, names the route's reason, and advises the `route` marker only where that reason is `owner-asked` or `default`, because a marker moves nothing that `cloud` or `in-flight` fixes; on a default change the refusal names `route=relay`.
- **The handoff's text** (`handoff.py`). `owed_checks` lists the checks a builder owes, from the plan's fresh-reader criteria and whether use and the floor are owed; on the mechanical lane (`mechanical=True, rows=brief.rows(…)`) it lists one `acceptance-criterion --row K` entry for each row of the brief and no use. `compose_handoff` lays out in a fixed order the builder's role, the affirmed brief and the settled plan verbatim, or on the mechanical lane `MECHANICAL_HANDOFF_REASON` under "The mechanical lane" in place of the plan, the checks as commands with no holder session, the allowance sentence, the record's contract, the stop rule, how to finish (reading the record back through the read-only decision), and a hand-started builder's tree and access. The floor entry carries the holder's `--floor-command` word for word; with none, the declared CI jobs are the floor and a builder floor falling due is a `cannot-launch` stop. The text is byte-identical for the same inputs, so a received handoff can be recomposed and compared.
  - **The steps.** `_checks_section` renders the checks from `BUILDER_STEPS`, one ordered table of the builder's steps, each with the hold the entrance places on it, in the entrance's own order: push and open the draft pull request; the floor at the head, because the entrance reads the floor before the cold reading and the rest of its chain; the cold reader until `clean`; criteria, or rows; use where owed; reach; `ready-reviewers`; answer every reviewer; after any commit made once the floor ran, the floor again at the new head with its marker, the cold reading's `clean` and reach standing there too before proof, as proof's hold requires; resolve each answered thread where the decision names thread resolution (`reviewer-thread-answered-unresolved`, or a merge blocked on unresolved threads), in `RESOLVE_THREAD_COMMAND`'s form, which the entrance names only once that floor stands; proof; the readiness record; read it back, taking the earliest of several owed steps first. The text says the order is fixed wherever a hold names it. `handoff.STOP` is the stop rule, outside the order: the reasons that mean the builder stops (`builder-stopped`, `cannot-launch`, `affirmed-brief-marker-absent`) point at it.
  - **What the text says besides.** The stop rule is worded on what the brief's Shape sentence says the change is. "How to finish" covers a stopped record as it does a ready one: either is the last post, and the builder then tells the holder, or ends and the owner does. The cold-reader note says to paste the account as plain lines, not as a blockquote, because the `open` comment's match is line for line. Where the handoff names `--instalment` or the work already has a merged implementing pull request, the text says to open the new one with no closing reference and post its `implementing-pr` marker, the issue being closed by hand after the last instalment; otherwise it keeps the closing reference. The handoff block records which (`staged`), and a recomposition takes the recorded form. The record's section says a reach entry's `report` is the builder's `reach-reading` comment, or null where reach flagged nothing, and on the mechanical lane asks for a `rows` mapping of every row.
  - **The drift guard.** `work.BUILDER_MODE_REASONS` names every reason the entrance returns a builder between the handoff and the ready record, `owed-at-ready`'s inner reasons and the `if_ended` reasons included. `_decide`, which wraps the decision `_decide_unflagged` makes so every decision passes through it, adds `unlisted_builder_reason: REASON` to a builder-mode decision whose reason the constant lacks, and so does the `if_ended` decision a holder's `with-builder` report carries; it also adds the reason to `UNLISTED_BUILDER_REASONS`. The flag is report data only, and never fails or refuses a real builder's run. An autouse fixture in `lib/tests/conftest.py` fails any test after which that set isn't empty, and `route_fixture.py` exits nonzero on a scenario whose report carries the flag. A test holds that each listed reason maps through `handoff.ANSWERS` to a `BUILDER_STEPS` entry whose sentence is in the composed text, and a walk test drives `route_fixture` through the steps in order, with a commit after the floor and a base that requires resolved threads, asserting that each read-back names the table's next step, to `final-pass` / `ready-reported`. Together they give this: a reason the entrance returns a builder on a path the suite reaches is listed, and a listed reason has its step in the text. They don't reach a reason returned only on a path no test drives, or whether a step's sentence is clear enough to act on.
- **The row reader** (`brief.rows`, `run acceptance-criterion --row N`). On the `ordinary` / `mechanical` lane there is no plan to carry criteria, so the brief's rows are what a reader judges. `brief.rows` returns each decision row's number and whole text, outside fenced regions, from the three forms `_has_decision_block` recognises: a `**N. …**` bold row runs to the next bold row or to `Not this`, a `Row N` heading to the next heading of its level or higher, and a pipe-table row is its cells joined with ` | `. `--row N` runs in builder mode on that lane only; before any tree, bundle or write it is refused `row-reader-off-lane` on another lane, `brief-row-absent` for a row `brief.rows` doesn't return, `row-and-criterion` beside `--criterion`, and `stage-not-the-builders` in holder mode. Its dispatch is `compose_check_dispatch("acceptance-criterion", …)` with a fixed row preamble, the row's whole text and `readiness.RETURN_TAILS["acceptance-criterion"]`, with `read` on the change's own tree at head, and no option changes what it says or reads. `recompose_check` recomposes it from the bundle's recorded `row`, and its report's marker carries `row=N` in place of `criterion`. A report counts only where its `row` or `criterion` is the one its composed dispatch names, and only without `builder_vendor` unless its seat was staffed under a hand-started record. Every row is owed one counting report at the record's head, whatever the builder maps it to.
- **Hand-started records** (`launch_tree.write_hand_record`, `complete_hand_record`, `hand_holding`). A builder the owner starts by hand gets a `stretch` request record with `started_by` `hand` and identity `declared`, under the handoff's dispatch id where it names one, and a pointer marked `hand`. The record also names `holder_session_id`, the holder identity a launched stretch is given, and `handed_off_at`, because `run handoff --by-hand` is the holder's own command and the holder's quiet, its launches after ready and its cost split are read from them; a record written without them reads `unknown` for each, with that reason. With no process to end it, the pointer reads as live until `complete_hand_record` writes its run record, once, naming what completed it. Such a record holds a process only by its `TRADECRAFT_STRETCH_DISPATCH` variable, and only where no launch's tree holds it, or, once the entrance has dropped the variable before a seat, by the entrance's flags naming it. Its seats carry `launched_by.started_by: hand`, identity `declared`, and a present `CLAUDE_CODE_SESSION_ID` is recorded as its session, refused only where it is the holder session the handoff names (`hand_session`), because the holder can't be its own builder. The variable proves only what it declares.
- **The return tails, and a report's findings in the accounting.** `compose_check_dispatch` ends a use's and a criterion's conditions with `readiness.RETURN_TAILS` for its stage, so `builder_checks` gives each counting report its `stage`, the `builder` whose launch it is, and the `findings` its return's tail gives. A composed bundle from before the tails existed recomposes as `differs`.
- **The readiness reading** (`readiness_reading`, in every entrance report that finds a record as `readiness`). The latest lawful `readiness` marker governs; it is read with `readiness.reconcile` against every counting report any stretch or hand record of the term launched, at any head, a ready record naming a dispatch that is none of them being invalid, and the reading reports whether it is at the current head, whether its dispatch is this work's stretch, `reconciled` and what is not, its declines, decisions, refusals and stop, its relaunch pairs, and whether each check it names reads `composed`. A `fixed` finding's commit is asked of GitHub's comparison (`GET repos/O/R/compare/COMMIT...HEAD`), once per distinct commit in a reading: `ahead` or `identical` is in the head; any other status, a 404 or a 422 is `unreachable`, since GitHub answers either to a compare naming a commit it doesn't hold; a transport failure or an answer naming no status is `unverified`, with its error, and leaves the record unreconciled as `unreachable` does, under its own kind. `reachability` reads `checked` when every commit was answered and `incomplete` otherwise. A row reader's entry names `row` and no criterion, and `launched_by_builder` matches it to its report by `row`; a `reach` entry with no dispatch counts where its `report` is a lawful `reach-reading` by an authorized producer at the entry's head. `vendor_model` names the builder's vendor and model with its `source`: `observed` from a launched builder's own launch log, read as `dispatch_record` reads one, or from a hand-started builder's readable usage log; otherwise `declared`, with `log: absent` or `log: unreadable` and the reason. A declared pair that differs from the observed one is listed under `declared_differs`, and the observed pair governs. A record that isn't lawful is listed under `invalid`.
- **Quoted report markers.** `builder_checks.check_reports` lists only comments whose first content is the unquoted `check-report` marker; a comment that only quotes it, in inline code, a fenced or indented block or a blockquote, is listed under `quotations`, as the entrance sets aside quotations of its other markers.
- **The readiness record** (`readiness.py`). Its marker carries exactly `head`, `status` (`ready` or `stopped`) and `dispatch`, and its body one fenced JSON object (`payload`) with exactly `schema_version` 1, `builder` (vendor, model, `started_by` `launch` or `hand`, and a usage log or null), `checks`, `findings`, `rows`, `decisions`, `refusals` and `stop`. A reach check that flagged nothing is lawful with `report: null`; only a reach that reads `reading-required` owes a reading, since a pending or unmeasurable one flagged nothing a reading could answer. A ready record carries no stop; a stopped one gives its kind, `shape` or `cannot-launch`, the second naming the check it could not launch, and a reason. A record that breaks this shape, or answers one finding twice, raises `ReadinessError`; `marker_error` returns that reason, or None.
- **A report's findings.** Each composed check's return has a fixed tail (`RETURN_TAILS`), and `report_findings` counts from it: a criterion's opening `Result:` line, where `fail` or `unable` is one finding; a use's closing `Findings:` list of `F1.`, `F2.` … or `Findings: none`; a cold reader's account, where each flag and a `Can tell: no` is one finding. A tail that can't be read counts as the single finding `F0`, `findings-unreadable`.
- **Reconciling.** `reconcile` holds every finding of every counting report to exactly one entry in the record: `fixed` with a commit the caller finds reachable, or `declined` with a reason. Otherwise the finding is `missing`, `unreachable` or `reasonless`; a second answer, or an answer to no finding, is `extra`; and a report with findings the record doesn't name is `left-out-of-record`. `relaunches` pairs each errored check with the later check naming it in `relaunch_of`, and `unmapped_rows` lists the brief rows no `rows` entry carries.
- **The route's cost** (`change_cost.py`). `route_split` gives three list-price figures: the holder's replies before the handoff, those at or after it, and the builder's, from a launched builder's own launches and every seat whose `launched_by` names one. The handoff's time is the stretch's `launched_at`, or the hand record's `handed_off_at`; a hand record without one makes both holder figures `unknown`. A hand-started builder's own figure is read from the usage log its readiness record names (`hand_usage_log`) by its declared vendor's reader (`hand_vendor`, lower-cased), a Claude transcript or a Codex event stream; any other vendor, or a log that isn't a readable regular file, reads `unknown` with its reason. That figure is the log alone and leaves out the seats that builder launched. The entrance reads that log only to price it and observe its vendor and model, and never follows it into a write; what it observes is the session that log records, the one the builder's record names. One unknown value makes its figure unknown. A launched builder's Claude launches, fresh or resumed, are priced reply by reply: each retained stream (`<output>.claude.stdout.log`) names its replies' message ids, priced from the session's transcript, because a stream's output count is the count as each reply began. An unreadable stream or transcript, or input-side counts the two disagree on, makes the figure unknown with its reason; a Codex resume keeps its share of the session the stretch began. `route_comparison` does nothing unless `~/.tradecraft/route-comparison.json` names an issue and a count; then it enters each work once in a ledger beside that file and reports `due` on the call that enters the count-th. Where the file names `since`, a work whose first stretch launched or was handed off earlier, or whose first launch can't be read, isn't entered (`not-counted`).
- **The holder's quiet, and its launches after ready** (`holder_transcript.py`). The holder's session and the window's start come from the stretch's request record (`holder_session_id`, `launched_at`) or the hand record (`holder_session_id`, `handed_off_at`). `holder_quiet` is `handoff_quiet` over that session up to the first ready record's comment, with three lists: `calls`, each call that ran a `work.py run` stage, a dispatch launcher, a `SendMessage` naming the builder or a GitHub write naming the change; `launches`, every agent the holder started in the window, a subagent or a direct command-line launch included, whatever message came before it (`launch_calls`); and `unprompted`, each reply no owner or delivered peer message asked for. `holder_after_ready` lists every seat or implementer bundle of the work begun after the first ready record that no builder launched, classed `bought-panel` (by the `panel` stage or role its launcher records), `source-verification`, `send-back`, `catch-up-resume` or `other`, and the `launch_calls` of the same session over the same window. An unreadable transcript, or a hand record with no session or time, reads `unknown` with its reason.
- **The reviewers' declines** (`reviewer_declines`). Every finding of a connected reviewer's review that the pull request answers `declined`, its opening word's formatting read past as the gates read it, through the readers the disposition gates use (`_disposition` for an inline reply, `review_findings._bare_disposition` and its review-link and identity patterns for a body-finding comment or a whole-review answer), so the report and the gates can't disagree about which answers stand, each with its reviewer, the finding's identity, the builder's reason and a link to the answer.
- **Also.** Only the last launch's ready record governs; a launched handoff keeps its tree unless the launcher exits before its pointer; proof takes use from the counting use report and declares the floor from the stretch's request, so a posted proof stays current after the launch; reach counts stretches, and a builder measures its own live launch at the head it reports, so it settles reach before `ready-reviewers`; a holder's read sees it pending; a builder floor puts its command in a block with output after.
- **Detached spawn** (`detached.py`). `spawn` starts a process nobody waits on, outside every caller's containment: through WMI on Windows and by a double fork on POSIX, with its output appended to named files or dropped. Keep-warm's runner starts through the same helpers.
- **The guard additions.** The write check's GraphQL query file and `tradecraft:send-back` refusal, and `at` on a stretch launch's refusals, are set out in A builder's own checks and writes.

**Why.**

- A report's findings come from a fixed tail, an unreadable one counting as one, and reconciliation reads every report the builder launched, so none vanishes or goes unanswered. Spawn is detached so the holder doesn't wait, and the comparison is switched on by a machine file so nothing lab-specific ships.
- The builder route is the default, so a change the owner says nothing about takes it, the mechanical lane included. The relay route is taken by a `route=relay` marker, a repository whose builds run in the cloud, or a first launch on it, and stays whole so a change can go back without a second change.
- On the mechanical lane every row gets its own reader, and the builder's mapping removes none, because a check is independent only while the party it checks can't aim it; a row reader reads the change at head with `read`, since choosing a capability or a tree for each row would be the builder choosing what it reads.
- A hand-started builder's seats keep the entrance's vendor and model, which this route leaves unchanged; only the staffing judgment follows the declared vendor, because that is the vendor whose work the seat judges.
- A fixed finding's commit is asked of GitHub rather than the holder's checkout, because the builder's commits live on its pushed branch, and an error never counts as reachable. What it checks is that the fixed commit is in the head, not that it came after the report it answers.
- Merge readiness is left out of `owed_at_ready`, because it stays the holder's.
- The handoff's order comes from one table that the suite ties to the reasons the entrance returns, so a step the entrance holds a builder on is a step the text names; the flag never fails a real builder, so a reason added later costs it only the flag in its report.
- The route is fixed by the work's first launch, over every term, so a change in flight finishes on the route it started and an amended brief can't move it; a `builder-session` marker can't decide it, because one may stand on either route.
- The handoff is composed rather than written, so a builder never receives instructions for a check that the entrance didn't compose, and the text it received can be compared byte for byte.

**Decisions in force:** D-1017, the builder route as the default, completed with row readers, a hand-started builder's staffing and cost, the vendor and model each record names, a fixed commit's reachability, and the release report's remaining fields; D-1013, the builder route, fixed by a work's first launch, a handoff composed once, a builder that answers for readiness through its record, and a release report that shows the owner its declines and decisions; D-1012, a builder's own checks and writes, which this route composes.

## Pricing a run

**What it does now.** `change_cost.py report` prices each recorded run from two price files: the shipped card, `lib/rates.json`, and the repository's own `.tradecraft/rates.json` at the top level of the checkout it runs in, or of `--root`. For each model and time, a shipped row that covers the use wins; a repository row is used only where no shipped row covers it, and the report lists a repository entry under `repository_entries_now_shipped` as removable once shipped rows price its model over the entry's whole interval, from its `effective_from` to its `effective_to`. Every priced share records which file priced it. A damaged repository file, or a row in it that is incomplete, still holds a `FILL` placeholder, has no currency, or carries a price that isn't a finite nonnegative number, is named under `price_files` and left unused, and the report runs on; a damaged shipped card stops the report. The report never writes either file.

A model that no row prices, including one whose row has ended, leaves its run with a figure. In a dispatch, that model's share comes from the runtime's own figure when the runtime recorded one marked `costBasis: "list"`, labelled `runtime-list-price` with no card amount; otherwise the share is left out and the run's figure is a floor whose reason names the model. A Codex dispatch has no runtime figure, so its missing model is always a named floor. A keep-warm ping on such a model is left out the same way, and the keep-warm line's floor gives the ping count for each model. In a holder transcript, replies on such a model are left out, and the row's floor gives the reply count for each model; when they are the only replies, the row is known at zero. Any other fault in a dispatch makes it unknown. In a holder transcript, a reply with any other fault is left out and named as a floor reason, and the row is unknown only when no reply could be priced; a reply with no price whose native count is malformed is such a fault, so on its own it leaves the row unknown. `total.runtime_list_price_models` lists the models a runtime figure priced. A subagent's transcript replies count as covered by a dispatch only for a model that dispatch priced.

A row may carry `prompt_tiers`, each a threshold and its own classes: a request whose prompt, its input plus cache reads plus cache writes, is above a threshold takes that tier's prices, and one at or below every threshold takes the row's own. Tiers are applied where each request's counts are kept: each transcript reply, and each call within a keep-warm ping. Where only a run's totals are kept, a tiered model is never priced from the card; it takes the runtime's list figure or a floor that says it is priced per request.

When a dispatch carries only the aggregate cache-write count, the comparison with the runtime's list figure accepts the card's figure at either the one-hour or the five-minute write price, and records which reading matched; a runtime figure more than a cent from both readings is flagged and the card's one-hour figure used.

Wherever a model has no price, whether the run ends known, as a floor or unknown, the report's `missing_prices` names it with the vendor's posted pricing page, the uses that met it, the repository file to paste into, and a ready-to-fill entry in the vendor's shape. Each price and the retrieval time in the entry is a `FILL` placeholder naming the page column to copy, under each header the page is served with; `cache_creation`'s says to repeat the one-hour write price, because the card keeps that class at the one-hour price for records that report only their total cache writes. `effective_from` is midnight UTC of the earliest affected use, and when the repository has no price file yet every item's `new_file` is the same whole file, holding every missing entry, so saving any one of them loses none.

**Why.**

- A helper model with no price is often a small share of a large run, and making the whole run unknown would drop every share the card does price. A floor that names the model keeps them.
- The runtime's figure is trusted only when marked as a list price, because a runtime too old to know a model charges it at another model's rates and marks that figure otherwise.
- The repository file sits in the repository, not beside the shipped card, because the shipped card lives in the installed plugin, where an entry pasted there would be lost at the next update and would show as a change to the plugin.
- A shipped row beats a repository row, because the practice checks the shipped card against the posted page and a pasted entry is checked by no one; the note says when the pasted one has served its purpose. It waits for the whole interval, because deleting the entry loses every use the shipped rows don't price, whichever uses one report happens to hold.
- A tier's prices are checked as strictly as a pasted row's, so a malformed shipped tier stops the report rather than pricing long prompts at nothing. A shipped row's base classes are not checked that way, because a `null` base price is how the card says a class has no price, and a run that uses that class is reported unknown for that reason.
- A damaged repository file doesn't stop the report, so a half-filled paste can't take away every other figure, and the guidance still shows how to finish it.
- A runtime figure or a zero excluded share is in USD whatever the card's currency, so a dispatch no card row priced is reported in USD and counts in the change total; a runtime figure is never added to a card figure in another currency.
- The guidance is built from where a missing price was met, not from the run's final status, so a run that ends unknown for another reason still says how to price the model.
- Tiers are priced per request because the vendor bills each request at the tier its own prompt reaches. Tiers are not applied to totals, because totals can't show which requests crossed the threshold, and pricing them at the lower tier would understate every request above it.
- A helper subagent writes five-minute cache and a main conversation writes one-hour cache, while `modelUsage` reports only their sum. Without the second reading, every recorded helper share would be flagged against a runtime figure that was right.
- No reading of the live page while a report runs and no command that writes an entry: adding a model is a lookup on the vendor's page and a paste into the repository's file, which the guidance makes complete, and a reader who looks the price up sees what the page says that day.

**Decisions in force:** D-999, price every model a run used and say how to add a missing price.

## The entrance's work before a launch

**What it does now.** `work.main` opens one run scope (`preflight.scope()`) at entry for every command, and each launcher opens its own, continued from the entrance's handoff. The scope holds the run's monotonic start, its timing split, its read-route tally, its read memo and its dispatch-store indexes. Outside a scope every reader reads directly and keeps nothing, so tools and tests that open none read the store and run Git each time they ask. Nothing is kept between runs.

- **The store index.** `run_lifecycle.StoreIndex` lists `*.request.json` and `*.run.json` in `rglob` order. It reads each request record once, and a run record only when a reader selects its bundle, and hands readers copies. It lists again after a child that is not a read returns, which is also when the records this run's launcher wrote appear, rereading only records that are new or whose size or modification time changed. A record written inside the entrance's own process would be dropped with `StoreIndex.forget`; no entrance path writes one today.
- **The read memo.** `build_reach.Git` memoises successful reads whose revisions are full object ids, plus the repository-constant reads; a branch read lasts only until the next refresh. A turn already measured starts no process, and a returned turn has new ids, so it is measured once after it returns. Failures and time-outs are never memoised.
- **The pull-request candidates.** `_implementing_candidates` takes them from the issue itself, authorized `implementing-pr` markers, the issue's timeline (cross-references from pull requests in the same repository) and GitHub's closing-reference graph. A number from the timeline or the graph is kept only if its pull request's current body closes the issue. No request lists a repository's pull requests.
- **The blob batch.** Binary detection reads every unknown blob of one diff inventory through one `git cat-file --batch`, one blob at a time through `seat_process.stream_read`, and the temporary view is built once per root per scope.
- **The read route.** `seat_process.run_read` starts a read suspended inside a parent-held kill-on-close job on Windows, resumes it, and closes the job on every return. Where the job cannot be set up the read takes the worker route and the run's `read_route` says so. On POSIX a read keeps the process-group route. The decide's reads take this route as well as a named stage's. A read whose pipe something it started still holds when its drain ends is refused as cut short, rather than answered with part of its output. The Git writes take it too, with `writes=True`: the entrance's own, creating and publishing the implementation tree and making catch-up and merge obligations (`worktree add`, `push`, `fetch`, `merge`, `add`), and a refusal's cleanup of a worktree it made (`worktree remove`, `branch -D`); the cloud route's (`push`, `fetch`, `merge`); the recipient tree's (`init`, `config`, `add`, `update-index`, `commit`, `checkout`); and the artifact copy's (`clone`, `checkout`, `config`, `remote remove`), so a hung write is stopped with what it started; a write is judged by its exit status, and one that exited 0 stands even when its output was cut short, because it has already happened. The recipient tree is built by `tree`, outside any stage, so its writes keep their own bound; the entrance's, the cloud route's and the copy's writes before a stage's window also take `write_timeout` (see A run's window and the entrance's cap).
- **The split.** Every report, refusal and request record carries `preflight`: seconds from the call, split into `github`, `removals`, `markers`, `launch_preparation` and `vendor` (the vendor program's own processes before the spawn), the innermost part winning and the remainder `unattributed`. The launch is the launcher's first write of the request record, which carries the split to that write (`until: request-record`); each spawned attempt carries `pre_spawn_seconds` and `pre_spawn_parts` to its spawn, the first attempt measured from that write and each later attempt from the end of the attempt before it, the moment that attempt's recipient returned, because a recipient's run is not the launcher's work. An attempt that spawned nothing takes no new start, so its preparation stays in the next attempt's interval. In the entrance, `launch_preparation` runs from the decision to the handoff, and closes before the launcher starts so the wait is never counted. After a launch returns the entrance finds its own bundle by the launch's work and stage, launched after the call (or beside `--output`), and prints the request record's split added to the first spawned attempt's interval (`until: spawn`); a seat stage prints one such line after its return. Where no attempt was spawned, the line carries the request record's split as it was written (`until: request-record`). With no split in the bundle the line falls back to `until: report`. A launcher that refuses before writing its request record prints its own `until: handoff` line on the standard error it shares with the holder; the entrance does not read or repeat it, and its own line after that refusal reads `until: report`. The entrance hands its split to a launcher with the hidden `--preflight-input`, and the cloud route, run inside the implementer launcher, writes its request record's split the same way.
- **Time-outs are named.** `run_lifecycle.RunTimeout` carries `limit_phrase`, the one place a limit is named. `build_reach.ReachTimeout` says time ran out and names that limit, and the removals refusal's advice follows each turn's cause. A missing commit keeps its own message.

**Why.**

- Each piece is done once per run, so the entrance's work grows only with the change's own builder turns; done per report, per marker or per file version, it would grow with the store and the repository instead.
- The index keeps `rglob` order because readers return the first damaged record or the first unsupported schema they meet. Run records are an order of magnitude larger than request records, and a bundle needs both to count, so reading the request first changes no result. Copies keep one reader from changing what another sees.
- The index relists only after a child that is not a read, the only place this run's records are written, because only those change what this run's questions depend on; records other runs write in between are not this run's evidence.
- Only reads of full object ids and repository constants are memoised, because nothing can change their answer; a branch moves when a builder returns, and a failed or timed-out read must be tried again.
- A listing of every pull request grows with the repository's whole history. Both the timeline and the closing graph are read because a missed candidate reads as no pull request and starts a second builder, and the timeline is filtered to the repository because it carries cross-references from others. A timeline or graph mention counts only when the pull request's current body closes the issue, because a mention alone does not claim the work.
- One batch per inventory makes a turn's Git processes grow with its commits and merges rather than its files; reading one blob at a time keeps memory bounded by the largest blob.
- A worker would be a second Python process for every read, often costing more than the read. The parent-held job gives the same guarantee, that a read stopped at its bound leaves nothing it started, at about the cost of a plain read. The job can be refused, as inside a sandbox, so the fallback is the contained worker route and never an uncontained read. A POSIX process group needs no second process.
- The request record is not written later, after the before-snapshot, because a launcher stopped before that write would leave no record. The split ends at that write rather than at `launched_at`'s stamp, so the reads between the two are counted, and `launched_at` stays where it is because the launch comparison reads it as the run's opening. The vendor's time after the spawn is the recipient's, so it is no part of the entrance's split.
- A run that runs out of time may still hold every object it was reading, so advice to fetch or restore sends a holder after revisions it has instead of raising the limit. `RunTimeout` keeps the messages callers already match on.
- The launch comparison's before-snapshot and after-walk keep their own reads in the launcher, because they ask about another moment: the store as it stands around the recipient's run.

**Decisions in force:** D-998, the entrance does its work before a launch once, contains each read without a second process and records its split, the launch being the request record's first write; D-1003, a stage's limit is its recipient's time and the entrance's work before the launch has its own cap, which bounds this section's work; D-840, the reserve, the build budget and stopping a hung read with what it started; D-939, a Claude launch's writes stay in its tree, whose before-and-after comparison keeps its own reads in the launcher; D-872, the removals count, which is read once per turn here without changing what it reports; D-996, the launch comparison's own read of the store, which stays separate.

## A run's window and the entrance's cap

**What it does now.** A named stage's run has two phases, held by one `run_lifecycle.Deadline`. Until its recipient starts, the run is inside the entrance's cap (`PREFLIGHT_CAP_SECONDS`, 900 seconds unless `--preflight-cap-seconds` declares more for that run), and its end is the latest return it prints: the call plus the cap, the allotted time and the reserve. `open_window` marks the recipient's start and sets the end to that start plus the allotted time and the reserve, so the part of the cap the run did not use is not spent. `withdraw_window` returns the run to the cap when an attempt spawned nothing. `require_cap` checks that enough of the cap is left for the work still to come before a spawn; it, and any read or write the cap's end cuts, raises `PreflightCapExceeded`, and the stage launches nobody, leaves no bundle and prints its split. Before the window opens a read is cut at the cap's end, and `write_timeout` never begins a write after the cap and bounds one begun before it by the latest return less the reserve. A refusal's own cleanup, such as removing the worktree and branch an add made, comes after the cap and has that same bound, because the cap's end has already spent any allowance counted from it.

- **Where the cap is checked.** The entrance checks it before its writes and at its handoff to the launcher. A launcher checks it at its start, and again before the request record's first write with an allowance covering every attempt's steps before its spawn: 20 seconds for the version read, 120 seconds for the before-snapshot where the launch is compared, the GitHub write bound's preparation for the seat that carries it (whose self-test stops at its own bound, `github_allowance.SELF_TEST_SECONDS`), and a 5-second margin (`SPAWN_MARGIN_SECONDS`) for the in-process work between them. The cloud route and the four stages that launch nobody (`catch-up`, `proof`, `ready-reviewers`, `release-report`) check it when their window opens.
- **Where each route opens the window.** A local launch opens it immediately before the spawn. A seat's fallback opens its own window with the whole limit, and spawns only by the cap's end; a fallback whose turn comes later is not started, and its attempt is recorded unavailable. The cloud route opens it at the fire or follow-up send. A stage that launches nobody opens it once the entrance has read and decided, so its limit is its own work's time.
- **The launch notice.** A launcher writes `launch-notice.json` with `window_opened_monotonic` when it opens the window, so the entrance's wait for it follows the recipient's window rather than the cap. A captured wait, the one a builder's check uses to read its launcher's frame, follows the window too (`run_process`'s `on_window`), and reads it before the old deadline stops the launch.
- **The return-time line.** A named stage prints `work: window {json}` as its first line, with `latest_return_at` computed from its own deadline (`window_line`). A launcher called directly prints `implementer: window` or `seat: window` first, the same way. The entrance passes the stretch launcher every limit, so it adds the hidden `--limit-declared` where its holder declared one, and the launcher's line says `declared` itself.
- **Allotment.** `Deadline.allotted` is the declared or default limit, held to the 3600-second ceiling of `floor` and `review-disposition`, counted from the launch; the window line says when a ceiling holds a larger declared limit. The reserve, the smaller of 60 seconds and the larger of 10 seconds or a tenth of the allotted time, follows the allotted time. A build's remaining budget is applied after that, by `lifecycle.allocation`, to the allocation its recipient is given, so the reserve and the printed return time stay those of the allotted time.
- **The clock's start.** The run's clock starts at the process's creation time where the platform gives it, and at entry where it does not; the split's `clock_start` reads `process` or `entry`.
- **Declared caps.** A run that declares a cap records the figure and its reason in a file under `~/.tradecraft/preflight-caps/<owner>-<repo>-<issue>/` before its first read, and adds its outcome once it knows it; a launched stage's request record carries them too. `run release-report` lists every declared cap for the change as `declared_caps`.

**Why.**

- A limit counted from the call would take the entrance's own time out of the recipient's, unseen. Counting the recipient's time from its start gives it what was declared, and a separate cap turns a slow entrance into a refusal with its split rather than a short build.
- The printed return time is fixed at the call, so the run still ends itself before its caller can know it ran over: the caller plans from that line, and the run returns, its record written, before it.
- A write in flight is not cut at the cap's end, because a half-made worktree, copy or push is worse than a refusal a little late; none begins after the cap, and each is bounded by the printed return so the run still ends in time.
- Every recipient a stage starts, a fallback included, gets its whole limit, so the only recipients given less are the closed list of exceptions: a build held to its remaining budget and a repair held to its ceiling.
- A declared cap is recorded before the first read so a run stopped part-way still leaves its reason, and the release report lists every one so the owner sees each run that needed more than the default.

**Decisions in force:** D-1003, a stage's limit is its recipient's time, counted from the recipient's start, and the entrance's work before the launch has its own cap; D-840, the reserve, the build budget and stopping a hung read with what it started; D-998, the entrance's work before a launch and its split, which the cap bounds; D-1012, a builder's captured check wait follows its launcher's window, so the check keeps its whole limit; D-1013, the stretch launcher is told when its limit was declared.

## A relay turn's own checks

**What it does now.** `work._check_account` writes the paragraph on checks in the instruction of every composed `build`, `floor` and `review-disposition` prompt, in a mechanical-lane wording (affirmed rows) and an artifact wording (acceptance criteria), local and cloud alike. It has the builder map each obligation to a committed test, a check it runs itself or an owed fresh reader; on the mechanical lane a row that names its checks after `Checks:` is mapped by those checks. A check the builder runs itself is run at the turn's final head when it has no earlier result the builder can cite by revision, when anything changed since the revision it last ran at can affect it (that turn's commits, an earlier turn's, or a merge of the base), when the builder can't rule an effect out, or when a holder reading in the dispatch or the holder's own dispatch text names it, unless an earlier turn already ran it after receiving that reading. A mechanical-lane prompt carries no readings, so a note there travels only in a dispatch the holder writes, which must carry this account itself. Every other such check is returned anyway, with the revision it last ran at, its result there and why nothing since can affect it, so the return accounts for every obligation every turn. Each owed fresh reader is returned after every repair for the holder to launch. The builder route's handoff, send-back and catch-up lines share none of this text.

**Why.**

- A check is scoped at all because a plan's own checks can run for many minutes, and rerunning one on a small repair that can't reach it spends the stage's time limit for nothing; it can push the turn past that limit and lose its return.
- The builder knows what it changed, so it can scope its own checks with no text from the holder; these are checks it already runs on its own work, so scoping them hands it no independent check. A fresh reader's check stays the holder's to launch, and CI runs every committed test at every head.
- A check is scoped by everything since its last run, not by one turn's commits, so a turn stopped before its checks, or a merge of the base, can't leave an affected check carried.
- A carried result names its revision and reason so the holder can read the reason against the history and have the check run where it doesn't hold; a holder's note naming a check always wins, on the turn it comes with: every reading after the settlement is carried into every later turn, so a note binding every turn would bring back the long rerun this section removes.
- The entrance checks none of this. The record is the builder's reasons and the holder's reading of them, and the floor is still read at each head.
- The builder route keeps its own rerun lines until a repair there has a measured cost, so that its scoping rests on its own measure rather than on this route's.
- One function writes both wordings so they cannot drift, and one text serves a first build and a repair: a first build has no earlier result, so it runs everything.

**Decisions in force:** D-850, the declared CI floor and the account every build or repair returns, with its builder-executable checks scoped as D-1029 says; D-944, brief rows that name their checks in the owner's cell, which the mechanical wording maps; D-885, the mechanical lane's accounting by affirmed row, renewed after every repair as this section's account; D-1029, a relay repair runs only the checks a change since their last run can affect.
