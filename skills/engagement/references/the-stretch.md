# Holding the unattended stretch

**Loaded when** coordinating the stretch from an affirmed implementation brief to release readiness, taking one of its dispatched stages, staffing a judging seat, or preparing its reports and records.

## The holder and the implementer

**The holding session designs the change with the owner through affirmation and owns the whole stretch that follows.** It dispatches every stage and receives every return, remaining the owner's counterpart through the reviewed pull request and its posted report. One holding session per change, never one for many, because its context grows from the first turn through every stage. It edits no file in the implementation tree and takes no judging seat. Where responsibility changes at affirmation, the handoff rule (`../references/the-handoff.md`) governs the exception.

The builder launcher registers an implementation worktree before dispatch. In a holder runtime that loads project pre-tool hooks, the holder guard rereads that machine-local registry on every edit, write, notebook edit or shell call and refuses an implicated write. A runtime with no such hook records the guard as unavailable and retains before/after revision and status evidence; those snapshots detect a breach but do not enforce the boundary.

**The material handing a party its job states the tools and permission or approval route it must be started with to perform it, and a launcher capable of checking that declaration refuses a launch that would not supply it**, because instructions cannot supply a capability the launch withholds.

**The holder resumes the artifact's implementer through substantive cold-reader repairs, the build, and every prescribed repair after judgment or use**, because those stages depend on the builder's choices or on the tree and finding the builder already holds; this includes small fixes. A holder session identifier and a builder session identifier may never be the same in a dispatch record, because a separate process is the enforceable half of that role boundary. **Source-verification rule:** every durable account the holder authors or finalizes on the unattended stretch, whose factual claims are established by the change tree, GitHub state, or a stage return, goes to a fresh implementer for source verification before release. This property, rather than a roster of surface names, selects the account; for example, it reaches a review report draft when that draft makes such claims. It excludes the affirmed implementation brief, which is the owner's settled term; a dispatch as an instruction, while its factual shared block is source-checked with the eligible account it belongs to rather than by a separate check of every dispatch; and the implementer's artifact and commit message, whose own rules retain their checks. **The default report sources are the executable floor, any required experience session and the connected reviewers' in-thread dispositions; a terminal ruling and fix batch are sources only where the owner bought a panel or those stages actually ran.** Where a panel was bought, its merged list, defense and terminal ruling remain stage-return producers the source check compares against, not accounts it assesses. The fresh implementer receives the exact account drafts with the affirmed brief, implementation tree, pull request state, the durable dispatch records required by this cell's `dispatch-records.md`, and the unabridged returns and in-thread dispositions that produced their claims. Its instruction says to compare every verifiable claim with its producer and return what cannot be verified rather than repairing, reinterpreting, or silently narrowing it. **During a fix batch, writing parties run serially in the change's implementation worktree and branch:** the resumed builder finishes and commits that batch before a fresh installer writes eligible repository content, and neither writes while the other does; source-ready accounts that precede a fix batch remain under their own installation procedure. The implementer returns at the extent its dispatch names. A recipient needing another party returns that need to the holder; recipients dispatch no pipeline stage themselves. Each instrument retains its own ordering, evidence, isolation and settlement rules.

**For a Codex implementer**, use `lib/dispatch_implementer.py`, which applies the explicit model and effort, workspace-write with automatic approval review, JSON return capture and a named session id without `--last` or `--ephemeral`. The dispatch tells the implementer to report a sandbox refusal and request approval to retry it, since stopping at the first failure suppresses that route. A fresh turn returns the id its later `--resume SESSION_ID` takes; a completed turn with no trustworthy id returns its product but cannot qualify as resumable. If approval is rejected or unavailable, report that inability to the holder. The [launch spike](https://github.com/Grimblaz-and-Friends/tradecraft/issues/593#issuecomment-5653831839) and [resume by id](https://github.com/Grimblaz-and-Friends/tradecraft/issues/593#issuecomment-5654461236) demonstrate the capability; the `dispatch-records.md` entry in this cell carries the launcher and record contract, including the manual path for a Claude implementer.

## A surprise from build onward

**From the start of build onward, a surprise is compared first with Shape and then with the reader cells of the affirmed implementation brief.** If Shape is wrong, stop: the term no longer covers the change. If a reader cell would now read differently, write only the affected row as a proposed contingent row, carry the recommendation and its strongest case against, and continue the run on that recommendation. Put it to the owner at once when they are present; otherwise post and mark its ask, and put it first at release if it is still open. If no cell changes, report the surprise with the session's reason and continue.

The posted row uses the ask block and mark in `../references/the-ask.md`; as the reading amendment in `../references/the-brief.md`, it carries the contingent row's criteria into the settled artifact without buying a fresh verdict, and is not an edit to the affirmed item. The holder gives the builder the affected row, the recommendation, and the contingent alternative, so continuing never turns into choosing silently.

**A seat judges a contingent row on both readings.** Its surviving criteria must be falsifiable whether the owner keeps the affirmed row or accepts the proposed one.

## Staffing judgment

**Every judging seat is a fresh dispatch on the other vendor from the implementer's**, with only the history its instrument permits: the artifact's cold reader, review seats, defense, judge, and the experience session's consumer. By default Claude holds the implementation brief, Codex implements, and Claude staffs judging seats. The comparison is with the implementer, whatever vendor holds the implementation brief. Each launch names its model and reasoning effort; freshness does not erase the predecessor evidence a role is meant to receive.

**The experience consumer also runs on the runtime the change's users run.** Both requirements apply. Where no qualifying consumer can be supplied, record the missing use and why under the instrument's omission route.

**An experience consumer takes the ordinary judging effort.** Its coldness protects the run from briefing, while the top effort is reserved for open-ended artifact/review perception and the terminal stage. The review roster carries those seats' effort split. An owner's recorded per-change instruction wins over either default without moving a stage between vendors.

**Staffing is read from the actual returned vendor.** A return from the requested vendor records `qualified`; an availability fallback records `degraded`, with requested and actual vendor and the reason. A degraded return does not complete a cross-vendor or fresh stage unless that stage carries its same-vendor reason, because capability alone does not restore the independence the requested staffing bought. Where the fallback cannot supply the declared capability, no judgment returns and the instrument's missing-seat or omission route applies.

## Returns and records

**Every return comes back to the holder and travels onward whole.** A file is the transport where available; the artifact's cold check takes its prescribed inline carrier. The holder passes the source itself, with only the labeled additions the receiving instrument permits and the withholding its cold boundary requires. It merges findings as an index of the source reports; the judging stage rules on the work.

**The holder writes the report and records from those returns, and sends each eligible account through the Source-verification rule when its sources are ready.** Once the executable floor, any required experience session and the connected reviewers' in-thread dispositions have supplied the default sources — joined by the terminal ruling and fix batch only where the owner bought a panel or those stages actually ran — the release-ready pull request body and any report draft are checked before posting. The release report carries any decision that is the owner's once, as its argued ask. A returned correction stays with its holder-authored account and any revision changing a returned claim is checked again. Only an account that needs a posted panel report's URL waits for that posting; another source-ready account is verified and installed under its own procedure. Once posting supplies the report URL or another source a dependent account needs, the same fresh implementer may resume to verify, install, and commit that eligible repository content. This keeps authorship with the party that saw the run and gives its claims an independent checker without making the checker a review stage. The holder retains every dispatch through this cell's `dispatch-records.md` contract, then applies each instrument's population when it aggregates cost rather than reconstructing it from prose. It publishes the branch, opens the pull request, posts any bought panel's report, and delivers the outcome to the owner; merging remains the owner's.
