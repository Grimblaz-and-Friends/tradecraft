# persist-changes

The mechanical sequence is owned by a script; the judgment about *what* to land and *what to say* stays with you.

**Purpose:** land validated work, including a catch-up merge, with staging, message, committed content, and push held to this practice's standards. **Audience:** any session with finished work or an in-progress catch-up merge ready to land on its current branch, or a protected-branch rejection to route. **Success:** the committed content equals the staged content and that commit is the verified remote head, with an honest message — or the stop is a typed one-line reason.

**Pause discipline: typed-halt.** This skill never asks a question: every stop the script's own logic reaches is a typed one-line `not-persisted: <reason>`, so it is safe in unattended runs.

This cell covers landing finished work, including a catch-up merge, and the protected-branch push-failure route below. Choosing whether and how to integrate, choosing a merge target or rebase, resolving conflicts, creating branches or pull requests, amending history, and recovery beyond those routes remain above this skill. The script has one history exception: after identifying its run's exact commit and parents, it retracts its own unpushed commit when its content differs from what it staged, only while the recorded branch still points exactly to that commit and its first parent is the recorded start head. This keeps unchecked content from riding a later push without discarding another session's commit.

## The mechanical part — the script owns it

The script sits beside this file at `scripts/persist.py`. Invoke it by that path resolved against the directory this file is in:

```
python scripts/persist.py -m "<message>" [<path> ...]
```

It operates on **the repository containing your current directory**, and **paths are resolved from that repository's root** no matter where you invoke it from.

For a catch-up, start with `git merge --no-commit --no-ff <base>`, or resolve and stage an already conflicted merge, then run the script. An in-progress merge supplies its staged content, so no path list is required; named paths stage any further working changes. Outside a merge, name at least one file or directory. This keeps the merge's commit inside the script's content and remote-head checks; `--no-ff` also prevents a fast-forward from finishing outside the script.

Publication means that a current branch on any configured remote contains the commit, even when the intended push branch is older or absent. The script reads the selected remote's branch heads and, when merge ancestry remains outside them, the other configured remotes' current heads. Object inspection and ancestry use batched input; missing advertised objects are fetched in batches, keeping remote branch counts out of command lines. Ancestry uses the recorded IDs; tags and stale tracking refs do not establish publication. An unreadable required snapshot, object fetch or ancestry traversal refuses before staging. A merge published on another remote takes the ordinary landing route on the selected remote, including deliberate branch publication when its intended branch is absent, because published ancestry needs no reconstruction.

Before staging, every unpublished merge reachable from the starting head must be a merge the script made and checked. It retains a checked-commit receipt in Git's common directory before pushing and validates it against the commit and its original reflog transition; commit shape alone never establishes ownership. This includes merges under later commits and on side parents. A proved prior checked merge at the starting head goes to the push-failure route for that existing commit, with no new staging, commit or push. Ordinary one-parent work with only published or proved checked merge ancestors retains its ordinary landing route.

If the script cannot establish that it made and checked an unpublished merge, it refuses without claiming that comparison was necessarily bypassed. Save the starting head on the recovery ref named in the refusal with `git update-ref <recovery-ref> <starting-head>`, and separately preserve pending staged and working content. Backing the merge out to its first parent with `git reset --mixed <first-parent>` removes it and every later commit from the active branch; their objects remain under the recovery ref, while the reset leaves working files and replaces staging. Prepare affected working paths and account for obstructing additions, then redo with `git merge --no-commit --no-ff <recorded-target>`, choose and validate content under the hook-policy boundary below, and run the script. Reapply and validate needed later work from the saved head without the rejected ancestry; rebuild later merges through the script and land ordinary work by naming its paths. Restore saved pending content separately. The script takes back no pre-existing commit; missing or inconsistent evidence authorizes no publication.

What the script's own logic refuses, and why, is below; each refusal is said again on the line where it stops.

- **Broad staging is refused, not just avoided**: name the files or directories. Broad staging committed compiled cache artifacts in tradecraft's own skeleton commit ([30fb484](https://github.com/Grimblaz-and-Friends/tradecraft/commit/30fb48482448ded6f45ccd9a2eb6ddb413bdee10) shipped `__pycache__` files).
- **Unnamed staged paths are refused outside a merge**, and the refusal lists them: silently inheriting someone else's staged changes is how unrelated work ends up in your commit. Named files or directories are staged again from their working files.
- **Unresolved conflicts are refused before staging**: resolve and stage them first, so naming a path cannot silently mark an unresolved merge as resolved.
- **The push goes to the branch's tracked remote**: the upstream remote if configured, the sole remote otherwise; with multiple remotes and no upstream it refuses rather than guessing, because a guess pushes to and then verifies the wrong remote.
- **Uncertain commit identity is refused**: missing, ambiguous or inconsistent reflog evidence, or parents that differ from the recorded start head followed by the recorded merge heads (the start head alone outside a merge), permits neither undo nor push. Git's reflog interface identifies the run's commit under files or reftable storage even after a post-commit hook makes another; repositories with reflogs disabled gain a branch reflog so this guard has trustworthy evidence.
- **Changed committed content is refused before push**: the whole committed tree must equal the saved staged tree, including paths a hook added, because unchecked bytes must not land. The refusal names up to ten changed paths, the count beyond that, the run commit and the saved checked tree. It reports whether the guarded undo restored the original branch and the run's changed index paths, was skipped, or was incomplete; unrelated index entries and flags, including another actor's staged work, survive. Working files retain the hook's output. A changed branch, wrong parent, held index lock, failed index preparation or preservation check, conditional-update failure, or recovery I/O failure prevents a claim of completed undo. If undo was skipped or incomplete, inspect remaining local history and staging before retrying. **For a one-parent commit, running again lands the working files exactly as the hook left them**, so run again only after checking and accepting that rewrite. **A byte-exact file takes the restore route:** if the active hook changes its required bytes, the product's holder must first reconcile that path's hook configuration. Then restore intended paths with `git restore --source=<tree> --worktree -- <paths>`, inspect/remove hook-only additions, validate the restored content and run the script with hooks still in force. Restoring against the unchanged conflicting hook repeats the mismatch; the script offers no bypass. Restore promptly: routine Git cleanup can prune the unreferenced saved tree. `git diff --no-renames --name-only <tree> <commit>` recovers the full changed-path list.
- **A taken-back merge must be restarted:** completed take-back restores the starting branch and run's index paths, but clears merge state. Choose the recovery content first: check and accept the rewrite, or have the product holder reconcile the hook configuration for a byte-exact file. Preserve needed merged bytes, restore merge-touched tracked paths to the recorded start, and inspect/remove additions that obstruct another merge, retaining unrelated edits. Restart with `git merge --no-commit --no-ff <recorded-target>`, then reapply the accepted bytes or, after the hook-policy prerequisite, restore intended paths from the saved checked tree and account for hook-only additions. Resolve and stage conflicts, validate, and run the script with hooks in force. Either route must retain the merge's parents; a plain retry loses ancestry. A saved-tree retry against the unchanged conflicting hook repeats the mismatch. If take-back was skipped or incomplete, inspect reported history/index before choosing recovery; this restart sequence assumes the starting branch was restored.
- **Branch movement before push is refused**: even with equal trees, the symbolic branch and its head must still be the recorded branch and run commit. The push names that commit explicitly so later movement cannot substitute unchecked content.
- **The push is verified, not assumed**: success requires both committed/staged equality and the remote head being that same commit.
- **Force-push does not exist here**: no flag, no environment override. A rejected push is information, not an obstacle.
- **Hooks stay in force**: there is no skip flag or environment override. A rejecting hook still blocks the commit; when formatting conflicts with a byte-exact file, that product's holder owns the hook-configuration change.
- **Detached HEAD, wrong branch, and absent remote branches are refused**: detached HEAD and absent remote branches are unconditional refusals, while `--expect-branch <name>` arms the wrong-branch refusal by naming the intended branch.

## The judgment part — yours

- **What belongs in the commit:** the validated change, plus any findings you fixed inline while making it — and nothing else.
- **The message:** say what changed and why, with enough evidence that a reader can trust it without re-deriving it. A message that would be true of any commit ("fix issues") is too short to be honest — the script enforces only a floor; the standard is yours to meet.
- **When the push fails:** stop and read the reason line — it carries Git's actual error and names the checked local commit. A failed push leaves that commit in place; for a merge, its parents remain in the commit and its in-progress merge state is already gone. Re-running the staging/commit command is not a push-recovery command. Use the existing commit, not another catch-up or a new commit manufactured for the retry. A later invocation whose starting head is that proved checked merge, still unpublished across configured remotes, redirects to this route without staging named pending work or advising back-out/restart. A rejection saying the branch takes no direct pushes or requires a pull request is routing information: branch from the named checked commit, restore the protected branch to its remote, then deliberately publish that branch and verify its remote head is the same commit. Other integration or recovery remains above this skill because a staging tool cannot decide it. Receipt evidence establishes prior checking, not successful publication.
