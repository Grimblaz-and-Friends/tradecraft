# The proof document

**Loaded when** composing, posting, or consuming `tradecraft:proof:v1`, or when running the holder-owned proof and reviewer-readiness commands.

## One document per pull-request head

`run proof` gathers the record again, composes one schema-version-1 object, and creates or updates the authenticated marker producer's pull-request comment for the current head. The holder supplies no body, head, evidence result, staffing value, or bundle identity, because the document is an output of the record rather than another claim about it. A retry rereads comments before deciding whether a write is still needed; documents for older heads stay unchanged, and competing authorized documents at one head are refused.

The command refetches the head, base repository/ref and independently resolved base tip before and after publication. A move before the write requires recomposition; a move during the write leaves the older-identity document in place and does not report current completion. When the effective classification requires no use, the document's `use` object alone carries its current head, classification, applicability and reason. For an affirmed mechanical lane it names the authorized affirmed-comment source and lane exemption even when paths match; otherwise its reason comes from path classification. No compatibility marker is emitted or required. A bought use keeps its source head and original note rather than manufacturing a current-head copy.

The comment begins with:

```text
<!-- tradecraft:proof:v1 head=FULL_HEAD -->
```

It then carries a fenced JSON object followed by a readable rendering of that same object. The JSON schema and interoperability fixtures are shipped beside this reference as `proof-v1.schema.json` and `proof-fixtures/`. Arrays have deterministic order and serialization uses sorted keys, two-space indentation, ASCII escapes and one final line feed, so unchanged evidence produces unchanged content.

## Evidence, declarations, and diagnostics

The object has nine top-level fields: `schema_version`, `identity`, `policy`, `floor`, `use`, `reviewers`, `dispositions`, `declarations`, and `diagnostics`.

- `identity` names the work, repository, issue, pull request, full head and producing plugin version.
- `policy` identifies the work configuration and use-policy path, repository revision and SHA-256 digest used to compose the result. The digest is over the raw Git blob at that revision, not checkout bytes. For these local inputs, proof refuses a present policy with staged, unstaged, untracked, deleted, renamed or conflicted changes and names the commit-or-revert remedy, because the document must describe the policy it used; an optional work configuration absent from both the revision and worktree retains `sha256: unavailable`.
- `floor`, `use`, `reviewers`, and `dispositions` retain public source identities. A source names its kind, repository, numeric or textual identity, URL, author, timestamp and relevant revision without copying the source body.
- `floor.checks` retains the independently selected relevant checks with public check, application, workflow and run identities, head, status, conclusion and timestamps. The floor contract below determines membership; duplicate, omitted, substituted, stale or additional entries fail the gate's independent comparison.
- `use` distinguishes current-head, ancestor, generated and missing evidence. A generated mechanical exemption names its affirmed-comment source and reason. An ancestor use lists every intervening commit and both names of renamed paths; authored runtime edits, including a merge's own edits, make it stale even when later reverted. Base commits and paths brought into a merge from the base buy use through overlap with the pull request's current use-buying changed paths.
- `declarations` carry machine-local dispatch facts: dispatch id, requested settings, observed vendor/model/effort where the runtime exposed them, fallback, staffing and revision. Missing, ambiguous, incompatible, late or contradictory records use `status=unverifiable` and a reason; marker text never fills the missing value.
- `diagnostics` retain missing, invalid, ambiguous, stale or unavailable inputs. No diagnostic is converted into a success boolean.

The producer never writes a `verified` field or line. The readable rendering labels public material `evidence:`, local record material `declared:`, and limitations `diagnostic:`. The gate alone emits `verified:` after independently reading the public records; accessible local execution remains a declaration even when internally consistent.

## Raw-output readiness and proof check

The selected change-proof policy may carry top-level `raw_output_patterns`, an array of nonblank strings, for example `"raw_output_patterns": ["run-output/**"]`. An absent member or empty array declares no patterns and runs no diff check; a malformed member is a policy error naming it and the policy. The default selection is `<adopter-root>/.github/change-proof.json` under the holder root; `--use-rules` replaces it. Ordinary reports and readiness read the selected checkout bytes; proof reads its clean committed snapshot. Readiness snapshots and verifies its selected bytes before effects without requiring a clean or committed policy.

Patterns match repository-relative names with `/` separators through case-sensitive `fnmatch.fnmatchcase`, independent of the platform's filesystem case rules. They match the whole path: `*` can cross `/`, and `**` has no separate globstar behavior. Pattern contents stay literal; there is no implicit exclusion, case folding or content classifier.

For a nonempty declaration, collect every paginated PR file record, require its inventory to agree with a valid `changed_files` count, and reject duplicate current names, unusable names or unrecognized statuses as unverifiable. Ignore `removed` records; check `added`, `modified`, `changed`, `copied`, `unchanged` and both names of `renamed` records. A missing rename source is unverifiable. Renaming out of a declared directory still retains the file and is checked.

Matching paths are deduplicated, sorted and reported whole. Both `run ready-reviewers` and `run proof` refuse at that head before label/ready effects or proof composition/publication/gate reruns, including already-ready PRs and every lane. The holder has the builder remove the named files from the PR change, return their summaries, and reruns the named stage. Insufficient inventory instead names the missing evidence and recollect/retry remedy. Build, floor and reviewer-disposition repairs remain available. The ordinary entrance reports these facts without launching a repair.

Every repository decision report carries `raw_output` with `status`, `message`, `policy`, `patterns` and `paths`: `undeclared` says `No raw-output patterns are declared.`; `not-evaluated` has patterns without an implementing PR inventory; `clear` found no matching non-removal change in a complete inventory; `blocked` names matches; `unverifiable` names a policy or inventory failure. Registration and tree reports inspect the declaration only, without adding policy prerequisites. Missing optional policies on those routes are undeclared; unreadable or malformed present policies are unverifiable.

This state never enters proof JSON, rendering or diagnostics; policy descriptors keep their existing fields and hash the selected committed blob. Freshness composition is skipped when the committed-policy raw check would refuse, so cached proof cannot claim completion. Proof recollects and evaluates again before composition; head/base moves and policy changes still require recollection. The deletion and absence allowances remove only this check, leaving existing prerequisites in force.

A failed PR file read still aborts general collection when no raw-output patterns are declared, because an empty substitute cannot classify owed use or panel evidence. With declared patterns, the entrance retains the failure for the raw-output unverifiable report and refusal.

## Base declaration and applicable floor

The optional `floor` member of schema-version-1 `<adopter-root>/.github/change-proof.json` names every CI job whose red must stop a merge. It carries required `jobs` and optional `stall_after_seconds`, with no other members. Each job has exactly `workflow` and `job`. `workflow` is an exact repository-relative path under the adopter's GitHub Actions workflows directory, ending in `.yml` or `.yaml`; it excludes absolute or drive-prefixed paths, backslashes, control characters, empty or dot components, glob patterns and ref suffixes. `job` is the nonblank, case-sensitive Actions job/check name without control characters, rather than the workflow display name or necessarily the YAML key. Matrix expansions are separate pairs. Duplicate pairs are invalid. The stall bound is a positive integer excluding booleans, defaulting to 3600 seconds. An absent floor or empty jobs list retains the builder floor; a malformed trusted declaration is an error.

Both entrance and gate resolve the pull request base branch to current tip B and read the declaration there, evaluating executions at live head H. Introducing, changing or deleting the declaration at H leaves that pull request under B's prior floor. The holder checkout, head policy, local use-rules override and proof descriptions cannot replace that authority. This does not move the entrance's other policy inputs to B. Confirmed absence and a failed policy read remain distinct; an unreadable declaration is unverifiable. A moved B or H requires recollection.

The entrance emits optional `policy.floor` with the existing policy-source fields `repository`, `path`, `revision` and `sha256`, describing the raw fetched base-tip blob. Confirmed absence is `null`; an unreadable blob omits the descriptor and produces a diagnostic rather than claiming absence. Older v1 documents lacking this descriptor remain structurally valid; the gate always derives authority from its own reads rather than the descriptor.

### Public execution selection

Read complete current-head Actions workflow-run pages, all check-run pages with `filter=all`, and every candidate run by numeric identity. Its repository, head and top-level canonical workflow path must agree. Strip an API ref suffix only for matching that path; workflow display names, addressable IDs, foreign sources and referenced reusable workflows do not substitute. Runs outside the adopter's workflows directory are undeclared. Select the greatest run ID separately per workflow path and triggering event, so a newer push cannot hide a failing pull-request execution.

Read all job pages with `filter=all`; associate each exact declared name to its check by `check_run_url` identity. Require consistent job, attempt, run, check, application, repository and head identities. Construct API endpoints from validated identities, never proof URLs. Within the selected run, the greatest job attempt selects that job's execution. A completed partial rerun can retain an earlier successful job from that same run; a newer run cannot borrow jobs omitted from it. Same-named jobs in a selected attempt remain separate and all must succeed.

An unfinished newer attempt with inconclusive inventory stays pending rather than borrowing earlier green. A queued run without jobs is pending, then stalled at the bound. The current proof gate's own attempt may retain completed tests while its gate job runs; it cannot establish its own floor. For floor exclusion, only a job named `Change proof` or ending ` / Change proof` in a positively identified gate run is the proof execution; other declared jobs in that required workflow remain floor jobs. A terminal-red selected run that omits a declared job still blocks. The existing required-gate identification contract remains unchanged. Unavailable or contradictory identity, association or pagination is unverifiable. A positively undeclared workflow, job or app check is excluded before considering its result; an Actions-app check without a parseable run is excluded only when its exact name is not declared.

### Results, routing and proof evidence

All declared jobs completed with `success` meet the CI floor with no builder resume or floor marker. The document records H, `floor.source: null`, every selected declared check and no local floor-dispatch declaration. Its readable evidence names B's declaration, workflow/job, selected run, attempt and conclusion and explains why no builder floor was needed.

Missing workflow execution, a job absent from a completed successful execution, or `skipped`/`neutral` results owe builder fallback. A builder floor retains the authorized current-head public marker source and local dispatch declaration under their existing limits; the gate verifies the lawful public attestation, not local execution from its prose. Fallback retains every visible selected declared check and diagnoses missing/nonexecuted jobs. Undeclared checks neither meet nor block a declared floor, including fallback; independently owed reviewer receipts and dispositions remain due.

Terminal red (`failure`, `cancelled`, `timed_out`, `action_required`, `startup_failure`, `stale`) blocks and names the execution. The holder determines the cause before choosing a route. For a failure caused by the change, use `run build --dispatch FILE`; once a pull request exists, this resumes the recorded builder. The holder's dispatch carries the failing job's workflow, job, run, attempt and failing log lines. `run floor` cannot clear a declared red. For an external failure, before rerunning, post one comment on the work issue naming the head, workflow, job, run, attempt and why the failure lies outside the change. That is the external route's only rerun; route a red result as a new execution by its cause without another external rerun. For a pull-request-body failure, fix the body: a check whose workflow listens for `pull_request`'s `edited` event runs again on the edit; otherwise rerun that job once after the edit. That rerun belongs to the body route and is separate from the external route's rerun. The ordinary entrance does none of these mutations and repeated reads spend no builder turn or rerun.

Unfinished execution reports pending with job, run and age, or holder-owned stalled at or beyond the bound. Investigate the named stalled runner. The clock uses job/check start when available, otherwise the selected run's creation time before work starts; a rerun uses its attempt start. Invalid or unavailable timing is unverifiable. Unknown completed conclusions are unverifiable. Blocked and unverifiable take precedence over pending or fallback; pending takes precedence over fallback. A builder marker overrides none of those states.

Without a declaration, retain the builder floor and existing complete retained non-gate public-check obligations. If builder evidence is missing, `floor.head` and `floor.source` are null, with relevant visible checks and a diagnostic. Required-gate provenance that cannot be established never becomes a green gate merely because CI met the floor.

The gate consumes only one authorized current-head proof document. Legacy standalone markers, older documents and unauthorized documents supply no current completion; missing proof fails with `run proof` as the remedy. Use qualification, bought use and ancestor applicability retain their existing semantics, and no-use is recorded only in the document's `use` object.

## The shared Actions review identity

`github-actions[bot]` is shared by ordinary workflows, so its receipt must be a submitted, completed pull-request review. Read its run id only from the exact `<!-- connected-review-attempt:RUN_ID -->` marker on the body's last non-blank line, because the reviewer appends it after any findings. GitHub's independently read run must have that id in the same repository, identify `<adopter-root>/.github/workflows/connected-review.yml`, and have the same full head revision as the review's `commit_id`. Its event must be `pull_request_target`, which runs the base branch's copy of the file so a pull request cannot change what ran. The workflow file portion before GitHub's optional `@ref` suffix must match exactly. A completed, successful job named `review`, directly or after nonempty caller names separated by ` / `, in any attempt of that run establishes completion; read all jobs pages with `filter=all`, because an overall failure or a failed later attempt does not undo a posted review.

Missing or malformed trailing run markers, rejected run facts and unreadable evidence grant no credit; collection and proof diagnostics retain the reason, and another qualifying review or a later read can establish the receipt. Ordinary and inline comments from this shared login cannot be receipts. Notices keep their existing handling, inline findings still need dispositions, and other configured reviewers keep their source rules. Run and job facts stay internal: proof still names the actual review as its source, with no new proof or configuration fields.

## Applicable use evidence

A lawful current-head use takes priority over an ancestor use, even when the ancestor note has a later timestamp, because a hand-bought use must become the entrance and proof's evidence. An older passing, unchanged use applies only with proved ancestry and complete intervening history. A commit reachable from the observed base re-buys use only when its first-parent file list touches a use-buying path among the pull request's changed paths at the current head. A merge's first-parent-relative paths split: a path is brought from the base only when another parent is base-reachable and changed that path since the parents' merge base. Those paths use the same overlap rule; every remaining path is the merge's own edit and any use-buying path makes the use stale, because restoring base content can remove an authored edit from the current diff. Renames include both names; deletions count. A file the change touched and later reverted no longer overlaps. Authored non-merge commits retain the per-commit rule, including runtime edits later reverted. When both sides changed a path and the merge resolves it to the base tip's content, it can disappear from the current diff and carry; that residual is outside the bought rule. A use that found something never carries to its repair.

For overlap-judged paths, an ordinary modification of the declared version path is left out only when the first-parent and commit JSON objects are equal after removing that literal top-level member. Modes are not read. Missing, renamed, deleted, unreadable or invalid JSON files grant no exemption; duplicate keys, non-JSON constants and boolean-to-number changes cannot hide another edit. A separate authored version commit still buys use. Catch-up re-bumps inside the merge only when the base side changed the declared file since the parents' merge base; otherwise it retains the change's version. Unavailable merge-side history or an incomplete current pull-request changed-path inventory cannot establish a carry. The entrance reports the evidence, current and observed base heads, current changed paths, incoming paths, overlaps and each merge's `brought_paths` and `own_paths`. Proof preserves the original source and every intervening `{sha, paths}` record; the gate independently derives applicability. Floor and generated no-use evidence remain current-head.


## Publication and gate reruns

Posting proof does not certify readiness and may expose incomplete evidence. The command reads the pull request base branch's active rules and resolves each required workflow's source repository and exact path; it joins a run through the fixed read-only workflow-provenance GraphQL query, sent as a POST, for that run's top-level workflow file. After confirmed publication, it requests one rerun per distinct positively matched current-head run carrying complete run and workflow identities. Pending, stale, absent, `none` and `unidentified` sources perform no speculative rerun and report why; a display name and a called reusable workflow are never matching authority, and submission is never reported as a pass. The returned JSON names the comment action and each source, run identity, request state and observed pending result.

## Reviewer readiness

Before authorizing `run ready-reviewers`, the holder reads the latest build or repair return and accounts for every criterion not carried by CI, obtains every owed builder-executable result and separate holder-launched fresh-reader return, and records the criterion results and seat references it relied on. Missing, unrun, failed or unresolved criteria stop readiness even with green CI. A fresh reader receives the criterion's exact artifact text, capability and built-result inputs through a recorded seat with a distinct stage such as `acceptance-criterion`; the builder neither launches nor judges it. The end-of-turn and repaired-head responsibilities live in the engagement stretch contract.

The endpoint validates the same applicable floor as routing and proof, rechecks B and H, applies `.tradecraft/work.json`'s optional `reviewer_label`, then marks a draft ready and verifies both results. Its floor validation does not certify arbitrary criterion records. On every lane the order is applicable floor and owed criterion results, readiness, reviewer dispositions and any bought panel, required use, then proof. A repair renews the criterion duty before its repaired head is treated as release-ready, even on an already-ready pull request; no draft toggle is required. Readiness requires no use decision because reviewer fixes precede use. Omitted or null label means none is declared. Apply it before the transition so integrations see it. An already-ready pull request can repair a missing label without toggling draft status; repeating after a partial failure completes the remaining operation.

Neither holder-owned command launches an agent, repairs the implementation, or advances another stage. The ordinary entrance waits for every configured reviewer separately and treats a review-limit, rate-limit, skipped, limited, upgrade or running notice as not reviewed. Before recommending proof or release it requires authorized dispositions for inline threads, identified body findings and unidentified reviews under the connected-reviewer answer contract, even when a prior proof exists or a legacy gate is green. An explicit proof publication may expose missing body answers through the existing diagnostic code, message and source fields; `dispositions` remains the inline-thread records and no proof field is added. Body identities grant no reviewer-run credit. A failed or pending gate evaluation then waits; it never routes back to the executable floor.
