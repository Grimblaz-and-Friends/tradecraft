# Launch findings

**Loaded when** the entrance holds a change on `launch-findings-unaccounted`, its report's `launch_findings` names a held bundle, or the holder quotes a Claude launch's write bound in a release report.

A Claude author or builder can write, and so can a use consumer given a shell. Exactly these launches are bound: local Claude author and builder launches, and the Claude use consumer given a shell. Other Claude seats given a shell are not compared, and Codex launches are unchanged. Its file-editing tools (Write, Edit, MultiEdit and NotebookEdit) are confined by a launch-owned check on each target path: a target outside its tree and its own session scratchpad is refused, names the path and fails the turn. Memory is switched off in its process environment, and a file-tool write to the memory store is refused regardless, because the store lies outside both. A helper call that asks for its own working copy is refused the same way, by its `isolation` value, by a definition that sets one, or because its type is unknown, and so is every `EnterWorktree` call; the launch's own instruction file tells the recipient to keep helpers in its tree. Shell commands have no OS fence on this route. So each of those launches also compares what it must not touch before and after its run, because a shell write lands and can only be found afterwards.

## What the comparison covers

- the machine implementer switch and the model rulings file;
- the owner's Claude settings, the owner's always-loaded `CLAUDE.md` and the installed plugins;
- the implementation worktree registry, the dispatch store's completed run records and the run's own request record;
- every checkout an active registration names, holder checkouts included, each registered repository's main clone, and the launcher's own plugin root when no covered checkout is that root.
- each covered repository's working copies and local branches, with each one's tip: the run's own repository and every covered checkout's.

A checkout's comparison leaves out its `.git` and stops at any nested worktree or clone, because every builder edits its own nested tree and commits into the shared `.git`. Edits inside the run's own tree are its own work. A change under the tree of another recorded run whose launch window overlapped this one is that run's, and a registry row naming another holder's session is that holder's only while a recorded run of theirs for that row's work or tree overlapped. Attributed changes stay visible under `attributed`.

**Working copies and branches.** The tree walk stops at nested copies, so the `refs` items compare each repository's copy list and local branches instead; a root outside any repository is recorded `not-a-repository`. Only the copy at the run's root and its checked-out branch are the run's own. A copy or branch that is new, gone or moved holds only when the run's own record names it in a tool call's input, by the recipient or a helper: a branch by its whole name or as the last part of a path, as `git worktree add ../x` names branch `x`; a copy by a path at or inside its top in no deeper copy, a quoted or escaped path read whole, absolute or relative to a directory that agent started in or named with `cd`, `pushd`, `Set-Location` or `git -C`. A branch checked out at a changed copy is folded into that copy's entry, so one account covers both. Every other change is only `listed`, and so are the default branch's own entry and a copy whose only change is a default-branch tip, even when the record can't be read. Where a remote has no `HEAD`, no default branch is identified and nothing is exempt; a record that can't be read holds every other entry. An item that could not be read or walked in time is an `uncompared` finding, because silence about it could hide damage.

The request's `write_bound` states what applied: the guarded tools and allowed paths, the scratchpad form, the guard's self-test, the memory request and fallback, the planned coverage, and `shell: no OS fence`. The run record's `launch_comparison` carries each item's status and every finding with its `id`; an author's or builder's run record also carries `write_guard` (refusals, calls completed with no guard decision, and calls the runtime rejected before they ran). Quote that bound in the release report.

**A cloud build is not compared.** A cloud builder runs on a remote machine and cannot reach this one, so its run record's comparison reads `cloud-not-run` with that reason, a clear status that holds nothing; a local build still runs its comparison. The work cell's cloud-builds reference owns the route.

## The hold

Any bundle for this change whose comparison has findings, or whose request has a write-bound baseline but whose stopped launch left no comparison (`unrecorded`), holds every next stage, the holder-named `run <stage>` included. A launch still running owes no account: its report entry reads `running`, because its comparison is written when it stops, and the live-launch routing governs it meanwhile. The run itself is untouched: a finding never fails or discards it.

**A failed cloud attempt check holds the same way.** A cloud attempt whose change-branch check, `[skip ci]` check, practice-check record, `environment` check, permission-mode check or local-tree check failed carries a `cloud-check:<name>` finding, and its account names that id with the `cloud-check` party, whose basis names the check and what the holder verified, except the local-tree check: only the local tree containing the returned branch tip releases it, never an account, because the next stage builds from that tree. The report is still kept and posted.

The hold releases once the `launch-account` comments that count for that bundle name, together, every one of its finding ids (the `launch-account` contract in `markers.md`). A comment counts when a trusted marker producer posted it as an issue comment, it is well formed, its `dispatch` is that bundle's, it was posted after the bundle's findings existed, and every id it names is one that launch flagged. A comment naming any id the launch didn't flag counts for nothing, the rest of what it names included, because it was most likely written for another launch. An account posted before the run completed, or for an unrecorded comparison before the launch began, counts for nothing. One comment naming every finding still releases on its own. Where two counting comments name one finding, the one posted later governs it; editing a comment doesn't change when it was posted. Within one comment each id appears once, or that comment counts for nothing. Nothing posted after the hold releases puts it back on hold.

While a bundle is held, its `launch_findings` entry lists in `owed` the findings no counting comment names yet, a failed local-tree check among them until the tree contains the returned tip, whatever names it. Its `uncounted` lists each `launch-account` comment that concerns that launch but doesn't count, with its reason: `untrusted-author`, `wrong-surface`, `malformed`, `another-launch`, `before-findings` or `names-unflagged`. A comment for another launch concerns this one only when it names one of this launch's findings. Its `accounts` names the comments that count, and `governing` names, for each finding more than one of them names, the comment that governs it. `findings` still lists everything the launch flagged.

Name each finding's party by what made the change, from what you know, never by default:

- `owner` — the owner changed it;
- `plugin-update` — the runtime's plugin machinery changed it: an installed plugin, a marketplace, or the runtime's cached plugin or marketplace data was installed, updated or refreshed. This holds whether another process did it or the launched runtime itself did, while starting or running, as long as no tool call or command the launched recipient made did. The `basis` says what shows that, such as the change's timing against the launch's session start and a stream with no tool call that touched it;
- `session` — another named session changed it; give its id in `session`;
- `builder-damage` — a tool call or command the launched recipient (the builder, author or use consumer) made changed it. The launched runtime's own plugin maintenance is not builder damage;
- `none-found` — you inspected what the finding names and found no change needing a party; the `basis` says what you inspected and how.

An `uncompared` finding or an `unrecorded` comparison is not a change anyone made, so inspect before naming a party. For `uncompared`, inspect the item it names; for `unrecorded`, inspect every item in the request's `write_bound.comparison.coverage`. When that coverage is empty because planning it failed, inspect what "What the comparison covers" above lists on this machine, and say so in `basis`. When the inspection finds nothing, `none-found` is the true party; when it finds a change, name the party that made it instead, and builder damage still goes to the owner and the practice.

For builder damage, tell the owner first. A notice the owner will see counts, such as an issue comment addressed to them while they are away; the account does not wait for the owner's restore decision, which stays theirs. Then file the practice's `product-incident` record as the charter directs for a practice failure. The account names both: `owner_report` is the notice's URL, or another exact locator where the notice is not on GitHub, and `practice_issue` is the filing. **Leftover copies and branches are the owner's to remove.** Never remove a working copy or branch a finding or `listed` entry names. Name each leftover by its path, branch and tip in the launch account's `basis` and in the release report's owner-decision section, for the owner's cleanup. A helper's copy is `builder-damage`; another session's is `session`.

A bundle recorded before this bound neither holds nor clears; the report says `not recorded: launched before #906`.

## An account in parts

GitHub refuses an issue comment over 262,144 bytes of UTF-8. Its refusal message says the maximum is 65,536 characters; that figure is wrong, and comments well past it are accepted, so measure the body in bytes rather than trusting the message. An account of a few thousand findings outgrows one comment. Post it as several comments, each carrying the marker with that bundle's `dispatch` and its own fenced object naming part of the findings, each under the limit. After each post, read the entrance's report: `owed` shows what is left to name, and `uncounted` shows why a comment you posted didn't count. To correct an entry, post a new comment naming that finding with its right party; the later naming governs. Never edit or delete an earlier account comment: an edit doesn't change which comment governs, and the record stays append-only.
