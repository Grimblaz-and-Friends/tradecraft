# Launch findings

**Loaded when** the entrance holds a change on `launch-findings-unaccounted`, its report's `launch_findings` names a held bundle, or the holder quotes a Claude launch's write bound in a release report.

A Claude author or builder can write, and so can a use consumer given a shell. Exactly these launches are bound: local Claude author and builder launches, and the Claude use consumer given a shell. Other Claude seats given a shell are not compared, and Codex launches are unchanged. Its file-editing tools (Write, Edit, MultiEdit and NotebookEdit) are confined by a launch-owned check on each target path: a target outside its tree and its own session scratchpad is refused, names the path and fails the turn, except in a `stretch` launch, where the refusal is recorded and the turn goes on; a file-tool call that completed with no guard decision fails a `stretch` turn too. Memory is switched off in its process environment, and a file-tool write to the memory store is refused regardless, because the store lies outside both. A helper call that asks for its own working copy is refused the same way, by its `isolation` value, by a definition that sets one, or because its type is unknown, and so is every `EnterWorktree` call; the launch's own instruction file tells the recipient to keep helpers in its tree. Shell commands have no OS fence on this route. So each of those launches also compares what it must not touch before and after its run, because a shell write lands and can only be found afterwards.

## What the comparison covers

- the machine implementer switch and the model rulings file;
- the owner's Claude settings, the owner's always-loaded `CLAUDE.md` and the installed plugins;
- the implementation worktree registry, the dispatch store's completed run records and the run's own request record;
- a `stretch` launch's own pointer under the store's `stretch-launches/`, as `own-pointer`, so a pointer removed or rewritten during the launch is a finding;
- every checkout an active registration names, holder checkouts included, each registered repository's main clone, and the launcher's own plugin root when no covered checkout is that root.
- each covered repository's working copies and local branches, with each one's tip: the run's own repository and every covered checkout's.

A checkout's comparison leaves out its `.git` and stops at any nested worktree or clone, because every builder edits its own nested tree and commits into the shared `.git`. Edits inside the run's own tree are its own work. A change under the tree of another recorded run whose launch window overlapped this one is that run's, and a registry row naming another holder's session is that holder's only while a recorded run of theirs for that row's work or tree overlapped. Attributed changes stay visible under `attributed`.

**Working copies and branches.** The tree walk stops at nested copies, so the `refs` items compare each repository's copy list and local branches instead; a root outside any repository is recorded `not-a-repository`. Only the copy at the run's root and its checked-out branch are the run's own. A copy or branch that is new, gone or moved holds only when the run's own record names it in a tool call's input, by the recipient or a helper: a branch by its whole name or as the last part of a path, as `git worktree add ../x` names branch `x`; a copy by a path at or inside its top in no deeper copy, a quoted or escaped path read whole, absolute or relative to a directory that agent started in or named with `cd`, `pushd`, `Set-Location` or `git -C`. A branch checked out at a changed copy is folded into that copy's entry, so one account covers both. Every other change is only `listed`, and so are the default branch's own entry and a copy whose only change is a default-branch tip, even when the record can't be read. Where a remote has no `HEAD`, no default branch is identified and nothing is exempt; a record that can't be read holds every other entry. An item that could not be read or walked in time is an `uncompared` finding, because silence about it could hide damage. So is an item whose changes could not all be compared in the time the launch allows after its walk: two minutes, or less when the stage's limit is close, as it is after a recipient stops at its ceiling. Its reason says the allowance ran out and how many of that item's changes were examined, and the findings and attributions made before then stay.

The request's `write_bound` states what applied: the guarded tools and allowed paths, the scratchpad form, the guard's self-test, the memory request and fallback, the planned coverage, and `shell: no OS fence`. The run record's `launch_comparison` carries each item's status and every finding with its `id`; an author's or builder's run record also carries `write_guard` (refusals, calls completed with no guard decision, and calls the runtime rejected before they ran). Quote that bound in the release report.

**A cloud build is not compared.** A cloud builder runs on a remote machine and cannot reach this one, so its run record's comparison reads `cloud-not-run` with that reason, a clear status that holds nothing; a local build still runs its comparison. The work cell's cloud-builds reference owns the route.

## What releases

Some changes to the installed plugins are the runtime's own work: any session's runtime, the app, or any Python process that imports a plugin makes them at moments no launch controls. A change of one of these kinds is **released** whoever made it, the launched session's own commands included, because a change's timing can't tell the runtime's work from the launch's. It is not a finding, holds no stage and owes no account, and the run record's `launch_comparison.released` lists it with its `id`, `item`, `path`, `change` and `kind`, beside `findings` and `attributed`, so you can still see what changed. The entrance's `implementer_environments` repeats each launch's comparison, `released` included. Releasing applies to two items only: the plugins folder (`plugins`), and the launcher's own plugin root (`launcher-plugin`), which is compared when no registered checkout is that root.

| Kind | What changed | Where it releases |
|---|---|---|
| `bytecode` | a `__pycache__` folder, or a `.pyc` file directly in one that was removed or whose header marks it as a kind Python checks against its source: one carrying its source's time and size, which is what an import writes, or its source's hash with checking on. Python rebuilds such a file when its source differs. One Python won't check holds (below). | anywhere in either item |
| `synced-marketplaces` | a `synced` folder at the plugins folder's top, or anything under it: the app's synced marketplace list | the plugins folder |
| `in-use-marker` | a `.in_use` folder or a file directly in it, or a `.last_inuse_sweep` file, at any depth: the runtime marks a plugin version in use and sweeps the marks | either item |
| `orphan-marker` | a `.orphaned_at` file at any depth: the runtime marks a retired plugin version. One added or changed at the top of a version an install entry still names holds (below). | either item |
| `usage-queue` | `store/` at the plugins folder's top, or a `.json` file directly in it: the plugin store's usage queue | the plugins folder |
| `catalog-cache` | a file at the plugins folder's top named `plugin-directory-cache…json`: a catalog of what could be installed, not of what loads | the plugins folder |
| `version-folder` | a whole version folder, `cache/<marketplace>/<plugin>/<version>`, added or removed during the launch, with everything in it: installing a new version and retiring the old one is the runtime's update. A removed one holds while an install entry still names it (below). | either item, so a launcher running from a retired version releases too |
| `install-record` | an install record whose listed fields didn't change, or that moved a plugin to a version folder added in the same launch (below) | the plugins folder |
| `marketplace-refresh` | a change in a marketplace's clone, `marketplaces/<name>` or anything in it, while that marketplace's `lastUpdated` in `known_marketplaces.json` moved: the app refreshed it | the plugins folder |

Where two kinds fit one change, the first in the table names it.

**The two install records are read by what they say.** `known_marketplaces.json` and `installed_plugins.json` decide which plugin code every later session loads and where its updates come from, so they are the only files the comparison reads the contents of; every other file is compared by size and time, or by digest. Only these fields are compared: in `known_marketplaces.json`, which marketplaces there are and each one's `source` and `installLocation`; in `installed_plugins.json`, which plugin keys there are and each key's entries as `scope`, `projectPath`, `installPath` and `version`. A change that leaves those alone, such as a time field (`lastUpdated`, `installedAt`) or the file's own `version`, releases with the basis `no listed field changed`. A plugin update releases with the basis `update to <path>`: the only differences are entries whose `version` and `installPath` both moved, each to a version folder of that same plugin that the same launch added.

**What still holds** in those items, because each could change what code runs:

- a file added, removed or changed inside a version folder that was there before and after, unless a kind in the table names it, such as bytecode in its `__pycache__` or a marker in its `.in_use`: editing an installed version in place is never the runtime's work;
- a plugin's or a marketplace's own folder (`cache/<marketplace>/<plugin>` or `cache/<marketplace>`) added or removed, even where the version folder inside it releases;
- a version folder removed while any entry in `installed_plugins.json`, read after the launch, still names it as its `installPath`, with every file in it that no kind in the table names, because the app retires a version only once no entry names it, so this takes an installed plugin away. Its in-use markers and compiled files still release under their own kinds. Each finding's `reason` names the version folder and the plugin key, scope and project of an entry that names it. Where `installed_plugins.json` can't be read after the launch, every removed version folder holds, because nothing shows no entry names it, and the `reason` says which reading failed and why;
- a `.orphaned_at` file added or changed at the top of a version an entry in `installed_plugins.json` still names, because the app marks only a version no entry names. Its `reason` names the version folder and the entry. Where `installed_plugins.json` can't be read after the launch, one at the top of any version folder holds;
- a `.pyc` file added or changed directly in a `__pycache__` folder whose header marks it as one Python loads without checking it against its source (a hash with checking off, which an import never writes: a compile step has to ask for it), whose header carries flags Python refuses, or whose header can't be read, such as a file shorter than the 16 bytes a header takes. Its `reason` says which: that Python loads it without checking it against its source, that Python refuses its flags, or that its header could not be read and why;
- a `.pyc` file anywhere but directly in a `__pycache__` folder, because it can load with no source to check it against, except inside a version folder added whole during the launch, where it releases as `version-folder` with the rest of that folder: a version folder no entry names loads nothing, and a newly installed plugin's own folder holds anyway;
- an install entry moved into another plugin's version folder, even one the launch added;
- an upkeep name in another place, such as `store/sub/x.json` or `cache/<marketplace>/synced/x.json`;
- an install record added, removed, unreadable before or after, or anything but a regular file, such as a link; a marketplace added or removed, or its `source` or `installLocation` changed; a plugin key or entry added or removed, or an entry's `scope` or `projectPath` changed; a `version` or `installPath` moved to a path no update in the launch added;
- a change in a marketplace's clone while that marketplace's `lastUpdated` stayed put;
- anything else in the plugins folder, a plugin's own data folder (`data/…`) included, because a plugin's code reads what it keeps there, so a write there can change what the plugin does, as a marker, a queue or a cache cannot.

The three holds on a named version and a compiled file don't reach inside an update's new version folder: one added during the launch that an existing install entry of that same plugin moved to, as the `install-record` basis `update to <path>` names it. Everything in it releases with the update. A newly installed plugin's first version folder, or an added version folder no entry moved to, is not an update's, so those holds apply there.

**What a clear launch does not prove.** The comparison sees the installed plugins before and after a launch, not who wrote to them. So five changes release although a launch's own commands can make them, and only a fence on what a launch can write would stop them; the comparison is not one.

- **A plugin update the launch made itself.** A new version folder for a plugin, with that plugin's install entry moved to it, releases as `version-folder` and `install-record`, exactly as the app's own update does. Every later session then loads that folder's code.
- **Anything inside that new version folder,** compiled files and markers included, whatever they are. Later sessions load it with the update.
- **A marketplace's clone edited while its `lastUpdated` moves** releases as `marketplace-refresh`. Later installs and updates from that marketplace take what the clone holds.
- **A compiled file made to carry its source's time and size** releases as `bytecode`, because Python takes it for that source's own. Every later session that imports the module runs it.
- **A version no install entry names, removed while a running session still uses it,** releases as `version-folder`, as the app's retirement of an old version does. The sessions running from it lose its files at once. An in-use marker names its process inside the file, which the comparison doesn't read, so a marker left behind by a finished session looks the same as a live one.

The run record's `released` lists each of these under its kind, so a holder with reason to doubt a clear launch reads them there. A change the comparison never sees reads clear too, and is listed nowhere: a file in a compared folder rewritten with its size and modified time kept, because every such file but the two install records is compared by those alone, and anything inside a `.git` folder, which the walk leaves out (below).

Released changes are not findings, so a `launch-account` never names a released `id`: an account naming an id the launch didn't flag counts for nothing. The plugins folder's walk leaves out every `.git`, a marketplace clone's included, so a change inside one is neither held nor released. A held install-record finding's `reason` names each listed field that changed, by marketplace or plugin key, with its value before and after, or which reading couldn't be parsed and why. Name that change in your account, never a time stamp. Nothing outside those two items releases: a compiled file in a registered checkout's `__pycache__`, and every change to a checkout, the registry, the dispatch records or the run's own records, still holds, because a write into a change's tree or the practice's own records is what the comparison exists to catch, and no session's runtime keeps files up there. A launch recorded before releases existed has no `released` list; it keeps its findings and its hold until an account counts, and nothing rereads it under these rules, because such a record keeps no install record's contents, so a reread would release some of its findings and not others.

## The hold

Any bundle for this change whose comparison has findings, or whose request has a write-bound baseline but whose stopped launch left no comparison (`unrecorded`), holds every next stage, the holder-named `run <stage>` included. A launch still running owes no account: its report entry reads `running`, because its comparison is written when it stops, and the live-launch routing governs it meanwhile. The run itself is untouched: a finding never fails or discards it.

**A failed cloud attempt check holds the same way.** A cloud attempt whose change-branch check, `[skip ci]` check, practice-check record, `environment` check, permission-mode check or local-tree check failed carries a `cloud-check:<name>` finding, and its account names that id with the `cloud-check` party, whose basis names the check and what the holder verified, except the local-tree check: only the local tree containing the returned branch tip releases it, never an account, because the next stage builds from that tree. The report is still kept and posted.

The hold releases once the `launch-account` comments that count for that bundle name, together, every one of its finding ids (the `launch-account` contract in `markers.md`). A comment counts when a trusted marker producer posted it as an issue comment, it is well formed, its `dispatch` is that bundle's, it was posted after the bundle's findings existed, and every id it names is one that launch flagged. A comment naming any id the launch didn't flag counts for nothing, the rest of what it names included, because it was most likely written for another launch. An account posted before the run completed, or for an unrecorded comparison before the launch began, counts for nothing. One comment naming every finding still releases on its own. Where two counting comments name one finding, the one posted later governs it; editing a comment doesn't change when it was posted. Within one comment each id appears once, or that comment counts for nothing. Nothing posted after the hold releases puts it back on hold.

While a bundle is held, its `launch_findings` entry lists in `owed` the findings no counting comment names yet, a failed local-tree check among them until the tree contains the returned tip, whatever names it. Its `uncounted` lists each `launch-account` comment that concerns that launch but doesn't count, with its reason: `untrusted-author`, `wrong-surface`, `malformed`, `another-launch`, `before-findings` or `names-unflagged`. A comment for another launch concerns this one only when it names one of this launch's findings. Its `accounts` names the comments that count, and `governing` names, for each finding more than one of them names, the comment that governs it. `findings` still lists everything the launch flagged.

Name each finding's party by what made the change, from what you know, never by default:

- `owner` — the owner changed it;
- `plugin-update` — the runtime's plugin machinery changed it: an installed plugin, a marketplace, or the runtime's cached plugin or marketplace data was installed, updated or refreshed. This holds whether another process did it or the launched runtime itself did, while starting or running, as long as no tool call or command the launched recipient made did. The `basis` says what shows that, such as the change's timing against the launch's session start and a stream with no tool call that touched it;
- `session` — another named session changed it; give its id in `session`;
- `builder-damage` — a tool call or command the launched recipient (the builder, author or use consumer) made changed it. The launched runtime's own plugin maintenance is not builder damage;
- `none-found` — you inspected what the finding names and found no change needing a party; the `basis` says what you inspected and how.

An `uncompared` finding or an `unrecorded` comparison is not a change anyone made, so inspect before naming a party. For `uncompared`, inspect the item it names; for `unrecorded`, inspect every item in the request's `write_bound.comparison.coverage`. When that coverage is empty because planning it failed, inspect what "What the comparison covers" above lists on this machine, and say so in `basis`. When the inspection finds nothing, `none-found` is the true party; when it finds a change, name the party that made it instead, and builder damage still goes to the owner and the practice.

For builder damage, tell the owner first. A notice the owner will see counts, such as an issue comment addressed to them while they are away; the account does not wait for the owner's restore decision, which stays theirs. Then file the practice's `product-incident` record as the charter directs for a practice failure. The account names both: `owner_report` is the notice's URL, or another exact locator where the notice is not on GitHub, and `practice_issue` is the filing. **Leftover copies and branches are the owner's to remove.** Never remove a working copy or branch a finding or `listed` entry names. Name each leftover by its path, branch and tip in the launch account's `basis` and in the release report's owner-decision section, for the owner's cleanup. A helper's copy is `builder-damage`; another session's is `session`.

A bundle recorded before this bound neither holds nor clears; the report says `not recorded: launched before #906`.

## An account in parts

GitHub refuses an issue comment over 262,144 bytes of UTF-8. Its refusal message says the maximum is 65,536 characters; that figure is wrong, and comments well past it are accepted, so measure the body in bytes rather than trusting the message. An account of a few thousand findings outgrows one comment. Post it as several comments, each carrying the marker with that bundle's `dispatch` and its own fenced object naming part of the findings, each under the limit. After each post, read the entrance's report: `owed` shows what is left to name, and `uncounted` shows why a comment you posted didn't count. To correct an entry, post a new comment naming that finding with its right party; the later naming governs. Never edit or delete an earlier account comment: an edit doesn't change which comment governs, and the record stays append-only.
