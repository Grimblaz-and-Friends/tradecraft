# work

**Purpose:** let one holder inspect a change without mutation, explicitly run the stage it names, and build a verified consumer tree through the same door. **Audience:** the holder deciding or continuing an affirmed product change. **Success:** the ordinary invocation reports the evidence and recommended next step read-only; `run STAGE` validates and performs exactly that stage; `tree` builds the declared consumer tree; `release` and `adopt` retain their registration behavior; and no recipient continues into another stage.

## Where this cell's depth lives

- **Recording or reading evidence that advances the entrance** → `references/markers.md`: each marker's exact form, lawful values, producer, surface and moment.
- **Composing or consuming proof, preserving ancestor use, or preparing reviewers** → `references/proof.md`: the proof wire contract, public/declaration split, publication behavior and holder-owned commands.
- **Reading launch settings or writing a machine ruling** → `references/launch-settings.md`: resolved values, historical sessions, bridge schema, precedence and lapse.
- **Implementing the independent proof consumer** → `references/proof-fixtures/README.md`: the positive document and semantic rejection cases shared with the gate.

For the ordinary entrance, run:

```text
python <plugin-root>/lib/work.py --repo OWNER/REPO --issue N --root HOLDER_PATH
```

The fifth merge across the practice's repositories since the last cross-change note, or the status read of a running evaluation, calls for engagement's read across landed changes.

In this repository, `<plugin-root>` is the repository checkout root. For an adopter, it is the installed plugin directory containing `lib/work.py`. `--root` is always the holder checkout's repository top level: it supplies `.tradecraft/work.json` and the use rules at `<root>/.github/change-proof.json`, and anchors the registered implementation root, but is never itself the implementation root.

Without `--use-rules`, the entrance reads that change-proof policy and refuses if it is absent. Use `--use-rules PATH` to select another rules file for that run, including during repository setup. A relative path resolves against `--root`; an absolute path selects that path, subject to the command's existing policy checks.

## Decide, then run on the holder's word

The ordinary entrance performs GitHub GETs plus, when an open pull request has Actions checks, the fixed read-only workflow-provenance GraphQL query sent as a POST; it performs no GitHub mutation. It reads local state but does not sweep or write the registry, create a directory or worktree, publish a branch, write a dispatch file or invoke a launcher. Its JSON report carries the schema version, `work`, `producer_version`, next stage, continuity, reason, detail, holder/runnable/waiting/terminal status, lawful and invalid marker claims, and the latest run selected for every exact check name and producer workflow. For checks, `started_at` and then numeric check id choose a genuine workflow's latest run; two workflows sharing a display name remain separate.

The required gate is every workflow required by the pull request base branch's active rules, matched to an Actions run by its top-level source repository and exact path. A display name, target-repository workflow id, reusable-workflow reference or work-configuration field never identifies it, because each can name a local copy instead. A successfully read rule set with no workflow requirement is `none`; unreadable rules or unresolved source provenance are `unidentified` and never count as green. With identified requirements, a check resolved to another source remains ordinary even when its display name is shared, while an Actions check with unresolved provenance waits under `unidentified`. With unreadable rules, every Actions run could be the gate, so a red or pending Actions result also waits under `unidentified` instead of routing to the floor.

An implementing pull request counts only through its own standalone closing reference or the issue's lawful `implementing-pr` marker. While the issue is open, an open candidate wins over every merged candidate because it is the change in flight. With no open candidate, one merged candidate returns a holder-owned state naming that pull request; it is neither a fresh build nor terminal. Multiple candidates in the winning class are refused, and a closed unmerged pull request does not count. A nonempty product list in `.tradecraft/work.json` makes the repository's issues practice-facing and requires a listed product incident unless an affirmed brief has already admitted the work; a missing or empty list disables that check because the practice exists to serve product work. The same file names connected-reviewer and marker-producer logins, so other accounts cannot satisfy review or advance the entrance; the shared `github-actions[bot]` login also needs the run provenance in `references/proof.md`. Where no connected reviewer is configured, no connected review is required.

An affirmed brief counts only with exactly one lawful `Review risk` and `Review lane` pair. `ordinary` / `mechanical` is the owner-affirmed exemption: the entrance proceeds to build without an artifact, cold verdict or holder reading, and classifies use as not required regardless of changed paths. Every other lane matches changed paths against the schema-versioned use rules. A bought use requires a current-head use note or a proved ancestor use whose authored intervening edits buy no use and whose base commits and paths brought into merges overlap none of the pull request's current use-buying changed paths. A merge path is brought in only when another parent is base-reachable and changed that path since the parents' merge base; remaining paths are the merge's own edits, because an authored restore can disappear from the current diff. Either not-required branch records its current-head decision and reason in the proof document's `use` section. Missing, mismatched, duplicated, draft or unauthorized lane text grants no exemption.

The floor policy is read independently from the pull request base branch's resolved current tip, never from the holder checkout or a use-rules override. The report names that base, the declared workflow/job pairs and their selected executions. Declared green jobs at the head need no floor marker or builder resume. Missing, skipped or neutral executions retain the builder floor. A declared red, stalled or unverifiable floor is holder-owned; follow the cause-based routing and procedures in `references/proof.md`. Pending jobs name their public execution and stall timing. Undeclared checks cannot block a declared floor. The declaration, selection and proof contract is `references/proof.md`.

Run a stage only when the holder says to:

```text
python <plugin-root>/lib/work.py run STAGE \
  --repo OWNER/REPO --issue N --root HOLDER_PATH \
  --holder-session-id ID [--dispatch FILE] [--timeout-seconds N] \
  [--claude PATH] [--codex PATH] [--handover-recovery-session UUID] \
  [--budget-override-reason TEXT]
```

`STAGE` is `artifact`, `cold-seat`, `build`, `floor`, `use`, `review-disposition`, `proof`, `ready-reviewers`, `release-report` or `catch-up`. The named stage is authority: `run` validates and performs exactly it, without requiring it to equal the recommendation or advancing after the return. The nominal caller limit defaults to 7200 seconds for `build` and 3600 seconds for other stages. `--timeout-seconds` declares the limit the holder runtime actually applies, including a tool default; it must be finite and positive. One deadline covers entrance preflight, launch, fallback, stopping and recording. The cleanup reserve is the smaller of 60 seconds and the larger of 10 seconds or one tenth of the caller limit, because stopping and recording need time even at a short limit. An undeclared build begins stopping by 7140 seconds. A run with no useful launch window returns to the holder. `--holder-session-id` is required when an implementer is launched or resumed; pass the runtime's session identifier, or a stable holder token when it exposes none, so launcher and registry keep holder and builder identities distinct. A holder-supplied artifact dispatch must ask for the whole artifact in the final message, opening with the affirmed brief, because the stage checks for it. A holder-supplied dispatch must be outside the registered implementation root and reaches the launcher byte-for-byte; otherwise the composed implementer prompt carries one-stage bounds, the exact affirmed brief, the latest artifact where the lane owes one, compact stage facts and explicit `gh api --method GET` commands, never the issue or pull-request record.

`run artifact` looks for the affirmed brief anywhere in the return, allowing a preamble, artifact marker or heading before it. Comparison removes blockquote prefixes and HTML comments, including the optional affirmed-brief marker, and collapses whitespace. It accepts 98% character similarity or at most four character edits, so one mis-encoded character also passes in a short brief. After the brief it requires at least eight alphabetic words of two or more letters, excluding heading lines and lines containing paths, links or file-retrieval instructions; a brief alone or with only a location tail fails. Exact fidelity before posting remains the holder's job. A failed return says what the check looked for and names its durable bundle and observed author session, or states that identity is unavailable. The stage never retries. Repeating `run artifact` resumes a failed return only when the latest artifact bundle completed after the current affirmed brief or amendment; the resume route refuses an unproved session. Otherwise the recommendation's continuity governs, so a new term starts fresh.

A composed `run floor` requires `--floor-command TEXT`, the exact command the holder selects from the repository's check instructions or settled artifact. The entrance names it verbatim and asks the builder to return the tested head, command, output, result and passing floor marker for the holder to post; a failed command returns no passing line. A missing command is a holder-owned refusal before launch. A holder-supplied dispatch remains byte-for-byte and must itself name that command and returned marker. An explicit authorized floor stage remains lawful when ordinary routing already accepts CI.

`--handover-recovery-session` is for an unresolved handover with no retained native session result. The refusal names its bundle and reserved UUID. The holder inspects Claude's saved session for that exact UUID; if it exists, repeat the same `run STAGE` command with `--handover-recovery-session UUID` to resume and record it. If it does not exist, return the unresolved bundle and UUID to the owner; do not start another replacement. The option never creates a session.

When an explicit artifact stage follows an amendment and the current term has no draft, its prompt carries the latest artifact text from any earlier term as the artifact under revision: that term's latest settlement even when its route is invalid, otherwise its latest draft. It follows the artifact with the latest holder reading made against it in the same term, labelled as governing where it differs, because revision must start from the whole text and judgment that produced it. An intervening term with no artifact changes neither; a newer artifact without a reading clears the older reading; and a current-term draft replaces both prior-term sections.

Every decision and dispatch request records `work` and the producing plugin version. Before any registry mutation, branch publication, temporary root or launch, `run` checks the named stage's safety table. A refusal names the stage, found version, minimum version and missing mechanism. A resumed stage selects its matching bundle and valid session together and checks that bundle's version; matching bundle evidence with no session, an unsupported schema, or an unsafe or unstamped version refuses. Only when no matching bundle exists may the authorized `builder-session` marker supply continuity.

Marker claims are classified once per source before validation: quoted markers never claim, an ordinary source claims the marker it opens with and only that contract's companions, and a reviewer-thread disposition carries `connected-reviewer`. The entrance reports every set-aside quotation with its source. Claims that remain are validated before they advance the decision: producer, surface, exact attributes, lawful values, required prose and unambiguous identity must hold. Claims produced by a dispatched stage must also agree with the latest matching successful bundle completed before the marker. Builder session, floor head and pass, and cold/use staffing therefore come from their run records rather than from marker text alone. The exact source-reading, travels-with and marker contracts remain in `references/markers.md`.

For a non-mechanical lane, the entrance reduces the artifact claims after the latest affirmed brief or amendment in record order. A settlement names the route its current-term verdicts support; a newer draft reopens the phase; and a holder reading counts only after the latest effective settlement. A one-time routed re-post may inherit an earlier routeless settlement's position under the migration rule in `references/markers.md`, so an intervening holder reading does not become stale merely because the holder supplied the missing route later.

Before each entrance launch, `run` maps `artifact` to `artifact_author`, build and repair stages to `implementer`, `cold-seat` to `cold_seat`, and `use` to `use_consumer`. A fresh implementer reads `~/.tradecraft/implementer-vendor` each time: absence chooses Codex, exact `codex` or `claude` chooses that vendor, and any other content refuses before a worktree, branch or bundle is made. The latest lawful whole-choice override line wins for its present role; an omitted role uses the machine vendor and its role profile. A resume keeps the proven session vendor, except that a machine switch to Claude hands an existing Codex lineage over once under the stretch's recorded exception. A conflicting override refuses rather than disappearing. Before a stage launches or resumes a recipient, the read-only report names its vendor, model and effort and each value's source, including fallback settings for a judging stage. For a resume it also names the selected session's recorded vendor and model separately from the next turn's requested settings, because a current default is not evidence of an earlier launch. `run` and both launchers print their resolved settings before launch. Where a role has no issue override, model and effort come from an applicable machine-local ruling bridge or the running version's defaults; the report names that path so the holder need not infer it from a launcher's table. The bridge matches the exact default it replaces, lapses when that default changes, and records its entry and ruling source wherever it supplies a value. The file and precedence contract is `references/launch-settings.md`. An `ordinary_seat` or `terminal_seat` issue choice reaches a launch when the holder passes its resolved values to `dispatch_seat.py` directly with the marker comment as their source. A holder-supplied `--claude` or `--codex` path is validated and forwarded; without one, `run` discovers the selected runtime. An unavailable executable remains an unavailable attempt rather than acquiring a requested setting as an observed one.

## Interrupted runs and continuation

A launcher writes its request, dispatch and initial run record before launching, then retains output, reported session identity and elapsed checkpoints as they arrive. The entrance bounds its own wait while allowing the child to spend its recording reserve; a stuck launcher is stopped with time left for the entrance to return. Only its final atomic write marks the record complete, because a caller's kill can run none of its cleanup. Launcher completion and recipient stage success are separate facts; unfinished or interrupted evidence never advances proof, staffing or a stage.

The entrance selects the latest applicable launch, including an unfinished one, before choosing a fresh builder without a pull request. A stopped artifact author resumes within the affirmed term; stopped build and repair stages resume the recorded builder in its registered root and branch. The report names the bundle, session, vendor, interruption, limit, progress and budget. The dispatch tells the recipient it stopped and to inspect the tree as it stands. A live or unresolved launch, unproved identity or mismatched lineage returns to the holder before another writer launches. A dead completed fresh failure that reported no session offers `--restart-unresolved-reason TEXT`: the holder explicitly replaces it in the registered tree, retaining the failed bundle and build-budget lineage. Failed handovers keep their reserved-session recovery route. Discovery excludes proved sibling instalments before selecting the latest attempt; missing attribution remains unresolved. Unproved descendant cleanup also returns to the holder. Seats remain fresh, with their stopped evidence retained.

After a ceiling stop, recommend the same stage only when Git content changed since the preceding stop (the launch state for the first window). Compare HEAD, index, tracked content and nonignored untracked content, because status alone misses a second edit to an already modified file. Unchanged or unreadable snapshots return a holder-owned state. The holder may still name the resume after no progress.

One builder lineage has a 14400-second build budget across distinct `build` invocations. Repair stages, artifacts and seats are excluded; stage changes and vendor handovers preserve the budget. Allocate an ordinary build no more than its remaining budget. Completed runs supply measured recipient runtime. An unfinished run's last durable elapsed checkpoint is its lower bound. Once both launcher and recipient are proved dead, its upper bound is that checkpoint plus the 0.25-second checkpoint interval and a 10-second margin for polling, recording and scheduling, capped by the enforced allocation. Unresolved liveness, missing checkpoint or unproved timing, spawn or cleanup keeps the allocation as the upper bound, because uncertainty cannot become a small charge. Both bounds and their separate bases remain visible in the report. Exhaustion or uncertainty that prevents proving an allocation fits returns to the holder. Another build then requires that invocation's `--budget-override-reason`, recorded before launch with consumption, uncertainty and allocation. Repair keeps its 3600-second stage ceiling as well as the caller's limit and progress rule, with no total budget. Runtime and override reasons appear beside money in the cost report without establishing usage or changing resume pricing.

## Roots and holder-owned endpoints

After the build, a confirmed conflict on any base or a behind branch on a base requiring up-to-date status checks routes to `catch-up` before floor, reviewers, use, proof or release reporting, because a stale green gate cannot establish merge readiness. Unknown synchronization facts remain visible and wait, except that unreadable strictness alone does not block a proved up-to-date, conflict-free pull request. A behind head with unknown strictness still waits. After the applicable current-head floor and the holder's criterion-completion check, make the pull request ready on every lane, disposition reviewers and any bought panel, then buy use where required and compose proof.

`run catch-up --root HOLDER_PATH --holder-session-id ID` resolves the registered implementation tree internally and launches nobody. It requires clean content and matching registered, local, remote and pull-request identities; it fetches and pins the actual base and lands through the persist script. A clean merge, or conflicts confined to the declared JSON version field, belongs to the holder through this endpoint; other conflicts are aborted and returned as a resumed-builder obligation. Floor and proof stay due at the resulting head. A checked commit left by a push failure follows persist's existing recovery route; repeating catch-up creates no second merge or bump.

The optional use-policy `version` object names a repository-relative JSON `path`, top-level string `field` and `increment` (`major`, `minor` or `patch`). The version has three integer parts. When the base side changed that file since the parents' merge base, catch-up sets it to the pinned base's value with that part incremented and lower parts reset; otherwise it leaves the change's version as it is. Tradecraft declares `.claude-plugin/plugin.json`, `version`, `minor`. Only an ordinary modification whose first-parent and commit JSON objects are equal after removing that member leaves the overlap comparison. File modes are not read. Other members, renames, missing or non-JSON content still count. This exemption applies to base commits and paths brought into merges; a separate authored version bump still buys use, so catch-up includes a needed adjustment in the merge commit. A holder may explicitly run use and record its reason when it suspects an interaction through a file only the base changed; file overlap cannot detect that interaction.


A fresh `run build` creates and registers the implementation worktree below the holder checkout's `.claude/worktrees/`, keeps that parent in the repository-local exclude file so it is neither committed nor shown in status, publishes its entrance-created branch to the uniquely selected remote, sets its upstream and verifies the remote head before launching. The builder stays on that branch, commits and pushes there, then returns; when its lawful session marker exists without a pull request, the next report is the holder-owned `open-pull-request` step rather than another build. Later implementer stages resolve and prove that registered root internally, so the holder command names no protected implementation path. The path-based holder guard remains authoritative: a direct launcher command naming the protected root is still refused.

A merged implementing pull request on an open issue names that pull request and returns the holder-owned decision about what the issue still owes: close it, explicitly run another build, or run a use owed after the merge from a landed commit. A further build is fresh; the entrance does not infer it from the still-open issue, and it refuses while the merged implementation's registration remains active so the holder can `release` that registration first.

`holder_write_guard=available` records only that the holder checkout declares the complete write-refusing `PreToolUse` hook; it does not claim the runtime loaded it. Without that declaration the registration records `unavailable`, and revision and status snapshots detect a breach without claiming to enforce the boundary.

`run cold-seat` creates an empty temporary repository outside the change, gives it one neutral detached commit and no remote or shared history, and removes it after the seat returns. Its prompt remains the exact artifact, exact brief and cold-check contract, with no fetch command or record.

`run proof` and `run ready-reviewers` are holder-owned endpoints and launch nobody. The former composes and publishes the current-head proof from the record and requests a specifically identified gate rerun; for a mechanical lane its generated no-use evidence names the affirmed comment and the lane exemption rather than claiming the paths did not match. The latter validates the same applicable floor as the read-only report, then applies the optional configured reviewer label before marking the pull request ready. Before authorizing readiness, the holder accounts for every artifact criterion in the latest build or repair return, obtains every owed non-CI result and holder-launched fresh-reader return, and records the results and seat references it relied on. Repairs renew this duty before the repaired head is treated as release-ready, even on an already-ready pull request. Their full contract is `references/proof.md`.

`run use` requires both the holder's job and a tree produced below:

```text
python <plugin-root>/lib/work.py run use ... \
  --dispatch JOB --tree-metadata TREE.tradecraft-tree.json
```

It validates the adjacent metadata, source revision, detached neutral repository and carried bytes before launching the consumer through `dispatch_seat.py`. An explicit `run use` remains lawful for a mechanical change; the lane changes recommended obligations, not the authority of a holder-named stage. `run release-report` launches nobody and returns the report handoff to the holder; it refuses a custom dispatch. That handoff reports each required source at the current head and aggregates it as `green`, `red`, `stale`, `absent`, `none` or `unidentified`. Only `green` and the positively established `none` need no gate departure: another verdict directs the holder to restate the `**Path departures:**` paragraph with its reason, while unreadable rules are recorded as uncertainty rather than as a claim that a particular gate was bypassed. A shared gate that does not yet read the affirmed mechanical lane may therefore remain red; the result is preserved rather than turned into a use duty. The report records rather than forbids a departure, because merging remains the owner's decision. Repeating either the ordinary decision or the release-report handoff cannot buy another recipient.

Build a consumer tree with the same door:

```text
python <plugin-root>/lib/work.py tree \
  --repo OWNER/REPO --issue N --root HOLDER_PATH \
  [--revision COMMIT] \
  --mode adopter|repository-session --output PATH \
  --path PATH [--path PATH ...] MODE-SPECIFIC-OPTIONS
```

Adopter mode requires one or more `--loading-surface` values. Repository-session mode requires `--front-page` and `--root-instructions` and accepts repeated `--directed-path` values. Repeated `--exclude-record` pathspecs remove records; repeated `--deny-text` probes refuse leaks. Without `--revision`, `tree` archives the active registered implementation root's clean committed `HEAD`. With `--revision`, it uses the holder repository without consulting or writing a registration, resolves the named commit, refreshes the selected remote's default-branch head, and refuses unless the commit is an ancestor of that remote head. Metadata always records the exact source revision and whether a registration was used. Both routes retain the same declared-path, loading-surface, exclusion, denied-text, raw-object-id, file-mode, detached-history and clean-tree guarantees. Before use, validation selects the registered source or holder source from the integrity-checked metadata claim, re-proves the recorded revision and carried bytes, and for an unregistered source refreshes and re-proves remote-default reachability. The holder still inspects the result and characterizes unavoidable residue before use.

The entrance consumes the affirmed brief and recorded evidence; it never decides what work is for, the brief's terms, a vendor or model default, whether to merge, or an owner ask. An ambiguous pull request returns to the holder, who records the lawful `implementing-pr` marker or opens the pull request that should exist; holder reading, waiting, panel coordination and terminal states likewise return to the holder.

Before recommending proof or release, the entrance checks individual inline replies, identified body answers and whole-review answers for unidentified declared findings. The connected-reviewer answer contract owns those forms; proof diagnostics may expose incomplete answers without adding proof fields.

## Registration commands

`release` and `adopt` retain their direct forms and sweep active registrations before their state change. Release makes the selected row inactive without deleting its worktree or branch:

```text
python <plugin-root>/lib/work.py release --repo OWNER/REPO --issue N --root HOLDER_PATH [--instalment VALUE]
```

Adopt proves and registers a holder-named existing worktree without dispatching or deleting another:

```text
python <plugin-root>/lib/work.py adopt --repo OWNER/REPO --issue N \
  --root HOLDER_PATH --implementation-root IMPLEMENTATION_PATH \
  --holder-session-id ID [--instalment VALUE]
```

The holder and implementation roots must be distinct top-level worktrees in the same repository, and an entrance-shaped branch for another issue is refused. Where named instalment registrations exist, adopt requires `--instalment`, because omission must not deactivate a sibling instalment.
