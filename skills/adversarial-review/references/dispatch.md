# The dispatch contract

**Loaded when** you are writing the dispatch that sends a review role its work — a seat, a defense, a judge. A recipient reading a dispatch it was handed does not need it.

**Every dispatch is built in three parts, in this order** [D-90] [D-97]. The **shared block** comes first, with nothing before it but a byte-identical title line — a preamble puts per-recipient framing ahead of the shared block. It carries, verbatim or by link and never the dispatcher's paraphrase, the assignment — artifact location, diff base and the revision under review, purpose statement, evidence standards, what every recipient's output must carry (`../references/the-record.md`), any session note reporting use of the artifact, and any findings an earlier review recorded against it, carried with the instruction that a seat files whatever an entry now earns and does not rule it — and every predecessor stage's output whole, which a dispatch read cold does not receive but for the carve-outs the roster names (`../references/roster.md`); nothing else in it aims attention. The assignment is byte-identical across every recipient dispatched against the same diff base. Then a **dispatcher's note** where there is one, labeled as such and additive; no seat takes one, because a cold vantage sits among them and aimed attention is what that vantage is defined against. Last, **in this skill's own words**, the recipient's identity and its lens brief — which the `cold-read` seat does not take, for the reason and with the full list of what a cold dispatch withholds in the roster (`../references/roster.md`). **Its working location where that differs, and the shape its own role's output takes — findings, verdicts, rulings — are the only other per-recipient content.** What every recipient's output must *carry* is not per-recipient at all: the same things are asked of every recipient, whatever the report later does with each and whoever else produces the fields it does not ask for, so what is asked is assignment content and sits in the shared block. **So is the revision and what lands the recipient there**, which differs by route rather than by recipient. Writing either per recipient is how a dispatcher ends up repeating a byte-identical section outside the block whose definition is that it is byte-identical. **Calling attention is lawful; filtering and restating are not** — an author compressing its own charter is an interested party.

**Findings an earlier review recorded against this artifact are fetched before the first dispatch**, from wherever the repository keeps them. **Match an entry by the subject it names against what this change touches** — a file the change edits, or the cell that holds it — not by the change under review, which no later review shares. A finding held for evidence is promoted by being met again, which cannot happen if the stage that would meet it never reads it — so the fetch belongs here, at the assignment, and not to the stage that wrote the entry.

**Independence extends to every role**: defense and judge are staffed like seats — never the artifact's author, and the judge never a finder. In a single-session lane, all review roles are fresh dispatches, not the authoring session reviewing itself. The launch records the working root, sandbox or permission boundary, model, and reasoning effort; those are inputs to the evidence, not ambient defaults.

**A dispatch whose subject is text the change edits gets a working root whose copy of that text is the change's own**, and is told that any always-on text reaching it otherwise is not its governing text. A runtime injects the repository's own doctrine and charter into every session it starts, from wherever it resolves them — which on this practice's own evidence can be a tree that is neither the change, its base, nor the default branch, so a recipient reads the rule the change replaced and rules against it. Naming the working root is not enough on its own [D-222]: the stale text arrives beside it, and only an isolated root plus that statement has been observed to make a recipient reject it. **Nor does diffing against the default branch establish it**, a seat having been handed text from a tree that was neither the change, its base, nor that branch.

**The dispatch names the revision, not only the root, and carries what lands the recipient there.** A root is not a revision: isolation cut by a dispatching tool comes up on the repository default every time rather than occasionally, so a dispatch naming a root alone has named the text the change replaced. **Where the dispatcher creates the root, it positions it before launching** — `git worktree add --detach <path> <sha>` — and the recipient only verifies and reports. A recipient launched into a root a tool cut cannot be positioned that way, so it carries `git checkout --detach <sha>` instead, `git worktree add <path> <branch>` refusing a branch already checked out elsewhere. **Prefer positioning**: a read-only permission boundary lets a recipient verify `HEAD` and not move it, and there the carried command is the one thing it cannot run. **It can fail, so the dispatch says what to do then**: a local modification that differs between the two commits aborts it, and a line-ending difference alone is enough. `git show <sha>:<path>` reads the right bytes without it; a recipient that must run the tree's own tools at that revision has no fallback and reports that it could not detach rather than proceeding. Never `-f`, which discards a recipient's work.

**And the recipient states, in its output, the revision it actually worked at**, or that it reached none, **and whether the tree it worked in was its own or shared with any other recipient**. A statement the report carries (`../references/the-record.md`) is what makes a stage that judged replaced text legible to someone who was not in it.

**Every dispatched recipient works in its own tree, cut detached at the revision the dispatch names.** That is what isolation is here, and it is owed whatever the recipient was dispatched to do: a seat that only reads leaves the same residue as one that writes, and only-reads is what most dispatched recipients do. **A recipient dispatched to write owes one thing beyond it — its write boundary is that tree.** Mutation testing, red-probes, anything that writes: without that boundary concurrent readers see files change underneath them mid-review. **`git worktree add --detach <path> <base>`**, whose two arguments do separate work. The base decides the revision: omit it and the tree comes up at the dispatching session's own HEAD, which for a tool-cut root is the default branch. `--detach` decides whether a branch is made: omit it and git puts the tree on one, carrying the change's own content where the base was the change, so a pull request opened from it re-proposes the reviewed change under an unrelated title. Omit both and each failure lands at once. At a named revision the flag changes nothing observable, which is why a check over the two forms proves nothing. **Detached, the base may be the change under review** — a seat probing that change has to hold it.

**A dispatched recipient's tree becomes removable when the review that dispatched it closes** — its final report posted — and not before: a seat that returned unusable output is re-dispatched once (`../references/arbitration.md`), and the one removal made on a session's own judgement took a cold seat's tree while that seat was still verifying. Trees outlive the sessions that cut them, so a rule owed by the dispatching session reaches none of the ones already standing, which is nearly all of them. **Removal covers the branch the tree's creation made**, where one still stands — a branch nothing removes is what outlives its tree, and whether the tree was cut with `--detach` is not what decides it.
