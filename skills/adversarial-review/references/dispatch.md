# The dispatch contract

**Loaded when** you are writing the dispatch that sends a review role its work — a seat, a defense, a judge. A recipient reading a dispatch it was handed does not need it.

**Every dispatch is built in three parts, in this order** [D-90] [D-97]. The **shared block** comes first, with nothing before it but a byte-identical title line — a preamble puts per-recipient framing ahead of the shared block. It carries, verbatim or by link and never the dispatcher's paraphrase, the assignment — artifact location, diff base and the revision under review, purpose statement, evidence standards, what every recipient's output must carry (`../references/the-record.md`), any session note reporting use of the artifact — plus the diff and available executable probe evidence, with commands, revisions, results and execution gaps, and every predecessor stage's output whole, which a dispatch read cold does not receive but for the carve-outs the roster names (`../references/roster.md`); nothing else in it aims attention. Where the assignment carries external-review material, it carries the whole external-pass bundle and its complete receipt block together, by file or link, inside this byte-identical block; the receipt includes its replay command, and a selected list or copied body does not. A proved-empty bundle is evidence too. The assignment is byte-identical across every recipient dispatched against the same diff base, except material the roster explicitly withholds for `cold-read`; the dispatch names that exception rather than silently giving it a selected substitute. Then a **dispatcher's note** where there is one, labeled as such and additive; no seat takes one, because a cold vantage sits among them and aimed attention is what that vantage is defined against. Last, **in this skill's own words**, the recipient's identity and its lens brief — which the `cold-read` seat does not take, for the reason and for what a review withholds beyond the standard in the roster (`../references/roster.md`), what makes a seat cold at all being the `engagement` cell's. **Its working location where that differs, and the shape its own role's output takes — findings, verdicts, rulings — are the only other per-recipient content.** What every recipient's output must *carry* is not per-recipient at all: the same things are asked of every recipient, whatever the report later does with each and whoever else produces the fields it does not ask for, so what is asked is assignment content and sits in the shared block. **So is the revision and what lands the recipient there**, which differs by route rather than by recipient. Writing either per recipient is how a dispatcher ends up repeating a byte-identical section outside the block whose definition is that it is byte-identical. **Calling attention is lawful; filtering and restating are not** — a summary can lose what its source carried.

**Role separation and judging-seat staffing are the `engagement` cell's; the judge is also never a finder.** The job declares its capability. The launch records root, selected boundary, model and effort; selected means the launcher's request, not runtime observation.

**A dispatch whose subject is text the change edits gets a working root whose copy of that text is the change's own**, and is told that any always-on text reaching it otherwise is not its governing text. A runtime injects the repository's own doctrine and charter into every session it starts, from wherever it resolves them — which on this practice's own evidence can be a tree that is neither the change, its base, nor the default branch, so a recipient reads the rule the change replaced and rules against it. Naming the working root is not enough on its own [D-222]: the stale text arrives beside it, and only an isolated root plus that statement has been observed to make a recipient reject it. **Nor does diffing against the default branch establish it**, a seat having been handed text from a tree that was neither the change, its base, nor that branch.

**The dispatch names its revision and landing route.** A root is not a revision: a tool-cut root otherwise opens on the default rather than the text under review. Where the dispatcher creates it: `git worktree add --detach <path> <sha>`; the recipient verifies and reports. A tool-cut attached root is **seat-launcher-incompatible**: this launcher refuses it before checkout, so use one that permits recipient positioning. **Prefer positioning**: it detaches every read or execute recipient. If it fails, including on differing local changes or line endings, `git show <sha>:<path>` reads the right bytes; a recipient needing the tree's tools reports it could not detach. Never `-f`.

**And the recipient states, in its output, the revision it actually worked at**, or that it reached none, **and whether the tree it worked in was its own or shared with any other recipient**. A statement the report carries (`../references/the-record.md`) is what makes a stage that judged replaced text legible to someone who was not in it.

**Every dispatched recipient works in its own tree, cut detached at the revision the dispatch names.** That is what isolation is here, and it is owed whatever the recipient was dispatched to do: a seat that only reads leaves the same residue as one that writes, and only-reads is what most dispatched recipients do. **A recipient dispatched to write owes one thing beyond it — its write boundary is that tree.** A capability-`execute` dispatch is dispatched to write for this rule and names that boundary. It also gives the seat a time bound sized for its job and tells it to bank findings to a named file in its tree as it goes, because a timeout can return no transcript. Mutation testing, red-probes, anything that writes: without that boundary concurrent readers see files change underneath them mid-review. **`git worktree add --detach <path> <base>`**, whose two arguments do separate work. The base decides the revision: omit it and the tree comes up at the dispatching session's own HEAD, which for a tool-cut root is the default branch. `--detach` decides whether a branch is made: omit it and git puts the tree on one, carrying the change's own content where the base was the change, so a pull request opened from it re-proposes the reviewed change under an unrelated title. Omit both and each failure lands at once. At a named revision the flag changes nothing observable, which is why a check over the two forms proves nothing. **Detached, the base may be the change under review** — a seat probing that change has to hold it.

**A dispatched recipient's tree becomes removable when the review that dispatched it closes** — its final report posted — and not before: a seat that returned unusable output is re-dispatched once (`../references/arbitration.md`), and the one removal made on a session's own judgement took a cold seat's tree while that seat was still verifying. Trees outlive the sessions that cut them, so a rule owed by the dispatching session reaches none of the ones already standing, which is nearly all of them. **Removal covers the branch the tree's creation made**, where one still stands — a branch nothing removes is what outlives its tree, and whether the tree was cut with `--detach` is not what decides it.
