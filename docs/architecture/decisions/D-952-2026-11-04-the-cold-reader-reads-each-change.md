# D-952 — The cold reader reads each change for its reasons

**Purpose:** record why instalment 2 of #942 builds the cold reader the way it does, and that it ends [D-944](D-944-2026-11-03-code-carries-its-reasons.md)'s interim. **Audience:** a future session changing the `cold-reader` stage, the `cold-reading` marker, what the reader may hold, or when a change's reading is current. **Success:** that reader can recover what was chosen over what without the issue.

The owner's [affirmed brief](https://github.com/Grimblaz-and-Friends/tradecraft/issues/942#issuecomment-6613335767) governs. Instalment 2's pre-implementation artifact was [settled on the cap route](https://github.com/Grimblaz-and-Friends/tradecraft/issues/942#issuecomment-6623789242). The lane is ordinary / connected, and no panel was bought.

## Rows and their reasons

- **Row 4, a fresh reader who never sees the issue, brief, pull-request text or branch name checks that the code explains itself, over the holder judging it.** The owner's proposal: a reader who never saw the issue should get "everything it needs from the adr, live documentation and code itself". Flags alone miss confident misreadings, so the reader writes what each section is for and why, and the builder and holder both review that account. Correcting the account would hide the gap the check exists to find, so it is never corrected by hand, and each fix is made in the code or the documents, preferring the code, and then reread. Each flag is the holder's call, under the amended row 4 below.
- **Row 5, the reader runs on every change that alters code, the mechanical lane included.** Reasons must hold everywhere, and a small change's reading is small. The brief estimated about $4 at list for a change of around a thousand lines, from #943's use consumer at $3.86 and 14 minutes on Opus 5.5 at `xhigh`; this change measures its own run in its release report.
- **The interim ends.** D-944 left the holder judging whether a change with no decision record decided nothing and is understood without its brief, and nominating the excerpts worth a look. Both now belong to the cold reader. The holder keeps its own pointer, in-force, lasting-reason and return checks.

## Calls made inside the rows

- **C1. A named entrance stage, `run cold-reader`, over a holder-written seat dispatch.** The holder holds the brief and could aim the reader through its dispatch, and a stage gives the every-lane gate somewhere to live.
- **C2. The entrance derives the reader's inputs only along row 4's list.** It follows `path#anchor` pointers from changed files to Markdown files that exist at the head, and from each pointed section only the links inside it. A file a changed file merely mentions isn't carried, so an unresolvable pointer reaches the reader as a dead end rather than being patched by whoever built the tree. The entrance can't tell a decision record by its path, so every link inside a pointed section is carried, not only its decision records.
- **C3. One `cold-reading` marker with `open` and `clean`, the holder's review riding in the `open` comment,** because the mechanical lane manufactures no `holder-reading` marker and row 5 requires that lane covered.
- **C4. A reading is current by blob, per changed path and per dependency; a reread is per file.** Blob identity is what the entrance can compare. Counting the pointed document's and listed records' blobs rereads a flagged file whose fix landed only in its document. A merge from the base that touches none of them owes no reread.
- **C5. No classification of what counts as code: every path in a gated change's change set is read,** because a path classifier is configuration every adopter would owe. Which pull requests the gate reaches is narrowed below, to those a builder built.
- **C6. The cold classification's defaults, Claude Opus 5.5 at `xhigh`,** keeping [D-795](D-795-2026-09-29-seat-defaults-follow-owner-rulings.md)'s seat rulings and matching the setting the brief's estimate assumed.
- **C7. No round cap, and the holder's acceptance is the exit.** As settled, C7 read "Row 4 fixes every flag", so a reading could close only once no flag stood. Under the amended row 4 a flag is fixed only where the holder judges it worth another round, and otherwise accepted with a one-line reason, so the loop ends on the holder's judgement rather than on a count of rounds. A flag that comes back on a reread is still evidence about the point, and the holder names which of four it is: a false claim about the tree, which the holder probes; a passage of the wrong shape, which is restated whole; a fork, a choice that is the owner's to make, which goes to the owner as an ask made after affirmation, with its cost stated; or a point not worth another round, which it accepts.
- **C8. The stage is `cold-reader` and the marker `cold-reading`,** after the brief's own name for the seat.
- **C9. Decision records a change adds may carry its issue and pull-request numbers in the reader's tree.** Row 4 lists them as inputs; the reader has no network tool, so their links are dead to it, and the occurrences are recorded as residue.
- **C10. The account's why answer opens with `Can tell: yes|no`, and only a reading of the whole current change clears a `no`.** Row 3's test is this: a change that decides nothing writes no decision record if a reader who never saw its issue can tell, from the code and the documents it points to, why it was made; if that reader can't, the change owes one. The `Can tell` line lets the entrance hold `clean` on that test mechanically, and a reread of a few fixed files answers only for those files.

## Made while building, and accepted by the holder

- **The gate is due only once a builder turn exists for the change, the rule reach uses.** A change no builder built has no builder to resume for the fixes a reading routes, so there is nothing for the gate to hold it for. This departs from the artifact's "every implementing pull request": a pull request opened by hand, with no recorded or observed builder turn, is not gated.
- **Suites about other stages run past the gate through one test fixture that stubs it,** `cold_reading_gate` in `lib/tests/conftest.py`, which runs for every test (`autouse`). Their fixtures carry synthetic heads with no Git objects behind them, so the real gate would hold every one as unverifiable. The gate's own tests carry the `cold_reading` marker, which exempts them from the stub, and run the real gate against a real repository and retained bundles.
- **The gate itself raises the holder-owned `cold-reading-post-owed` step and sets aside an invalid `clean`.** A reading whose account no `open` comment carries yet is the holder's to post before the builder can be resumed with it, and a `clean` can be judged only where coverage, flags and the builder's turn are computed, which is the gate, not marker validation. A `clean` posted after the latest `open` is listed invalid on every hold the gate returns, the hold that waits for a reading to be posted included; one posted before it closed an older reading and is left alone.
- **A bundle the gate can't read reports `cold-reading-unverifiable`, naming it, rather than aborting or vanishing.** A reading or builder bundle with an unsupported record schema, a reading whose retained return or tree metadata is missing or unreadable, or a builder turn whose frozen prompt can't be read, makes the gate holder-owned and an `open` marker that depends on it invalid. Neither marker validation nor the decision stops on one bad record, and a damaged reading never makes the gate ask for a fresh one as though none had run. The builder's prompt fails closed the same way: a damaged reading stops the prompt rather than letting it go out without the reading it owes, and `run cold-reader` reports one as a refusal naming the bundle rather than raising. A return the stage refused for its form is skipped, because it was never a reading. A `cold-reading` marker with no posting time is set aside, because it can't be ordered against the reading it claims.
- **Every flag has a way out through a reading the gate orders, or the holder's acceptance.** A flag the holder didn't accept stands until a later reading that read its path no longer raises it; a reading has read a path it covers, or a document or record one of its covered paths depends on, and reading the whole change doesn't by itself reach a path outside it. Two rules keep that from trapping a change. A flag must name a file its own reading's tree carries, or the stage refuses the return and the reading runs again, so no flag can name a path no reading reaches. And once the builder has reviewed a reading, a reread covers every stale file plus every changed file that a standing flag names or that points to the document it names, whether or not that file changed, so a flag answered without editing its file, or ruled a misreading, is still read again. A flag whose path nothing in the change reaches any more is answered by the reread of what changed. A flag on a dependency two changed files share counts once. Without these, the holder found that a flag on a mistyped path, or on a file the builder answered elsewhere, could never clear.
- **`run cold-reader` reads only what the gate orders.** Only the gate knows which paths are owed a reading, so a run the gate didn't order is refused, naming what the gate recommends instead; a bad timeout is refused before any tree is built.
- **The reader launches on its role's resolved vendor:** Claude by default, or the vendor a per-issue `model-override` names for `cold_reader`, because the role is overridable and staffing must be judged against the seat that actually runs. A seat on its builder's vendor records why: `owner-selected-claude-implementer` for Claude, as the stretch's staffing rule already names, and `owner-selected-codex-cold-reader` for an owner-selected Codex reader judging a Codex builder.
- **The diff travels inline below a size bound and as one file in the reader's root above it,** so a large change's prompt stays readable.

## Row 4 amended: the holder's judgement ends the loop

This change's own reading loop ran twelve readings without a `clean`. Flags per reading went 9, 6, 7, 7, 7, 1, 4, 3, 2, 1, 1, 1, settling at about one new missing reason a round, at roughly $10 and an hour a round, because the gate's only exit was a reading with no standing flag. The owner ruled on that loop: "yes, but you also need to end this loop earlier. Let's start by leaving it up to the holder's judgement and measure how that goes". He then affirmed the amended wording of row 4 on 2026-11-05: "Affirmed". The affirmed row's decision cell, whole:

> **4. A cold reader checks the code explains itself.** After the build, a fresh reader works from only the changed code, the design documents it points to, the decision records they list, and any design document or decision record the change itself adds or edits. It never sees the issue, brief, pull-request text or branch name. It writes what each changed section is for and why, flags where it can't tell, and nominates a few excerpts worth learning from (row 7). The builder reviews its account for the reasons it decided while building, and the holder reviews it against the brief. Every misreading is fixed in the code or the documents, preferring the code, and that section is then reread. Each flag is the holder's call. A flag worth another round is fixed in the same way. The holder accepts the rest, each with a one-line reason. A reading whose remaining flags are all accepted closes with no further builder turn or reread. A `Can tell: no` is always fixed. The account itself is never corrected by hand. Once #772 lands, a document fix made after the build returns to the owner for his lock.

Its owner cell now reads: "Judges the holder's calls from the release report. For every reading, the report lists each flag fixed or accepted, with the acceptance reasons, the reading's cost and its duration." C7 above changed with it.

**The strongest case against.** The holder has read the brief, which is exactly what the cold reader exists to avoid: a holder who knows why the code is the way it is can accept a flag whose reason the code still doesn't carry, and the gap the reading found closes without a fix. The release report's measurement is how the owner catches a bad acceptance, since it lists every accepted flag with the reason the holder gave.

**How it was built.**

- **The acceptance line.** Beneath the `open` comment's "Holder's review against the brief" heading, one line per accepted flag: `Accepted: path:lines — KIND — reason`, naming the flag by its path, its lines where the holder gives them, and its kind; where two flags share all three, the flag's own text goes before the reason. The form is strict, unlike the reader's lenient flag lines, because a holder's line that doesn't parse, or names no single flag, must set the `open` aside naming that line rather than accept nothing. Lines above the heading are the account's, so an `Accepted:` line there is never read as one.
- **What an acceptance does.** An accepted flag doesn't stand and owes no reread. A `Can tell: no` is not a flag, so no line can accept it, and it holds the change until a whole-change reading says `yes`.
- **Closing with no builder turn.** When the acceptances leave nothing standing or owed — no flag from any reading, no stale or uncovered path, no standing `no` — the gate asks the holder for `clean` at once, and a `clean` posted after that `open` counts. That includes a reading that raised no flag at all, so the builder's own review of an account for misreadings now runs only when something is routed to it; the holder's review against the brief still looks for misreadings, and a holder who wants the builder's view names the `build` stage. A reading with some flags routed and some accepted resumes the builder for the routed ones and rereads what they reach.
- **The measurement.** `run release-report` returns, under `cold_readings`, each reading's head, whether it read the whole change, the flags it raised, which were routed and which accepted with their reasons, and the run's vendor, model, effort and duration, from the readings and `open` comments the gate already loads, so the holder doesn't count by hand. The list-price cost stays with the dispatch record's cost report, which holds the rate card; the release-report reference says to take it from there.

## Answered connected-review findings

The connected reviewers' findings at the amended head were ruled by the holder and fixed in one turn. Those that change what this record says:

- **Named stages hold too.** `run ready-reviewers`, `run use`, `run proof` and `run release-report` refuse without effect while the gate returns a decision, because a named stage skips the decision the gate sits in.
- **Readings are scoped to their pull request.** A cold-reader request records its branch and pull request, and a reading recorded for another one doesn't count. Readings recorded before lineage was, this change's own, count only when this change's history holds the head they read. A cold-reader record that won't parse holds the gate as unverifiable.
- **A fallback records its reason.** The seat is always given the same-vendor reason, so a reading that lands on the builder's vendor through fallback records the reason an `open` checks; a Claude reader falling back onto a Codex builder records `cold-reader-fell-back-to-builder-vendor`.
- **The builder's vendor is proved before any tree is written,** from a build bundle or else the latest lawful `builder-session` marker, and a reading nothing proves is refused as unverifiable.
- **The builder is resumed only for what the latest `open` routed:** an unaccepted flag or a `Can tell: no`. Only a successful builder turn that returned something counts as a reading's review.
- **An `open` must carry its reading's head.**
- **The tree:** `none` is read leniently; a deletion-only change carries no files; a flag may name a covered path the change deletes; repeated headings' numbered anchors, reference-style links and `./` pointers resolve as the renderer would; a renamed file's diff keeps its removed lines; a committed root `CHANGE.diff` that would collide with the generated one is refused; an empty `## Sections` fails the form.
- **Declined:** tracking file mode in coverage. A mode-only change has no text whose reason a reader could judge, and adding mode to the coverage key would restale every recorded reading.

## Codex's network, probed

The artifact asked the builder to confirm what Codex's read-only sandbox does about network before relying on it. One low-effort turn ran with the cold-reader launch's own flags, `codex exec --strict-config --ignore-user-config --ephemeral --sandbox read-only --disable apps -c apps._default.enabled=false -c windows.sandbox="elevated" -c model_reasoning_effort="low" --skip-git-repo-check`, on Codex CLI 0.166.0-alpha.5.1 under Windows, and was asked to run `curl -sS -m 15 -o NUL -w "%{http_code}" https://example.com`. Inside the sandbox it returned `000curl: (7) Failed to connect to example.com port 443 after 28 ms: Could not connect to server`, exit 1; the same fetch outside the sandbox returned `200`. Network is not reachable from the read-only sandbox, so the cold-reader launch passes no further configuration for it, and its permission boundary keeps recording `sandbox=read-only`.

## The design document for the new code

`code-reasons.md` owes a design-document section for code a change adds, creating the repository's design document if it has none. tradecraft had none, and its decision entries live in repository-only material that shipped code may never reference. So this change opens the shipped library's own design document, `lib/DESIGN.md`, inside the shipped tree, and gives it a section, "The cold reader", saying what the reader and its gate do now and why. The section names the decisions in force by their decision-log ids, D-795, D-944 and D-952, without linking them, and says the decision log stays in the repository. So in this repository a reading of library code gets its reasons from the design document and the code's own lines, not from the records: each section states its reasons whole, and the ids are for a maintainer searching the log, not pointers a reader follows. `lib/cold_reader.py` opens with a pointer to that section, and so does the block of gate and stage functions this change adds to `lib/work.py`. That pointer names the block's first and last definitions, `COLD_READING_REVIEW` through `_execute_cold_reader`, so its reach can be checked, and the new test module opens with the same pointer. The rest of `lib/work.py` is code this change only edits, so it waits for tradecraft's catch-up, which also extends the document to the library's existing code.
