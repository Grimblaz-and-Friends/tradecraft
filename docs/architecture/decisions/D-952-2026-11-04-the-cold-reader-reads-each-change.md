# D-952 — The cold reader reads each change for its reasons

**Purpose:** record why instalment 2 of #942 builds the cold reader the way it does, and that it ends [D-944](D-944-2026-11-03-code-carries-its-reasons.md)'s interim. **Audience:** a future session changing the `cold-reader` stage, the `cold-reading` marker, what the reader may hold, or when a change's reading is current. **Success:** that reader can recover what was chosen over what without the issue.

The owner's [affirmed brief](https://github.com/Grimblaz-and-Friends/tradecraft/issues/942#issuecomment-6613335767) governs. Instalment 2's pre-implementation artifact was [settled on the cap route](https://github.com/Grimblaz-and-Friends/tradecraft/issues/942#issuecomment-6623789242). The lane is ordinary / connected, and no panel was bought.

## Rows and their reasons

- **Row 4, a fresh reader who never sees the issue, brief, pull-request text or branch name checks that the code explains itself, over the holder judging it.** The owner's proposal: a reader who never saw the issue should get "everything it needs from the adr, live documentation and code itself". Flags alone miss confident misreadings, so the reader writes what each section is for and why, and the builder and holder both review that account. Correcting the account would hide the gap the check exists to find, so it is never corrected by hand, and each fix is made in the code or the documents, preferring the code, and then reread.
- **Row 5, the reader runs on every change that alters code, the mechanical lane included.** Reasons must hold everywhere, and a small change's reading is small. The brief estimated about $4 at list for a change of around a thousand lines, from #943's use consumer at $3.86 and 14 minutes on Opus 5.5 at `xhigh`; this change measures its own run in its release report.
- **The interim ends.** D-944 left the holder judging whether a change with no decision record decided nothing and is understood without its brief, and nominating the excerpts worth a look. Both now belong to the cold reader. The holder keeps its own pointer, in-force, lasting-reason and return checks.

## Calls made inside the rows

- **C1. A named entrance stage, `run cold-reader`, over a holder-written seat dispatch.** The holder holds the brief and could aim the reader through its dispatch, and a stage gives the every-lane gate somewhere to live.
- **C2. The entrance derives the reader's inputs only along row 4's list.** It follows `path#anchor` pointers from changed files to Markdown files that exist at the head, and from each pointed section only the links inside it. A file a changed file merely mentions isn't carried, so an unresolvable pointer reaches the reader as a dead end rather than being patched by whoever built the tree. The entrance can't tell a decision record by its path, so another link inside a pointed section is carried too; the holder's pointer check catches that malformed section.
- **C3. One `cold-reading` marker with `open` and `clean`, the holder's review riding in the `open` comment,** because the mechanical lane manufactures no `holder-reading` marker and row 5 requires that lane covered.
- **C4. A reading is current by blob, per changed path and per dependency; a reread is per file.** Blob identity is what the entrance can compare. Counting the pointed document's and listed records' blobs rereads a flagged file whose fix landed only in its document. A merge from the base that touches none of them owes no reread.
- **C5. No classification of what counts as code: every path in a gated change's change set is read,** because a path classifier is configuration every adopter would owe. Which pull requests the gate reaches is narrowed below, to those a builder built.
- **C6. The cold classification's defaults, Claude Opus 5.5 at `xhigh`,** keeping [D-795](D-795-2026-09-29-seat-defaults-follow-owner-rulings.md)'s seat rulings and matching the setting the brief's estimate assumed.
- **C7. No round cap.** Row 4 fixes every flag. A flag that comes back on a reread is evidence about the point, and the holder names which of three it is: a false claim about the tree, which the holder probes; a passage of the wrong shape, which is restated whole; or a fork, a choice that is the owner's to make, which goes to the owner as an ask made after affirmation, with its cost stated.
- **C8. The stage is `cold-reader` and the marker `cold-reading`,** after the brief's own name for the seat.
- **C9. Decision records a change adds may carry its issue and pull-request numbers in the reader's tree.** Row 4 lists them as inputs; the reader has no network tool, so their links are dead to it, and the occurrences are recorded as residue.
- **C10. The account's why answer opens with `Can tell: yes|no`, and only a reading of the whole current change clears a `no`.** Row 3's test is this: a change that decides nothing writes no decision record if a reader who never saw its issue can tell, from the code and the documents it points to, why it was made; if that reader can't, the change owes one. The `Can tell` line lets the entrance hold `clean` on that test mechanically, and a reread of a few fixed files answers only for those files.

## Made while building, and accepted by the holder

- **The gate is due only once a builder turn exists for the change, the rule reach uses.** A change no builder built has no builder to resume for the fixes a reading routes, so there is nothing for the gate to hold it for. This departs from the artifact's "every implementing pull request": a pull request opened by hand, with no recorded or observed builder turn, is not gated.
- **Suites about other stages run past the gate through one test fixture that stubs it,** `cold_reading_gate` in `lib/tests/conftest.py`, which runs for every test (`autouse`). Their fixtures carry synthetic heads with no Git objects behind them, so the real gate would hold every one as unverifiable. The gate's own tests carry the `cold_reading` marker, which exempts them from the stub, and run the real gate against a real repository and retained bundles.
- **The gate itself raises the holder-owned `cold-reading-post-owed` step and sets aside an invalid `clean`.** A reading whose account no `open` comment carries yet is the holder's to post before the builder can be resumed with it, and a `clean` can be judged only where coverage, flags and the builder's turn are computed, which is the gate, not marker validation. A `clean` posted after the latest `open` is listed invalid on every hold the gate returns, the hold that waits for a reading to be posted included; one posted before it closed an older reading and is left alone.
- **A bundle the gate can't read reports `cold-reading-unverifiable`, naming it, rather than aborting or vanishing.** A reading or builder bundle with an unsupported record schema, a reading whose retained return or tree metadata is missing or unreadable, or a builder turn whose frozen prompt can't be read, makes the gate holder-owned and an `open` marker that depends on it invalid. Neither marker validation nor the decision stops on one bad record, and a damaged reading never makes the gate ask for a fresh one as though none had run. The builder's prompt fails closed the same way: a damaged reading stops the prompt rather than letting it go out without the reading it owes, and `run cold-reader` reports one as a refusal naming the bundle rather than raising. A return the stage refused for its form is skipped, because it was never a reading. A `cold-reading` marker with no posting time is set aside, because it can't be ordered against the reading it claims.
- **Every flag has a way out through a reading the gate orders.** A flag stands until a later reading that read its path no longer raises it; a reading has read a path it covers, or a document or record one of its covered paths depends on, and reading the whole change doesn't by itself reach a path outside it. Two rules keep that from trapping a change. A flag must name a file its own reading's tree carries, or the stage refuses the return and the reading runs again, so no flag can name a path no reading reaches. And once the builder has reviewed a reading, a reread covers every stale file plus every changed file that a standing flag names or that points to the document it names, whether or not that file changed, so a flag answered without editing its file, or ruled a misreading, is still read again. A flag whose path nothing in the change reaches any more is answered by the reread of what changed. A flag on a dependency two changed files share counts once. Without these, the holder found that a flag on a mistyped path, or on a file the builder answered elsewhere, could never clear.
- **`run cold-reader` reads only what the gate orders.** Only the gate knows which paths are owed a reading, so a run the gate didn't order is refused, naming what the gate recommends instead; a bad timeout is refused before any tree is built.
- **The reader launches on its role's resolved vendor:** Claude by default, or the vendor a per-issue `model-override` names for `cold_reader`, because the role is overridable and staffing must be judged against the seat that actually runs. A seat on its builder's vendor records why: `owner-selected-claude-implementer` for Claude, as the stretch's staffing rule already names, and `owner-selected-codex-cold-reader` for an owner-selected Codex reader judging a Codex builder.
- **The diff travels inline below a size bound and as one file in the reader's root above it,** so a large change's prompt stays readable.

## Codex's network, probed

The artifact asked the builder to confirm what Codex's read-only sandbox does about network before relying on it. One low-effort turn ran with the cold-reader launch's own flags, `codex exec --strict-config --ignore-user-config --ephemeral --sandbox read-only --disable apps -c apps._default.enabled=false -c windows.sandbox="elevated" -c model_reasoning_effort="low" --skip-git-repo-check`, on Codex CLI 0.166.0-alpha.5.1 under Windows, and was asked to run `curl -sS -m 15 -o NUL -w "%{http_code}" https://example.com`. Inside the sandbox it returned `000curl: (7) Failed to connect to example.com port 443 after 28 ms: Could not connect to server`, exit 1; the same fetch outside the sandbox returned `200`. Network is not reachable from the read-only sandbox, so the cold-reader launch passes no further configuration for it, and its permission boundary keeps recording `sandbox=read-only`.

## The design document for the new code

`code-reasons.md` owes a design-document section for code a change adds, creating the repository's design document if it has none. tradecraft had none, and its decision entries live in repository-only material that shipped code may never reference. So this change opens the shipped library's own design document, `lib/DESIGN.md`, inside the shipped tree, and gives it a section, "The cold reader", saying what the reader and its gate do now and why. The section names the decisions in force by their decision-log ids, D-795, D-944 and D-952, without linking them, and says the decision log stays in the repository. So in this repository a reading of library code gets its reasons from the design document and the code's own lines, not from the records: each section states its reasons whole, and the ids are for a maintainer searching the log, not pointers a reader follows. `lib/cold_reader.py` opens with a pointer to that section, and so does the block of gate and stage functions this change adds to `lib/work.py`. That pointer names the block's first and last definitions, `COLD_READING_REVIEW` through `_execute_cold_reader`, so its reach can be checked, and the new test module opens with the same pointer. The rest of `lib/work.py` is code this change only edits, so it waits for tradecraft's catch-up, which also extends the document to the library's existing code.
