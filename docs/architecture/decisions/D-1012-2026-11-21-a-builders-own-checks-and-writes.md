# D-1012 — A builder's own checks and writes

**Purpose:** record why the first of #1011's two pull requests gives a builder that carries its change to ready a launch of its own, a GitHub allowance for its own change, a run that stands after a refusal, and checks it can launch but not aim or edit, and what was chosen over what. **Audience:** a future session changing the `stretch` launch, its allowance, builder mode in the entrance, or how a builder's checks are composed, framed and counted. **Success:** that reader can recover what was chosen over what without the issue.

The owner's [affirmed brief](https://github.com/Grimblaz-and-Friends/tradecraft/issues/1011#issuecomment-7071427121) governs, including its Delivery paragraph, which gives this pull request the builder's tools and the second one the route. Its pre-implementation artifact was [settled on the cap route](https://github.com/Grimblaz-and-Friends/tradecraft/issues/1011#issuecomment-7072055248). The lane is elevated / routine-panel. Nothing composes a `stretch` launch until the second pull request lands, so everything here is inert on today's route.

## Rows and their reasons

The brief has seven rows. This pull request carries rows 1, 3 and 5, the builder's tools; rows 2, 4, 6 and 7 (the holder-written plan, the final pass, the one handoff text, and the default route) are the second pull request's, as the brief's Delivery paragraph says.

- **Row 1, the builder runs its checks as tools.** A builder's own `work.py run` is recognised and limited to the checks and own-change writes the brief gives it: `cold-reader`, `use`, `acceptance-criterion`, `proof`, `ready-reviewers` and `catch-up`. A check the builder launches records that it did.
- **Row 3, a check's instructions, inputs and report are out of the builder's reach.** A check is independent only while the party it checks can't aim it or edit it. So the settled artifact supplies a builder's use job, criteria and consumer trees. The entrance builds the tree inside the run that launches the seat, and posts the report from the seat launcher's own frame before the run returns.
- **Row 5, the builder writes only to its own change, and a refusal doesn't void its run.** The allowance covers the branch, the pull request opened from it and the change's issue. A refusal the builder recovered from is recorded in `refusals` and leaves the run standing. A seat keeps the rule that fails its launch on a refusal (#962 stays open for it).

## Calls made inside the rows

- **C1. Who launched a process is read from the launch's process tree, not a variable.** A builder can clear a variable but can't leave the kill-on-close job its Windows worker names, or the Linux subreaper below its launcher, except by the routes `lib/DESIGN.md` lists. The variable only names which launch.
- **C2. The tree check reads a pointer directory, `stretch-launches/` in the store, rather than every request record.** Every entrance run, seat launch and record begin makes this check, and a working store holds thousands of bundles; reading them all would slow today's route, which this change must leave as it is. The pointer is written before the stretch's first comparison snapshot, and the comparison covers it as `own-pointer`, so removing or rewriting it is a launch finding, as the request record's would be. A pointer outlives its launch and reads as not live once its run record completes.
- **C3. The root check alone reads the registry, and only reads it.** The plan's root rule names the registration, and the launcher isn't told the holder checkout. Identity and the stage table read no registry, so a refused stage still makes no registry or GitHub read.
- **C4. `release` and `adopt` are refused to a builder; the read-only decision and `allowance` without a grant are open.** Both refused commands write the registration, which is the holder's.
- **C5. A third variable, `TRADECRAFT_STRETCH_JOB`, names the job to the launch worker,** which drops it before the recipient starts. A seat launched directly with the stretch's other variables still set would otherwise find the stretch's job name taken. No keep-warm ping carries any of the three.
- **C6. A check's tree origin is kept beside its sealed record, in `tree-origins/`,** rather than inside it, because the tree record's digest seals its fields.
- **C7. The return frame travels on the seat launcher's stdout,** captured and forwarded by the entrance for builder-mode checks only. Today's route keeps the inherited-stream wait. The captured wait follows the launcher's window as the inherited one does, so a builder's check keeps its whole limit.
- **C8. One refused call is one entry in `refusals`, naming every source that reported it,** in its call's place in the run's stream. A call a bound refuses is also reported by Claude as a permission denial, and two entries for one call would count it twice. A refusal is placed by its tool-use id, or by its command or path read with either slash and in any case, because the file guard logs the resolved path and the call carries it as written. One placed by its text goes to a call whose input is that text before one that only contains it, then to a call Claude denied, because an earlier allowed call can name the same path; calls that tie and differ leave it unplaced rather than merge two refusals.
- **C9. The composed check takes today's use route's hold and synchronization, and prints its staffing plan,** but writes its own report rather than a stage decision's, because it launches one composed seat and has no recommendation to report.
- **C10. A seat launch and a record begin follow the entrance's one session rule:** a present session that is not the launch's is refused, and `declared` is for an absent session variable only. An empty `CLAUDE_CODE_SESSION_ID` is an absent one, in the entrance, the seat launcher and a record begin alike. Given the entrance's builder flags where the tree check can't be made, they refuse `launch-tree-unknown` before any bundle, because the builder's check would otherwise read as the holder's.
- **C11. A posted report counts only from a configured marker producer,** because the entrance posts under that login and any other author's comment is a claim.
- **C12. `work.py allowance stretch` prints the stretch sentence a holder-written dispatch carries,** though the entrance runs no `stretch` stage, because the launcher refuses a dispatch stating any other allowance.
- **C13. A stretch launch's comparison credits its own root's registry row re-snapshotting `revision_before` and `status_before`,** and nothing more. Its catch-up writes that row after the landing it made, and the unchanged comparison held on it; crediting by `launched_by` or `built_by`, as the plan anticipated, would not reach it, because the entrance writes the row in the builder's own run. The credit is a parameter of its own, which only the stretch launch passes; every other launch still holds on it.
- **C14. The six builder stages run in a comparison window each, not all in one.** Their stand-ins live in separate fixtures, each with its own home and registry; what a comparison could hold on is each stage's own writes, and a window per stage examines them all.
- **C15. After `uv run`'s options, a word is read both as an option's value and as the program,** because the check can't tell which of uv's options take a value; either reading that calls a launcher refuses, and a launcher named only as data in the command that runs passes.
- **C16. Only a composed `use` is held while a clean cold reading is owed.** A criterion check isn't, so a builder can gather its criteria's results and the reading's flags at one head and repair once; a result counts only at the head it names.
- **C17. A builder's check takes its producer's vendor from its own launch's request record,** because a first stretch launch has no completed bundle yet, and an older one would staff against another producer. A holder-run check keeps the completed-bundle lookup.
- **C18. A composed check passes the launch-account hold and its stage's version requirement before it builds a tree or launches a seat,** as a named stage does, and runs only on its own launch's registered root: a `--instalment` naming another registration is refused.
- **C19. A builder's own pull request is confirmed by a live read of its head, even the number its launch was given,** because the launch was told that number, not shown it; a pull request named by no number is the builder's only where the current branch is its own and one open pull request is headed by it.
- **C20. The return frame is the first one whose byte count reaches the end of the launcher's output,** so a return holding a frame of its own is read as return bytes.

## Rejected

- **Identifying a builder by the variable alone.** A builder can clear it, and its checks would then read as the holder's.
- **A post made later, reading the return from the store.** The builder's shell can write the store, so the report would be whatever it left there.
- **A tree stage the builder runs.** A tree the builder declares or names is something the seat reads.
- **A check stage with no recomposition.** A dispatch the caller supplied, with every declared field forged, would count.
- **Reading every request record for the tree check** (C2's reason).
- **Recomposing a reading from the diff kept beside its record.** The kept diff sits in the store, which the builder's shell can write, so a dispatch and a kept diff rewritten together would recompose; the diff is regenerated from the source instead.
