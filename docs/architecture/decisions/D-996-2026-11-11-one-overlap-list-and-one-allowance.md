# D-996 — One overlap list and one allowance for the launch comparison

**Purpose:** record why #984 has a launch's comparison read the dispatch store once and work out once which other runs overlapped it, and why everything between the after-walk and the final record runs inside one allowance that ends in `uncompared` instead of a lost record. It also records the calls made inside the brief's rows. **Audience:** a future session changing how a launch credits changes to other runs, how long the comparison may take, or what the launcher writes when it runs out of time. **Success:** that reader can recover what was chosen over what without the issue.

The owner's [affirmed brief](https://github.com/Grimblaz-and-Friends/tradecraft/issues/984#issuecomment-6802913137) governs. Its [pre-implementation artifact](https://github.com/Grimblaz-and-Friends/tradecraft/issues/984#issuecomment-6803312937) was [settled on the would route](https://github.com/Grimblaz-and-Friends/tradecraft/issues/984#issuecomment-6803521789), with the holder's directions in [the first reading](https://github.com/Grimblaz-and-Friends/tradecraft/issues/984#issuecomment-6803522498) and [the second](https://github.com/Grimblaz-and-Friends/tradecraft/issues/984#issuecomment-6806963829). The lane is ordinary / connected, and no panel was bought. This record supersedes none; it bounds [D-939](D-939-2026-11-03-claude-launch-writes-stay-in-their-tree.md)'s before-and-after comparison and puts [D-987](D-987-2026-11-09-a-launch-keeps-its-helpers-in-its-tree.md)'s working-copy and branch check inside the same allowance.

## What was slow, and what it costs now

Crediting a changed path worked out the overlapping runs again for that path, and deciding an overlap can read another launcher's process. On the owner's store of 2,717 run records, one path took 0.36 s, so 30,000 paths would have taken about three hours; the working-copy and branch check then read the store a second time. With the list worked out once, the holder measured the built `compare` on a store of 2,842 records examining 30,000 changed paths in 7.2 to 7.3 s over three runs, every path a finding and the item `compared`.

## What was chosen over what

- **The fast loop plus a fixed limit, over the fast loop alone and over writing the return into the run record before the comparison** (the owner's ruling, 2026-11-11: "Fast loop plus limit"). The fast loop alone removes the slowness measured but leaves the one step between the return reaching disk and the final record without a limit, so the next slow step there loses a record the same way. Writing the return first was left out because a launcher killed during its recording still loses it, and the entrance would have to count a return from a record that never finished.
- **`uncompared`, over recording an unexamined change credited or clean.** It is what the walk already records when it runs out of time, so the entrance already holds on it and the holder already inspects the item it names. Recording an unexamined change as credited or clean would hide damage, which is the risk a panel would have answered.
- **Two minutes** (`COMPARING_SECONDS`), the owner's limit. At the measured rates it covers several hundred thousand changed paths.

## Calls made inside the rows

- **The final write keeps an eighth of the reserve.** The allowance ends at `Deadline.final_write_at`, an eighth of the reserve before `Deadline.wait_end`, when the entrance stops waiting, whenever that comes before the two minutes. What follows the comparison is a few small writes: usage records, closing the streams, publishing the output and the atomic record write. An eighth is the gap the entrance already leaves between its wait's end and stopping the launcher's tree, and a record lost for want of write time is the worse failure. So after a ceiling stop whose walk used its whole window, the comparing has `reserve/2 − reserve/4 − reserve/8 = reserve/8`: **7.5 s at the 60 s reserve of a default stage limit**, half the "about 15 seconds, less the write" the brief gives. After such a stop on a slow machine, expect changed items to read `uncompared`.
- **`wait_end` is one `Deadline` property** that the entrance's wait (`work.py`), the record write's retry (`dispatch_lifecycle.py`) and the comparison all read, so the launcher's bound can't drift from the entrance's wait.
- **The list is obtained at most once, at the first point of need,** so a comparison where nothing needs it spends none of the allowance on the store.
- **Changes are sorted in memory before the store is read.** The run's own edits, and changes no other run could account for (an item the walk couldn't compare, a dispatch record, the own request, a registry file change other than a row, any change when the run's window can't be read), are decided first, so a slow read never marks the run's own tree `uncompared` for its own edits. Every other change needs the list, a changed home file included, since the unchanged rule credits it to a run whose root contains it; when the store read runs out, those items read `uncompared` too.
- **In time, crediting still comes before the default-branch rule.** Only when the allowance has ended does an entry still unattributed on the default branch get listed as the default branch, because that rule needs neither the list nor the run's record, and listing is not crediting.
- **A refs item whose pending entries could not be attributed or classified is `uncompared` with a count,** not held entry by entry as an unreadable record.
- **The run's stream is still read when nothing is pending,** so an in-time comparison records `run_record: read` as before; when the allowance stops the read or the matching, `run_record` reads `not-read`. The final, unterminated line is checked too, since row 2 checks after each line.
- **No new comparison field and no schema change.** The allowance's seconds, its bound and how many of the item's changes were examined appear in each affected item's reason, where the holder reads them.
- **The allowance's expiry is caught inside `compare`,** so the launcher never records the whole comparison `unrecorded` and the findings and credits already made stay.
- **The allowance is checked between repositories, and the working out of one repository's copies and branches is not interrupted.** The holder measured that working out, with the overlap list, at 6 ms for 3 repositories with 200 changed branches each and 0.7 s for 10 repositories with 5,000 changed branches and 200 changed copies each, so a check inside one repository buys little. Row 2 checks after each change examined, so every pass over the repositories checks after each one. When it ends there, a repository already credited keeps its credits; one not yet reached keeps the entries worked out without the list, so nothing in it is credited; and a changed repository whose entries were never worked out reads `uncompared` rather than dropping out of the record.
- **An allowance that ends with nothing left unexamined leaves the comparison `clean`.** That happens when it ends during the read of the run's record with no copy or branch entry waiting on it. Row 2's "never `clean`" protects unexamined changes, and here there are none, so `clean` with `run_record: not-read` is true.
- **A single step that hangs, such as one file read, is not interrupted;** the entrance's wait still ends that launch.
