# D-317: The installed version check is declined, because it has no consumer

**Status:** Accepted 2026-09-01 (PR #317)

## Context

`tools/check_version_bump.py` refuses a pull request that changes the shipped zone without raising the plugin version, and its refusal text says why: *"a consumer cannot tell installed from current."* Nothing anywhere reads the number afterwards.

This machine's install sat at `0.60.0` / `ba49e68` while `main` moved through six commits, one plugin release each, to `0.66.0` — `git rev-list --count ba49e68..e333441` returns 6, and `git show <sha>:.claude-plugin/plugin.json` across them returns `0.61.0` through `0.66.0`. It went stale when `945fe6b` landed (`2026-09-01 09:22:47 -0400`) and was current again at `lastUpdated 2026-09-01T20:26:22Z` in `~/.claude/plugins/installed_plugins.json` — **about seven hours behind, across six releases**, closed by the owner noticing and running the update by hand.

The filing said two days, and this entry does not, because the figure was carried from #313's title rather than re-derived. The widest window the timestamps permit at all is `installedAt 2026-08-31T22:53:36Z` to that `lastUpdated`, 21h33m, and the window in which the install was actually behind `main` is the seven hours above. **The number matters to the Reopen clause below**, which invites a later session to weigh a recurrence against this baseline.

[#313](https://github.com/Grimblaz-and-Friends/tradecraft/issues/313) filed that as a defect whose cost was that reviews had judged changes against doctrine the changes replaced. **That attribution was wrong and was withdrawn on the issue.** A subagent's `AGENTS.md` is read from the dispatching session's working directory — measured by asking tool-free seats for the `Contents of <PATH>` lines their own system prompts carry, under both plain and worktree-isolated dispatch, neither of which returned any plugin-cache path. The stale doctrine came from long-lived worktrees, which is [#284](https://github.com/Grimblaz-and-Friends/tradecraft/issues/284)'s subject; the evidence went there.

What survived is narrower: the version rises, and no consumer is made to catch up.

## The check is declined, and the first reason is the one that decides it

The obvious remedy is a check comparing the installed plugin version against the working tree. It is declined. Four reasons, strongest first.

**1. It has no consumer.** The check compares an install against a working tree. Only this repository's own sessions have such a tree — and they do not read doctrine from the install at all. `.claude/skills/adversarial-review/SKILL.md` is a generated stub whose body says *"Generated by `tools/roster.py` from `skills/adversarial-review/SKILL.md`, which is the `adversarial-review` cell and carries all of it. Read that file now."* Three cold seats given realistic in-repo jobs with no skill named each invoked the unprefixed cell name, and one reported following that stub into `skills/adversarial-review/SKILL.md`. An adopter, meanwhile, has no working tree to compare anything against. There is nobody for whom this check answers a question.

**2. There is no lawful firing site.** [D-222] removed lifecycle hooks after installed `SessionStart` and `UserPromptSubmit` hooks, plain output and JSON envelope alike, failed to enter Codex model context; no `hooks/` directory exists in the tree. `.github/workflows/ci.yml` runs on GitHub runners with no plugin installed, so CI has nothing to compare against.

**3. A check a session must remember to run re-creates the failure it fixes.** The measured failure was that nobody looked across six consecutive releases, while the guard enforcing the number ran on every single commit that produced them. A remedy whose trigger is *remember to check* has the same trigger that already failed.

**4. The version is a poor handle anyway.** A consumer comparing versions must already have fetched something to compare against, which is most of the work the comparison was meant to prompt.

### The comparison already exists where it has a consumer

`tools/check_codex_compat.py`, `_assert_plugin`, reads the version from `.claude-plugin/plugin.json`, calls `codex plugin list --json`, and raises when the two disagree: *"installed tradecraft version is {actual!r}; this tree is {expected_version!r}"*. So the comparison this decision declines is **already written** — as a **precondition assertion for a probe**, which is the one context where it answers a question somebody is asking: the probe is about to test the installed plugin, so whether the install matches the tree decides whether the probe is measuring what it claims.

**It is not, however, running on its own.** `grep -rn "check_codex_compat"` finds one invocation site outside its own tests — `README.md`, under a manual instruction to re-run the Codex compatibility check from an authenticated host — and `.github/workflows/ci.yml` runs `lint.py`, `check_version_bump.py`, the tests and `doctrine_callout.py`, not this. It fires when its caller fires, which is a human who decided to run a probe. Said plainly because the alternative reading — that a comparison like this is already live and could be cheaply widened — would walk straight into reason 3.

That is the distinction the decline turns on. A precondition has a caller who needs the answer at that moment. A background staleness warning has no caller at all, which is reason 1 restated from the other side. **This was surfaced by the change's own experience session** — the seat sent to decide the proposal cold found the existing code unprompted, and named it as the shape worth having.

## What ships instead, and why it is this small

`README.md` gains two sentences beside its Pinning paragraph. It gains **only** two, because the larger claim was probed and failed.

The brief this change was built under assumed an adopter reading the current text could believe a merged fix was on its way to them. A cold seat was given the unchanged `## Install it` section and asked the adopter's question — a fix you need was merged upstream yesterday, do you have it, and what do you do — and produced the delivery model unprompted: *"there are two gates between the merge and your working tree — their bump, then your fetch."* Three further independent A-arm seats went as far as the recorded evidence says and no further: each reached for re-running `marketplace add` plus `install`, so each knew a fetch of its own was required, and none named a restart or `claude plugin update`. The two-gates articulation is one seat's; the need-to-act is four seats'. **The premise was false, so the brief was amended rather than the prose reworded** [D-304].

The same probes showed what a reader does *not* get, and both fail silently rather than confusing anyone:

- **The restart.** `claude plugin update --help`: *"Update a plugin to the latest version (restart required to apply)"*. None of the A-arm seats named it; one listed *"whether the nine skills reload without restarting the session"* as an open question it could not answer from the text.
- **The invocation.** `Usage: claude plugin update [options] <plugin>`, with `-s, --scope <scope>` defaulting to `user` while `README.md` recommends `--scope project`. Every A-arm seat reached for re-running `marketplace add` plus `install` instead.

## What was deliberately left unsaid

**No update order.** An earlier reading had the addition state marketplace-refresh-then-plugin-update. It was dropped. Whether `claude plugin update` refreshes the marketplace clone on its own was never established — settling it requires forcing the clone stale, which mutates the owner's plugin directory and was judged out of proportion — and the composite sequence was never run end to end. `README.md` two paragraphs above the edit site already refuses to assert unmeasured CLI behaviour (*"not something we have measured; every CLI surface we tried refused to act on the declaration alone"*), and shipping an unrun sequence would have breached that standard in the same file.

**No Codex update command.** `codex` is not on PATH in the environment where this was built; `codex --version` returns command not found. Nothing symmetric was invented.

## Reopen on

An adopter reporting that they ran an old version without knowing; a firing site appearing that does not depend on a session remembering; or the roster stub ceasing to redirect into the working tree, which is what makes reason 1 hold.

## The rejected alternative worth naming

**Prose telling sessions to update after a shipped-zone merge**, in the `landing` cell's flow. Rejected as reason 3 in another costume: it fires only for whoever merged, and only if they remember, while every other session on the machine stays behind. The flow already carries the steps a change owes; adding one nothing enforces would grow the surface [#260](https://github.com/Grimblaz-and-Friends/tradecraft/issues/260) is trying to shrink, and buy a trigger already measured to fail.
