# D-99: The dispatch prompt caches only when it is byte-identical, and the cost argument is dead for panels

**Status:** Accepted 2026-08-21 (PR #99)

## Context

[D-90](D-90-2026-08-20-dispatch-contract.md) measured [#82](https://github.com/Grimblaz-and-Friends/tradecraft/issues/82)'s prompt-caching argument at one block size, found it did not hold, and then hedged: *"Both results can stand; a payload large enough may clear a breakpoint that a 1,250-token one does not."* [#92](https://github.com/Grimblaz-and-Friends/tradecraft/issues/92) was filed to settle that, and `agent-orchestra` had recorded the same gap as an explicit known-unknown — *the cacheable prefix unit for `Agent` dispatches*. Neither project had ever established where the breakpoint falls.

It has now been measured. This entry records what the instrument found and retires the hedge; it changes no rule.

## Decision

**No payload clears a breakpoint, because the breakpoint is not where the hedge assumed.** A sweep of sibling dispatches whose prompts share a leading block and diverge only in a one-line tail read `cache_read_input_tokens` **26,881 at every size** — 4,226, 16,423, 64,396 and 256,374 prompt characters, on measured common prefixes with the preceding dispatch of 4,139, 16,336, 16,287 and 256,286 characters — the last holding for that family's second and third dispatches, its first having followed the 64,396 arm and shared 64,259. Those two share their **256,286-character (≈74,800-token) prefix** with a same-size sibling dispatched five seconds earlier, and still rewrote all of it. The 64,396 arm is the exception in kind rather than in result: its same-size siblings were refused, so its single warm point followed the 16,423 arm and shares only that arm's prefix — the matched-sibling design is tested at 256,374, four times larger, with two clean points. Cache creation is linear in prompt length with a fit essentially exact — `12,650 + 0.29185 × prompt_chars`, residuals no larger than 75 tokens, under 0.6%, across a 60-fold span.

**For a dispatcher this is a straight per-recipient cost.** Every byte of a block whose per-seat tail differs is written fresh at the five-minute write multiplier of 1.25x, once per recipient, with no sibling discount at any scale — a five-seat panel pays the block five times whether the shared part is one literal string or five bespoke prompts. At today's ~5,500-character assignment that is about 1,600 cache-write tokens per seat, roughly 2,000 base-token equivalents, and ~10,000 across a five-seat panel. Under every arrangement this repo's contract permits, the block's size is a cost that only ever rises.

**The mechanism is not a missing breakpoint but a misplaced one.** Of eight dispatches carrying a *byte-identical* 71-character prompt, the five that followed a same-prompt sibling cache **completely**: `claude` siblings read 40,006 with `create` **0**, `general-purpose` 39,899 with `create` **0**, `Explore` 27,732 with `create` **0** — the entire request, attachments and prompt included. The three that no same-prompt sibling preceded wrote 82,150 tokens between them (`claude` 0 / 40,006 and `Explore` 0 / 27,732, both first of their type in the session; `general-purpose` 25,487 / 14,412, which had a same-type predecessor but not a same-prompt one), which is the write the hit requires. So a breakpoint does sit after the user message; it sits at the **end of the whole request**, behind the per-recipient bytes. Because the cache references the whole prefix *"up to and including the block designated with `cache_control`"*, one differing byte collapses the hit back to the tools-and-system entry. The API documentation names this failure under its own heading, *"Common mistake: Breakpoint on content that changes every request"*: *"The lookback does not find stable content behind your breakpoint and cache it. It finds entries that prior requests already wrote, and writes happen only at breakpoints."* Its remedy — move the breakpoint to the last block that stays the same across requests — is the one move a dispatcher cannot make, because the dispatcher does not place the breakpoint.

**The consequence is structural, and it is stronger than the measurement it rests on. No arrangement that *pushes* the per-seat difference into the request produces cross-seat cache sharing on this runtime.** A pushed difference must sit somewhere, and every available *somewhere* is inside the span that must be identical: put the lens in the prompt and `messages` diverges; put it in the agent definition and `system` diverges, which invalidates `messages` after it. Inside the request there is no third place. **#82's cost argument was therefore never available at any block size to a panel whose seats are told their lens at dispatch time** — which is every arrangement this repo's contract permits — and the correctness half carries the rule alone, which is what D-90 concluded on narrower evidence and what this entry confirms on the mechanism. **One route does escape it, and it is measured rather than hypothetical:** a byte-identical dispatch whose discriminator is *pulled* on turn 1, after the cached boundary, does share across seats that end up differing — `create` **0** for siblings two and three. It is rejected below on price, not on possibility.

**What is cached is real and is not what a dispatcher controls.** The 26,881-token region is the agent type's system prompt and tool set, and the type is at least part of what selects it — visible in the corpus as it stood immediately before this change's own dispatches entered it (285 `Agent`-tool dispatches, before 2026-08-21T03:51:00Z): `Explore` reading 17,052–17,061 against `general-purpose` reading 21,551–27,676. Re-running that query today returns a wider span at the top, because the byte-identical arms reported above are themselves now in the corpus — a count over a corpus the change writes into is a query, not a number. Anthropic's [workflows page](https://code.claude.com/docs/en/workflows) documents exactly this fan-out: *"Two agents that run with the same model, effort level, agent type, tools, output schema, and working directory build the same tools-and-system-prompt prefix, so an agent that starts after a matching sibling's response has begun reads that sibling's cache on its first request."* Two adjacent facts belong with it. **Within a single dispatch the prompt does cache** — each request reads the whole of its predecessor (0 → 41,214 → 57,716 → 69,442), so the waste is across siblings and never within one. And **a fixed block of post-breakpoint harness material is rewritten on every dispatch before its prompt** — ~12,650 tokens where the sweep's dispatches took the workflow default, and ~14,400 on the mechanism run's `general-purpose` dispatch at a 71-character prompt. **Both are workflow-instrument figures and the variable between them is the agent type, not the instrument**; a first draft of this sentence labelled the second an `Agent`-tool measurement and was wrong. Its content is the deferred-tool list (10,584 chars) and skill listing (13,953) injected as attachments, plus `AGENTS.md` (6,833) and the global `CLAUDE.md` (7,244) — about 11,300 tokens of it, injected into the conversation rather than the system prompt. A five-seat panel dispatched under today's contract pays it five times for byte-identical boilerplate. Nothing in this repo controls its size; it is recorded so it is not re-derived.

**The predecessor's positive result is best read as its published confounds.** Its span was 64,740 **bytes** — about 18,900 tokens at this sweep's measured 3.43 characters per token, which this sweep brackets on both sides and exceeds by 4.0x at the top. Its own document draws the opposite conclusion from those runs — *"the batch tiered (124,361 / 88,313 / 87,777) — the first pass writes and the others read"* — and this entry does not adopt that reading, because the figures are per-dispatch cache-write totals over unequal numbers of API calls (88,313 across 14 calls against 115,285 across 27 before the change), which cannot support a per-call comparison in either direction. That is a reason to set the predecessor's evidence aside, not to enlist it. Its **inside-the-span** formulation is therefore still not imported: its cache-alignment rationale is dead here at every scale, and the correctness half is already carried by the four-word clause `2338ac4` landed. **The instrument must enumerate every project slug for the repository**, D-90's own correction, held throughout.

**One finding cuts against a rule this repo already has, and the rule should not move for it.** Anthropic's [Claude Code prompt-caching page](https://code.claude.com/docs/en/prompt-caching) states it: *"The system prompt embeds the working directory, platform, shell, OS version, and auto memory paths, so two sessions in different directories build different prefixes and miss each other's cache. That includes worktrees of the same repository, since each worktree has its own working directory."* The skill's *"Seats that mutate the tree get their own worktree"* is correct on its own reason — concurrent readers seeing files change mid-review — and a cost argument is not grounds to weaken it. But it costs a full prefix rebuild per isolated seat, which was not known when it was written, and a future session weighing worktree isolation should weigh that rather than rediscover it.

## Rejected

- **Byte-identical dispatch with a pulled seat assignment.** Give every seat one identical dispatch carrying the whole roster and let each agent claim its seat by a call made on turn 1, after the cached boundary — the discriminator pulled rather than pushed, since anything pushed sits in the request and destroys the identity. Built and measured: it works, siblings two and three receiving their entire dispatch at `create` 0. Rejected on the denominator. The arms differ only on turn 1, where it saves 32,376 base-token equivalents of a 61,483 baseline — 52.7% of that term, and **a saving worth 0.25%–0.70% of a real review**, those costing 4.6M–12.8M across eight corpus sessions. The turn-1 term it halves is itself only 0.48%–1.34% of a review. It asks for the contract's per-recipient part deleted, every seat reading every other seat's lens, a race-safe claim tool, and a nondeterministic seat-to-agent mapping. Filed with its numbers and its runner as [#98](https://github.com/Grimblaz-and-Friends/tradecraft/issues/98), which records the two conditions that would reopen it: roughly eighteen siblings sharing one large context, or seats that each do very little.
- **Any change to the dispatch contract.** Nothing measured touches it. The rule is correct on its correctness reason and would be correct if the cache did not exist.
- **Any change to `skills/adversarial-review/SKILL.md`, which this change leaves untouched.** Its byte-identity requirement — *"one literal string cannot drift"* — never carried a caching rationale and does not lose one here: it exists because a dispatcher that retypes the assignment per recipient decides one recipient at a time what gets reviewed. Nothing measured above is a reason to relax it, and a session arriving here from the cost question should not read it as one.
- **Editing D-90 or #82.** The entry is frozen and reversal is by a new entry; the issue is exhaust.
- **Running the `agents/` falsifier before writing this.** Its whole payload was the cost case for hoisting stage-invariant material into an agent definition, and the same denominator kills it whichever way it lands. No spike measured the hoist, so the figure is an estimate rather than a measurement: moving a ~5,500-character assignment from the creation region to the read region saves about 1,850 base-token equivalents per seat, roughly 9,000 across a five-seat panel — under 0.2% of a review. The affirmation reasoned from ~32,000, which is the seat-claim scheme's measured saving rather than this one's; the correction moves the number down and strengthens the rejection. It is recorded below instead.

## Deferred, with the evidence that would reopen them

- **Whether user-authored agent-definition body text sits inside the cached prefix.** Declared open under `skills/authoring/references/spikes.md`, which is what an unresolved spike is owed. It is documented that the body becomes the subagent's system prompt; it is **not** documented that the harness's breakpoint falls after that body, and [claude-code#50213](https://github.com/anthropics/claude-code/issues/50213) reports a related defect — trailing context appended past the marker, ~4.7K tokens rewritten per spawn, which that issue decomposes as roughly a 3.5K environment block plus 1.2K of user messages and measures as agent-shape-dependent. It was closed by an inactivity sweep with no response on the merits, so the behaviour is neither confirmed fixed nor confirmed rejected. **Read closely it points toward confirming this premise rather than against it**: its stated root cause puts the marker after the agent's prompt and only the environment tail outside, which on the falsifier's criterion below predicts a confirm. It is cited here for the defect it proves possible — material landing past the marker — not as evidence for the answer. Suggestive but not decisive: `claude` and `general-purpose` share a tool set and a byte-identical message payload, and their reads differ by 107 tokens, which can only be system-prompt text and sits inside the read. **The falsifier:** in a fresh session define two agent types with identical `tools:` and description length differing only in body size, dispatch siblings of each, and compare `cache_read`. A difference of about the body size confirms; a flat result refutes and moves the difference into `create`. **Why it did not run:** the new agent type was not picked up mid-session, and the reason is narrower than "the registry is fixed at session start" — Claude Code does watch the agent directories and applies edits without a restart, but *"The watcher covers only directories that existed when the session started, so after creating a scope's first agent file in a new `agents` directory, restart to load it"* ([sub-agents](https://code.claude.com/docs/en/sub-agents)). This session created `.claude/agents` seconds before dispatching into it. Both CLI binaries then failed with `OAuth session expired and could not be refreshed`. **Reopen on:** anyone populating `agents/` — but note the next line first.
- **The correctness case for `agents/`, which is not this entry's subject and must not be argued on cost.** A dispatcher cannot compress what it does not retype, and that is the failure D-90's own review caught: an evidence-standards block introduced as a quotation, five of seven bullets exact, shipped byte-identically to all five recipients and satisfying the contract completely. If `agents/` is ever populated here that is the reason. **Reopen on:** a recurrence of dispatcher compression that the contract's fidelity clause does not catch.

## Instrument and its limits

`usage.cache_read_input_tokens` and `cache_creation_input_tokens` on each request of each `subagents/**/agent-*.jsonl`, deduplicated by `requestId` — several assistant records share one request and a naive read counts them repeatedly. Costs are stated in base-input-token equivalents at the published multipliers: read 0.1x, five-minute write 1.25x. Dispatches were sequential, which is the *most generous* arrangement for finding a hit and matches the mechanism the harness itself uses — a workflow fan-out holds every sibling but the first until the first response begins, capped by `CLAUDE_CODE_WORKFLOW_PREFIX_STAGGER_MS`, default 5000.

**The size sweep and the mechanism run both ran on the workflow subagent rather than the `Agent` tool**, because generating a 256,374-character prompt as an `Agent` call would have cost roughly 75,000 output tokens to type — 256,374 characters at this sweep's measured 3.43 characters per token — and overflowed the dispatching session's own context. Only the corpus observations and the within-dispatch sequence above are `Agent`-tool measurements. **The mechanism was therefore re-measured on the `Agent` tool itself**, since it is the path this repo's reviews use and no byte-identical pair had been dispatched through it: three sequential dispatches carrying a byte-identical 71-character prompt read 0 with `create` 40,974 cold, then **40,974 with `create` 0** twice — the same complete hit. The two instruments differ in prefix size (26,881 on the workflow subagent against 17,052–27,676 across the `Agent` corpus at the same pre-change snapshot — `Explore` at the floor, `general-purpose` spanning 21,551–27,676) and agree on the behaviour the finding rests on. The model was held fixed at `claude-opus-5` throughout, the confound the predecessor's runs carried. Filler content also changed between the sweep's two runs: the first run's pseudo-random word filler was refused by the classifier above 4K and the second used coherent prose, so the 4,226-character arm comes from the first run and the other three from the second. The read column is 26,881 in both, which is the column the finding rests on. Classifier refusals cost three arms their full width — the size sweep's 64,396-character arm's outer siblings, the seat-claim run's large arm, and the mechanism run's divergent-tail control, which five refusals across six probe dispatches cut to a single point — each reading the filler payload as a pattern already blocked; no arm was re-attempted, and every conclusion is bracketed by measured arms on either side, the large seat-claim projection moving its saving from 0.25% to 0.39% of a review and changing no recommendation.
