# D-939 — A Claude launch's file writes stay in its tree, and the launch checks it left everything else alone

**Purpose:** trace #906's decision that a Claude author's or builder's file-editing tools are confined to its tree and session scratchpad by a launch-owned path check, that every writing Claude launch compares what it must not touch before and after its run, and that an unattributed change holds the change until the holder accounts for it. **Audience:** a future session changing the implementer or seat launchers, the write guard, the comparison's coverage or attribution, or the entrance's hold. **Success:** it can recover why there is no shell guard, why the comparison and the hold fail closed, why a running launch owes nothing, and why attribution trusts recorded runs, without re-deriving them or quietly widening the bound.

The owner's [affirmed brief](https://github.com/Grimblaz-and-Friends/tradecraft/issues/906#issuecomment-6595294947) governs. Its pre-implementation artifact was [settled on the cap route](https://github.com/Grimblaz-and-Friends/tradecraft/issues/906#issuecomment-6595890998) after two qualifying `would-not` verdicts, with the holder's repair list in [6595812091](https://github.com/Grimblaz-and-Friends/tradecraft/issues/906#issuecomment-6595812091). The holder's readings govern the build: [6595905504](https://github.com/Grimblaz-and-Friends/tradecraft/issues/906#issuecomment-6595905504) accepts revision 3 as the plan and moves the live launch (AC-16) to the use stage, and [6598031790](https://github.com/Grimblaz-and-Friends/tradecraft/issues/906#issuecomment-6598031790) reads the first build, accepts its calls and departures, and adds the running-launch rule below. The holder chose ordinary / connected and named path resolution as the risk that might justify a panel; none was bought. The product harm answered is the filing's: another product change's work or evidence lost or corrupted by one Claude build.

**Why the file tools are guarded and the shell is not.** The owner chose "Guard and verify" over an OS-level bound under a separate Windows account, after the pickup check found that Claude Code's own sandbox refuses to start on this machine ("the Windows sandbox is not active on this session (feature gate off)") and that no WSL distribution existed. He then chose "Slim A, hold Linux": the before-and-after check and the file-tool rules, with no shell-reading guard. Both are quoted as the affirmed brief records them. A file tool names its target in its input, so checking it is exact; reading shell commands is a guess, and is the part that leaks. The Linux builder that would fence the shell is held in #937 with #930, and the cloud builder is the owner's parallel purchase in #938, starting with its spike. Turning on Claude's own sandbox once it reaches Windows is its own change, because it also fences network. Until one of those lands, a shell write still lands and is found only afterwards.

**The guard is a launch-owned hook, not deny rules.** `lib/tree_write_guard.py` runs as a PreToolUse command hook from the launch's own settings file, because the spike showed that check refusing an outside write under auto mode with user settings only, while a deny list can't express "everything but this tree" and the spike's deny arm couldn't be separated from auto mode's own judgment. The scratchpad is allowed because the runtime directs every session's temporary files there; the launch always names the session (`--session-id`) so it can derive that path from the root and session before the process starts. Memory is switched off in the child environment, and a file-tool write to the memory store is refused regardless, because the store lies outside both allowed places.

**What fails closed, and why.** Each case is a place where silence could not be told apart from hidden damage:
- The guard refuses any form whose resolution could differ from the runtime's (`~user`, environment-variable forms, device and UNC paths, drive-relative paths, hard-linked files) rather than guessing, and expands only `~` and `~/…` itself; it never relies on whether the runtime's file tools expand `~`.
- A guard that can't evaluate denies. A self-test with its own config and log proves the hook before launch, and a failed self-test is a preparation failure, never an unguarded launch.
- After the turn, a refusal fails it, and so does a completed (or unanswered) file-tool call the guard never decided, because only the guard's own log can show that the hook never started. A call the runtime rejected before running wrote nothing, so it is listed, not failed.
- An item the comparison can't read or walk in time is an `uncompared` finding, and a stopped launch whose run record has no comparison is `unrecorded` and held.
- A launch still running is the exception. Its comparison is written when it stops, so it reads `running`, holds nothing and owes no account; the existing live-launch routing governs it. Holding it would ask the holder for an account of findings that don't exist yet, which no party could fit and which would stop matching once the comparison is written.

**What is not compared, and why attribution trusts recorded runs.** A checkout's `.git` and the worktrees nested inside it are left out, because every builder edits its own nested tree and commits into the shared `.git`. Clones of repositories with no active registration, the memory store against shell writes, the store's handover files, bundles that appear during the run, and anything outside the coverage list are not compared; the brief accepts those exposures with the unfenced shell. A change is attributed only to another recorded run whose live window overlapped this one: under that run's root, or, for a registry row naming another holder's session, when that holder's overlapping run names the row's work or root. Attribution reads recorded fields, so a shell write that forged a live run record could hide itself; row 2 decides attribution from recorded runs, and preventing that forgery would need the shell fence this change does not build. Everything else, the owner's edits and plugin updates included, is the holder's to account for.
