**What fails closed, and why.** Each case is a place where silence could not be told apart from hidden damage:
- The guard refuses any form whose resolution could differ from the runtime's (`~user`, environment-variable forms, device and UNC paths, drive-relative paths, hard-linked files) rather than guessing, and expands only `~` and `~/…` itself; it never relies on whether the runtime's file tools expand `~`.
- A guard that can't evaluate denies. A self-test with its own config and log proves the hook before launch, and a failed self-test is a preparation failure, never an unguarded launch.
- After the turn, a refusal fails it, and so does a completed (or unanswered) file-tool call the guard never decided, because only the guard's own log can show that the hook never started. A call the runtime rejected before running wrote nothing, so it is listed, not failed.
- An item the comparison can't read or walk in time is an `uncompared` finding, and a stopped launch whose run record has no comparison is `unrecorded` and held.
- An unfinished run, such as a hard-killed launcher's, never gets a `completed_at`. It overlaps this run, and so excuses changes under its root, only while `run_lifecycle.liveness` reports it active or when its last durable checkpoint (`launched_at` plus `elapsed_checkpoint_seconds`) falls at or after this run's before-snapshot. Otherwise it would explain every later change under its root forever, which row 2 does not allow.
- A launch that failed before its process call ran nothing, so it records `not-launched` rather than holding. The launcher decides this from a flag set immediately before the process call, not from `attempt["launched"]`, which stays false for an unresolved Windows launch that may have run.
- The launcher's own unrecorded comparison (planning failed, or no cleanup window was left) names its finding `unrecorded`, as the entrance does for a run record with no comparison, so an account names both alike. When planning failed the request's coverage is empty, so the holder inspects what the work cell's launch-findings reference lists as covered.
- A double quote in the interpreter, guard or config path refuses preparation: the hook command quotes each path, and the argument-list self-test would not catch a broken command.
- An account counts only when posted after its findings exist: after the run completed, or, for an unrecorded comparison, after the launch began. Finding ids are predictable, so an account posted beforehand would otherwise pre-empt the inspection.
- A launch still running is the exception. Its comparison is written when it stops, so it reads `running`, holds nothing and owes no account; the existing live-launch routing governs it. Holding it would ask the holder for an account of findings that don't exist yet, which no party could fit and which would stop matching once the comparison is written.

**What is not compared, and why attribution trusts recorded runs.** A checkout's `.git` and the worktrees nested inside it are left out, because every builder edits its own nested tree and commits into the shared `.git`. Clones of repositories with no active registration, the memory store against shell writes, the store's handover files, bundles that appear during the run, and anything outside the coverage list are not compared; the brief accepts those exposures with the unfenced shell. A change is attributed only to another recorded run whose live window overlapped this one: under that run's root, or, for a registry row naming another holder's session, when that holder's overlapping run names the row's work or root. Attribution reads recorded fields, so a shell write that forged a live run record could hide itself; row 2 decides attribution from recorded runs, and preventing that forgery would need the shell fence this change does not build. Everything else, the owner's edits and plugin updates included, is the holder's to account for.

**Stat, not content digests, for trees and records.** Trees and completed records are compared by type, size and modification time, as the settled artifact's D6 chose, and a reviewer's request for content digests was declined. A shell rewrite that keeps a file's length and restores its timestamp passes a stat comparison, but it evades a shell the brief leaves unfenced, as forging a recorded run does. Single files the brief names (the switch, rulings, settings, `CLAUDE.md`, the registry and the run's own request) are compared by sha256.
