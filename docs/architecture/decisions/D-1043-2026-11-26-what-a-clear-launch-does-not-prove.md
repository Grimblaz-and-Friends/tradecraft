# D-1043 — What a clear launch does not prove

**Purpose:** record why #1039 has a Claude launch's comparison hold an installed plugin version removed or marked for retirement while an install entry still names it, and hold a compiled file Python won't check against its source, while saying on the findings page which changes it still releases. It also records the calls made inside the brief. **Audience:** a future session changing what a launch comparison releases or holds in the installed plugins. **Success:** that reader can recover what was chosen over what without the issue.

The owner's [affirmed brief](https://github.com/Grimblaz-and-Friends/tradecraft/issues/1039#issuecomment-7182283506) governs. Its [pre-implementation artifact](https://github.com/Grimblaz-and-Friends/tradecraft/issues/1039#issuecomment-7182613219) was [settled](https://github.com/Grimblaz-and-Friends/tradecraft/issues/1039#issuecomment-7182688914) by a cold seat, and one builder carried the change to ready on the builder route. The lane is ordinary / connected, and no panel was bought. This record supersedes none. It narrows three of [D-1023](D-1023-2026-11-24-what-a-launch-comparison-releases.md)'s released kinds, which matched a version folder, an orphan marker and a compiled file by where they are alone.

## What it answers

Each kind D-1023 releases is matched by where the change is, while the reason it releases is a property the rule never checked, and the comparison can't tell who made a change. So a launch could take an installed plugin away, or plant compiled code Python never checks, and the product's next stage would go on with no hold. No recorded launch has done either. The owner bought the work as valued, not measured.

## What was chosen over what

- **Reading the install record for a removal, over keying on whether the launch added a version of that plugin.** The app retires a version only after the install record has moved off it, and apart from installing. Over the 763 comparisons recorded on the owner's machine before 03:45Z on 26 November 2026, 11 launches removed whole version folders and none of them added a version of the same plugin, so a rule keyed to "no version added" would have held all 11. Reading the record after the launch holds only a version an entry still names.
- **Holding an orphan marker on a named version without knowing whether the app would act on it.** Of the 13 version folders then cached on that machine, at 03:50Z that day, the 9 with a marker were the 9 no entry named, so a marker on a named version is not the app's work. Whether the app would later delete such a version was not tested, because the test would have to run in the real plugins folder, and the hold doesn't depend on it.
- **Reading each changed compiled file's 16-byte header, over holding all bytecode again or releasing it all.** Python checks two of the three kinds it knows against their source. The third, a hash with checking off, loads whatever the source says, and an import never writes one. All 24 compiled files under the plugins folder at 03:50Z were the kind an import writes. Bytecode changed in 21 launches, 135 changes in all, so holding it all would bring back the holds D-1023 removed. The added cost is reading 16 bytes for each changed file.
- **Stating the five changes that still release, over holding a plugin update when the launch's own commands name it** (the owner's ruling of 26 November 2026, "Say so"). The tool calls of 20 launches named the install record, and the ones read were reads or prose, not writes. A hold keyed to naming would have fired on those and missed a write made from inside a script. Holding every update would hold the app's own, which 8 launches made. Holding the removal of a version a running session still uses was also offered, by recording each in-use marker's contents before a launch and checking its process afterwards. The holder recommended against it, and the owner affirmed the brief as written. A marker's process is named inside the file, which the comparison doesn't keep, and 5 of the 13 version folders those 11 launches removed took marker files with them.

## Calls made inside the brief

- **An install record unreadable after the launch holds every removed version folder and every marker at a version folder's top,** because a removal or a marker releases only where no entry names the version, and an unreadable record shows no such thing.
- **Nothing inside an update's new folder is read or checked.** The holds on a named version and on an unchecked compiled file would hold a marker at its top, since the moved entry names it, or an unchecked compiled file in it, while the brief releases anything inside such a folder, compiled files included. An update's new folder is one added in the launch that the released `install-record` change's basis names. A newly installed plugin's first folder, and an added folder no entry moved to, are read like any other folder, so both holds apply there.
- **A sourceless compiled file inside an added version folder still releases with that folder,** while an unchecked one in its `__pycache__` holds. The brief reads only compiled files in `__pycache__` and leaves the whole-folder release of everything else unchanged, so the findings page states the asymmetry rather than the code removing it.
- **A compiled file gone by the time of its read releases,** as one removed does, because nothing is left to load, and the app retiring a version between the after-walk and the read would otherwise hold the launch.
- **A flags word Python refuses holds.** Python compiles the source again rather than load such a file, but only the kinds Python checks against the source release. Flags 2 has no hash bit, so Python checks it by time and size, as it checks flags 0, and it releases.
- **Upkeep files inside a held removed version keep their own kinds,** because first match first already names them, and the folder's own entry carries the hold.
- **The fixtures' compiled files are real ones,** made by `py_compile` in a mode named each time, because placeholder bytes carry no readable header and would hold where the tests mean a release.
- **Three existing tests changed that the pre-implementation artifact did not foresee,** which foresaw only the expectation for a removed installed version and the placeholder compiled files. The version-swap helper removed a version while its entry still named it, and the installed-launcher upkeep case wrote an orphan marker at the top of a named version. Both now hold, as a named version removed and a marker on a named version. The swap now moves the entry, as the app's update does, and the marker is written only where the launcher runs from a checkout.
- **`classify_recorded` keeps releasing a removed version folder and an orphan marker by name, and reads no compiled file,** because a finished record keeps no install record contents and no files. It is a measuring tool that neither the comparison nor the entrance calls.

The tests are in `lib/tests/test_launch_release.py`: a named version removed or marked in either item and with either separator, the after-reading failing, compiled files in each of Python's modes and with refused or short headers, what still releases, and the new holds' reasons as the entrance reads them. `lib/tests/release_fixture.py` drives the scenarios `installed-removed`, `retired-removed`, `marked-installed` and `unchecked-bytecode` for the use session.
