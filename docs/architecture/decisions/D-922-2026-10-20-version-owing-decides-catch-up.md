# D-922 — Version owing decides catch-up's version

**Purpose:** trace #910's decision that catch-up, the composed merge obligation, the builder's version instruction, and readiness and proof all follow one answer to whether a pull request owes a version. **Audience:** a future session changing catch-up, merge-obligation composition, the version report or the version instruction. **Success:** it can recover why a lab-only pull request keeps the base's version, why a change confined to the version field owes nothing, and which policy decides owing, without restoring the unconditional bump or quietly changing use purchase.

The owner's [affirmed brief](https://github.com/Grimblaz-and-Friends/tradecraft/issues/910#issuecomment-6297878008) governs. Its [settled artifact](https://github.com/Grimblaz-and-Friends/tradecraft/issues/910#issuecomment-6298539295) was settled by the recorded cap resolution after two would-not rounds, and the holder's readings ([1](https://github.com/Grimblaz-and-Friends/tradecraft/issues/910#issuecomment-6298562097), [2](https://github.com/Grimblaz-and-Friends/tradecraft/issues/910#issuecomment-6300168058)) govern the build. The holder chose ordinary / connected. The product harm answered is a product's version history gaining releases with nothing in them; none has been observed, because no product declares a version yet.

**Supersedes #761's row 2 catch-up rule** (PR #827, `b29f175`). That rule had catch-up increment the declared version whenever the base side had changed the declared file since the parents' merge base. Its premise was that every tradecraft change bumps the version, and all eight changes it counted touched shipped paths. Lab-only pull requests owe no version, and the rule could not tell them apart. The instance: #905 and #909, both lab-only, were each set to `0.197.0` by catch-up (commits `c79e54f` and `d410086`) while the entrance's own report on #909 said no bump was owed. Catch-up and the merge obligation now count the merged result's diff against the pinned base with the report's own count, `version_policy.owing`: the use rules, removals and both names of a rename, and each rule's excludes. The local count uses `--no-renames`, which yields the same name set as GitHub's `renamed` record; once pushed, that diff is the pull request's file list, so catch-up counts the inventory the next report counts. When the change owes a version and the base changed the declared file, the field is set to the base's value incremented, as before, even over a higher head. When it owes one and the base didn't touch the file, the change's version is kept for the report to judge. When it owes none, the field takes the base's value. The decision reads the pull request side's field before any placeholder is written, so a field conflict always yields a prescribed value and the catch-up report's `version_decision` says which branch applied and why.

**A change confined to the declared field owes nothing by itself.** The alternative, counting the declared file like any other path, was rejected because an unowed bump then perpetuates itself: under tradecraft's `.claude-plugin/**` rule a pull request carrying a stale bump would owe a version at its next catch-up, take another, and be reported "owed version is met". The exemption holds only for one ordinary modification whose merge-base and head JSON objects are equal after removing the declared member, the same eligibility the use-overlap exemption already applies; additions, removals, renames, type changes and unreadable or invalid JSON still count. Use purchase and change-proof's gate are deliberately unchanged: the exemption lives in the owing count, not in `use_required`, so an authored version change still buys a use, and the gate, which computes no version owing, needs no sibling change.

**A pull request that owes no version but moves the base's value goes back to the builder.** The report marks it `blocked` with `unowed: true`, reusing the below-target status so every existing readiness, proof and builder-resume route applies without a new branch. The test is three-way: the head's field differs from both the base tip's value and the merge base's value. A pull request still holding an older base's value it never touched is not refused, because it merges to the base's value and refusing it would send a builder to repair a non-defect. The composed version instruction now states this branch, and a prescribed merge value governs the merge while the final diff governs what the turn returns.

**Owing is decided under the entrance's selected policy**, the rules loaded for that invocation from the holder root or `--use-rules`, and never from the base's, the head's or the merged result's `.github/change-proof.json`. The next report selects the same bytes, so catch-up and that report cannot disagree over a policy the pull request itself edits. `version_decision` records the selected bytes' hash so a later disagreement can be traced to a policy that moved between invocations.

**Accepted costs.** The version report makes one more GitHub GET, the `compare` read that names the merge base, when a changed declared file needs the field-only test or the unowed-but-moved check. Catch-up and the merge obligation now read the pinned base's declared value on every declared merge, so an invalid declared version at the pinned base stops them even when the base didn't change the file; it fails visibly where the old code would have guessed, and the decision needs that value on both branches.
