# Release readiness reads GitHub's merge verdict, and answered threads are resolved where the rules require it (#884)

**Purpose:** retain why the entrance now counts GitHub's own merge verdict toward release readiness, how it names a block, and why thread resolution is an instruction to the answering turn rather than an act of the entrance. **Audience:** maintainers of `lib/work.py`'s routing and release report, and adopters reading its reports. **Success:** a maintainer can change the verdict classification, the block attribution or the resolution route knowing what each call rested on.

The owner bought #884 and affirmed its brief on 2026-10-20 ("Fix the cause: the release report reads GitHub's merge verdict and names what blocks", then "agree" to resolving answered threads only where the repository's rules require it, then "affirm"). The harm was Daemon#77: Daemon PRs #65 and #83 were reported with all evidence complete while GitHub held them `BLOCKED` under a repository ruleset requiring resolved review threads. Before this change the entrance judged readiness from the practice's own evidence plus two GitHub conditions read one by one, a conflict and a branch behind under a strict rule; GitHub's overall `mergeable_state`, already present in the pull-request record it fetched, was never read. The settled artifact is [6298149724](https://github.com/Grimblaz-and-Friends/tradecraft/issues/884#issuecomment-6298149724), settled by [6298301270](https://github.com/Grimblaz-and-Friends/tradecraft/issues/884#issuecomment-6298301270).

## The calls

- **D2, classifying the verdict.** `merge_state` is the live PR's `mergeable_state`, lowercased, stored in the synchronization facts `_collect_synchronization` builds, so `_decide` and `run release-report` read it from the newest PR fetch. `clean`, `has_hooks` and `unstable` are ready; `unstable` lists every non-successful current-head check run as information, or a note when none is visible, because GitHub merges past failing optional checks. `unknown`, empty or missing waits as `merge-verdict-unknown` and names the rerun, because GitHub computes the verdict lazily and a read just after a push can return it; there is no polling, so the entrance stays bounded and read-only. GitHub's `behind` proves a rule requires the branch current, so a compare-behind head routes to `catch-up` even when the strictness read was false or unreadable, and a `behind` against a current compare is named as an unattributed contradiction with a reread. `dirty` keeps the existing conflict route.
- **D3, naming the block.** Any other word is not ready, and `blocks` names, in order, `required-gate` (the gate is not green or none), `unresolved-review-threads` (the rule requires resolution and the threads read found unresolved ones, every author included, because GitHub's rule counts every thread), or `unattributed` only when neither applies, with GitHub's word, the non-successful checks at the head and, under an unreadable thread rule, the unresolved threads and the uncertainty. The reason is `merge-blocked-` plus the first kind. A failing required status-check context such as `lint-and-test` is an unattributed candidate, not a fourth kind, because row 1 names three. Inside `_decide` the gate block cannot arise, since the existing gate reasons fire first; it appears in `run release-report`, which a holder may name past a red or pending gate.
- **D4, the thread rule.** True when a `pull_request` rule in the same `rules/branches` response requires thread resolution or classic protection enables `required_conversation_resolution`; false only when the rules read succeeded, every such rule says false and classic protection was read as not requiring it; otherwise unknown. Classic protection is fetched at most once and shared with strictness, and the rule's errors stay in its own uncertainties, because an unreadable thread rule must not become a new `base-synchronization-unavailable` wait where strictness is unaffected. On a strict-ruleset repository such as tradecraft this adds one protection GET per read.
- **D5, the threads read.** A fixed read-only GraphQL query through `GitHubREST.review_threads`, built like `workflow_run_files` and never through `mutate`, paginated by `endCursor`. It runs only when the rule requires resolution or GitHub reports `blocked`, so ordinary reads spend no GraphQL call. `answered` uses `_undisposed_threads`'s reply rule.
- **D6, placement in `_decide`.** `_merge_readiness` runs after the gate checks and immediately before the release recommendation, with each reason a literal at its own call site so the holder pane's completeness walk sees it.
- **D7, `run release-report`.** After the fresh-sync early return and the reach and terms refusals, the payload carries `merge_verdict`; when it is not ready the reason becomes the block reason and the detail names the blocks ahead of any review-disposition incompleteness. Holder-close recording is unchanged, because the #889 journal already makes reruns safe and the holder may still deliver a not-ready report.
- **D8, resolution is the answering turn's act.** Where the rule requires it, a composed `review-disposition` prompt carries `THREAD_RESOLUTION_INSTRUCTION`, the exact `resolveReviewThread` command, each unanswered root comment id with its thread id, and a lookup command instead of a guessed id where one is unknown. Elsewhere, and where the rule cannot be read, the prompt says nothing about resolving, so a `declined` thread stays visible to the owner at merge. The entrance never resolves a thread itself, because it is a read.

## Two builder calls

- **The draft route in `run release-report` fires on GitHub's `draft` verdict, not on the pull request's own `draft` flag**, and only after the reach and terms refusals. Firing on the flag, or ahead of those refusals, would have rerouted existing release tests whose fixture defaults to a draft PR; `_decide` keeps its existing flag check and adds the verdict word.
- **The fixture floor is declared met.** The release fixtures in `lib/tests/test_work.py` set `floor_public` to `ci-met` at the head, so a failing optional or required-context check is read against the verdict rather than as a red builder floor.

## Evidence
