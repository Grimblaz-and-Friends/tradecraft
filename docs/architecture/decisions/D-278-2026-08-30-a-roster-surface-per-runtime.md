# D-278 — One roster surface per runtime, and the always-on total stops being one number

**Purpose:** record why this repository generates a second roster into `.agents/skills/`, why the two surfaces are not one, and why the always-on figure now reports per runtime. **Audience:** a session changing the roster generator, its guard, or the always-on figure. **Success:** a reader can tell which parts were measured, which were chosen, and what was rejected with its price.

## The defect

[#199](https://github.com/Grimblaz-and-Friends/tradecraft/issues/199) established that this repository never loaded its own cell descriptions and fixed it with a generated roster under `.claude/skills/` ([D-210](D-210-2026-08-26-project-roster-and-the-loaded-total.md)). That remedy is one runtime wide. Codex discovers a project's own skills under `.agents/skills`, this repository had no such directory, and so every trigger the practice deliberately routes to a description reached every adopter, reached a Claude Code session here, and reached no Codex session here **as this repository's own** — on a machine with the published plugin installed those nine descriptions did load, at whatever version was installed, so what a Codex session here was missing was this tree's current descriptions rather than any descriptions at all, and a stale trigger fires wrongly rather than not firing [PR #278 review, M17] — including the `substrate` cell, which exists substantially to keep this practice portable across the two runtimes it claims.

`check_project_roster` carried the exclusion in its own docstring: *Codex is outside that scope and stays outside it*, with the note that a universal would have asserted a fix Codex never received [PR #210 review, M10]. The sentence was true and correct when written. What nobody re-checked is that Codex acquired a loading surface afterwards. **How long it stood is derived, not stated**: `git log -S "Codex is outside that scope" -- tools/lint.py` puts it at `5eea69b` on 2026-08-27 and its removal at `8e816e9` on 2026-08-30, which is three days. A draft of this paragraph said eleven weeks — five times the age this repository had reached, and wrong by twenty-five times. The figure was the entry's own argument for buying a mechanism rather than a rule, so it is stated here as the command that derives it. [PR #278 review, M5]

## What was measured, and in which direction

The change rests on facts about two runtimes, so both were run. One temporary git repository held `zorbex-alpha` under `.agents/skills/` and `zorbex-beta` under `.claude/skills/`; every probe was forbidden to read, list, glob or search files and told to answer from loaded context alone.

- **Codex** (`codex exec --ephemeral --sandbox read-only`, codex-cli 0.150.0-alpha.12.2) returned `zorbex-alpha` with its description verbatim and did not return beta.
- **Claude Code** (`claude -p`, run twice under different phrasings) returned `zorbex-beta` and answered that `zorbex-alpha` was not available to it, while listing every skill it did hold.

**So the split is symmetric and neither directory reaches the other's runtime.** That is what closes off the cheap shapes: one shared directory serves one runtime, and a link between them is unavailable as a *committable* remedy for the reason [D-210](D-210-2026-08-26-project-roster-and-the-loaded-total.md) records — `mklink /D` is refused without privilege on the owner's machine, git carries `core.symlinks=false`, and MSYS `ln -s` silently copies. **It is not unavailable as a thing somebody does to a working tree**, and this change is what makes it an obvious thing to try: `mklink /J` needs no privilege, and a junction at a surface directory defeated `inside_roster` in both directions — pointed outside, `--write` wrote nine entries there and exited 0 with the lint green; pointed at the other surface, it left the mandated gate red forever with its only named remedy a no-op. The guard now compares the surface against where it was declared to be, which the second branch, reachable only once there are two surfaces, is what bought. [PR #278 review, M12]

**Against this branch**, a Codex session in the session worktree and one in a plain checkout were each asked for every offered skill whose identifier ends in `substrate`, and whether its description carries the phrase `the streams a launch must name`. Both returned two entries: one YES holding this tree's description, one NO holding the plugin version installed on that machine, which predates that clause. **That is one cell of nine.** The generator writes every surface in one loop and the guard holds every cell to it, so the other eight follow from the mechanism rather than from a run; a probe covering all nine, against a criterion whose falsifier is *a cell is absent*, is [#282](https://github.com/Grimblaz-and-Friends/tradecraft/issues/282)'s, with the re-checkability of the loading premise itself. [PR #278 review, M30]

**The trap that cost three probes, recorded because the next session will hit it.** Asked instead whether an *unprefixed* `charter` or `substrate` was offered, the same sessions answered NO — with the plugin installed, both entries surface to the model under the plugin-qualified identifier, so a question about the *name* cannot discriminate and a question about the *description* can. A control entry under a name no plugin uses was offered immediately, which is how discovery was separated from labelling. **A negative answer about a name is not evidence a surface failed to load.**

## The mechanism

`tools/roster.py` gains a `Surface` — a directory and the runtime that loads it — and `SURFACES` holds one row per runtime. `verify()` and `write()` loop over it; `expected()`, `roster_names()` and `inside_roster()` take the surface they are working on.

**A finding about a surface is reported per surface and names both its directory and its runtime; a finding about a cell is reported once and names neither.** A cell stale in both directories draws two findings, because they are two files and repairing one leaves the other serving a superseded trigger to the other runtime — which is #199's defect with the runtimes swapped. The cell-shaped ones are unparseable frontmatter and no cell at all: the cell is what has to change, and it is one file however many copies of it are owed. **The runtime naming reaches every surface-shaped message, and this is the correction that made it true** — a draft claimed it universally at six sites while three shapes named only a directory, including *out of step*, which is what every description edit produces. [PR #278 review, M2]

**The frontmatter is identical on every surface and the body is not.** What loads must be one cell's block copied verbatim, or one trigger fires two ways. What explains the file names the runtime that copy exists for, which keeps [PR #210 review, M10]'s discipline alive after the exclusion it was written about has gone: a session opening the copy it is not served by learns that from the file rather than concluding it is a stray duplicate.

**Ownership is checked on every surface, not the first.** [PR #210 cycle one, C1-F2/C1-F3] records that checking it on one path is what let hand-written content go on being destroyed after the removal branch stopped. A second surface is a second set of those paths, and `tools/tests/test_roster.py::test_ownership_holds_on_every_surface_not_just_the_first` is what fires on the loop that forgets.

## The always-on total stops being one number

The quantity is per runtime, so **every surface a reader meets prints one total per runtime**: `here` carries a row per surface, built from the doctrine files *and* the skills directory that runtime loads. The two differ in both halves — Codex reads `AGENTS.md` and Claude Code reads `AGENTS.md` and `CLAUDE.md`, which is a pointer to it, so charging every row for both reported the runtimes as loading the same amount when they do not. That was found by the external pass and by no seat. [PR #278 external pass]

**`repo_total` survives as the one scalar a delta could be taken against, and is the smallest row** — it cannot overstate what some session here reads, and the largest was rejected on this change's own arrival, a maximum having reported this pull request's movement as **zero** with the base loading nothing into Codex. **Nothing renders it alone.** A draft argued a scalar was safe because rows would be printed beside it and would agree on any lawful tree, and both halves were false: one of the three renderers printed no rows at all — `tools/lint.py`'s, the one a session reads on the flow's first mandated step — and the rows disagree on trees the guard passes, a lawful hand-written project skill under one surface being loaded, counted, and reported by nothing. Both probed. The delta is per runtime for the same reason: taken off the smallest row it could not see growth confined to another surface, so a change raising what every Claude Code session here loads could book `+0` against the ceiling the outflow rule defends. [PR #278 review, M1, M21, M22]

**The figures in this entry are the working tree's, and the base's are derived rather than credited to a command that does not emit them.** `python tools/figures.py` reports the working tree only; the per-runtime rows at another revision come from `figures.always_on_at(root, ref)`, and the ref is a sha rather than `origin/main`, which is a moving target this repository's own engine warns against and which had already moved by the time this was reviewed. A draft credited both to the script and named the moving ref. [PR #278 review, M18]

This is #199's correction one layer out. `is_roster_path` is made per surface so it can bound the **depth** of what it accepts, which is its live work in `always_on_at` where `ls-tree -r` returns deeper paths. **It is not what keeps one surface's entries out of the other's total** — both callers scope the listing before the predicate runs, so a widened predicate is never offered a path from the other surface. A draft of this section said otherwise and stated it as one of the design's load-bearing reasons; substituting a widened predicate into both callers leaves every number identical, on this tree and on a divergent one. [PR #278 review, M6]

**Every renderer is the figure's own, and there are three of them** — `figure_always_on`'s value, the merge callout's sentence, and `tools/lint.py`'s note. They would otherwise be three wordings of one decomposition. The callout is the one the owner reads at the moment he merges, and it carries no `needs:` on `lint-and-test`, so it posts on exactly the trees where the roster guard is red and the runtimes disagree [PR #210 review, M1]; the note is the one a session reads before it writes. **A draft of this paragraph said there were two, in the commit that shipped the third as a hand-written copy** — which is how the lint's note came to render a redefined scalar it had never been told about, and why the invariant is now stated with its members enumerated rather than counted. [PR #278 review, F5]

## Rejected

- **Accepting the split and recording it in prose** — a doctrine or `authoring` line telling authors that a description-borne trigger does not reach a Codex session here. It pays with a rule what the mirror pays with a generator already built and reviewed, and the admission order puts a mechanism ahead of prose. The gap would also widen with every future change that routes a trigger to a description. This was the fork put to the owner; he picked the mirror.
- **Shipping `.agents/skills` to adopters.** **What was measured is narrower than the conclusion, and the gap is stated rather than papered over.** The installed plugin's cache does hold the whole repository root with `.claude/skills/`'s nine entries, and a Codex probe in a bare directory did list the nine cells **once each** — so the plugin loader ignores `.claude/skills`. But that cache holds **no `.agents/` at all**, this change post-dating it, and `.claude/skills` is the directory this entry's own central finding says Codex never reads anywhere. So the probe shows the loader ignoring a directory it is documented not to read, and the open question is whether it ignores the one it *is* documented to read for project skills, at a plugin root. The boundary holds on the affirmed scope rather than on that evidence; the answering probe writes into a Codex configuration and is the owner's to run. [PR #278 review, M16]
- **The `SKILL.md` specification's reference validator in CI.** The guards here already hold more than it checks — frontmatter fields, byte-for-byte agreement with the cell, ownership, line endings — and an external toolchain for less is not worth the dependency. Declined and recorded rather than filed.
- **Admitting `.agents` to `REPO_ROOTS`**, for the reason [D-210](D-210-2026-08-26-project-roster-and-the-loaded-total.md) gives about `.claude`: a session can drop other directories under it, and resolving against one would give `python tools/lint.py` two answers for the same commit.
- **Collapsing the per-surface findings into one line naming both directories.** They are two files that can be independently wrong — one present and one missing, one generated and one hand-written — and a collapsed line would have to be re-split the moment they differ, which is the state the guard exists for.

## What this change did not touch

No shipped file, so no version bump; `python tools/check_version_bump.py --base main` agrees. **No always-on surface was edited, so no outflow was owed** — and the narrow reading is the load-bearing one: the cells' names and descriptions are untouched, and what changed is their *reach*, one runtime having begun to load a copy of them. This entry is not authority for the broader proposition that creating a new always-on surface owes no outflow. The change books real growth in what a Codex session here loads, and the owner affirmed that cost in the boundary. [PR #278 review, M26] No doctrine rule was added, per the admission order — the mechanism carries it. [D-210](D-210-2026-08-26-project-roster-and-the-loaded-total.md)'s sentence that *a Codex session here loads neither roster and stays at 11,351* is now history rather than a defect, and frozen entries are not repaired. **The same is true of D-225's index row**, which reads *a Codex session loads no description at all [D-210], so for that runtime the removal left no carrier* — the recorded justification for restoring a clause in `AGENTS.md`, and the one of the two still doing work. Both are superseded by being read, which is what the log's own rule says and why neither row is edited. Named here because a later outflow pass reading that row would otherwise believe the carrier argument still holds. [PR #278 review, M29]
