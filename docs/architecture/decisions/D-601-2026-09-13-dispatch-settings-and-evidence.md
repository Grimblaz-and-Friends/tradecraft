# D-601 — A change's dispatch settings live on its issue, and a dispatch is recorded rather than reconstructed

**Purpose:** preserve why the per-change setting is a sentence on the issue rather than a file the launcher reads, why continuity is keyed to dependence rather than size, and what the run that built this demonstrated about its own premises. **Audience:** a future session extending dispatch capture, revisiting the effort defaults, or reopening whether a per-change settings file should exist. **Success:** they can tell which claims here rest on a run and which on judgement, and they do not rebuild the rejected file.

The owner affirmed [the brief](https://github.com/Grimblaz-and-Friends/tradecraft/issues/592#issuecomment-5655702442) in a design sitting; the artifact settled in one cold round, `would`, before implementation.

## The file that was proposed and rejected, and who rejected it

The holding session's opening recommendation was a machine-readable per-change file on the branch — the choice written in a format the dispatcher would read, with a guard checking that the run matched the intent. The owner's answer was a question rather than a ruling: *"if I say it in the discussion, the dispatcher should have it in context, right? Do we need more than that?"*

He was right, and the reason is worth keeping because it is not obvious. **The record half does not need the file.** `lib/dispatch_seat.py` at `ed69ada` — before this change touched it — already built a per-attempt record of the vendor, model and effort it was asked for, so what a dispatch was launched at is recoverable from the dispatcher rather than only from wherever the choice was written down. **That is a claim about the requested settings and not about what ran**: this change's own first review found a path where a process that never started is recorded as launched, which is a defect in the new code and also a caution about how far the sidecar's word can be taken. The file bought only the comparison of intent against execution, which is a thinner thing than it looked while being proposed.

What survived is the residue the conversation genuinely does not cover, and it is two things rather than one. A holding session's context is compacted — on [#586](https://github.com/Grimblaz-and-Friends/tradecraft/issues/586) it processed tens of millions of tokens — so an instruction given early is not reliably in context late, and this repository already holds that principle for exactly this reason: a settling row is read off written places because a figure reconstructed from memory of the conversation is the thing the record exists to replace. And the implementing launch emitted nothing at all, which is the larger half.

**The rejection is recorded because the file is the shape a later session will reach for first.** It is the tidier design. It is also the one that spends a format, a parser and a guard on a problem the existing sidecar mostly already solves.

## Why dependence rather than size

The owner's own words asked the narrower question — *"Does your revised statement include small fixes? Those to me can still stay fresh"* — and the rule written is broader than his phrasing on purpose. A size threshold reaches only the case it names; the quantity that actually governs is whether the work depends on choices the builder made. A finding that carries its own remedy needs the tree and the finding. A finding disputing why something was shaped that way needs the agent that shaped it. Size correlates with that and does not define it, and the batch is dispatched as a batch, so one dependent finding takes the whole batch back to its builder.

**The counter-evidence is on the record and was not dismissed.** On [#586](https://github.com/Grimblaz-and-Friends/tradecraft/issues/592#issuecomment-5651511703) and [#593](https://github.com/Grimblaz-and-Friends/tradecraft/issues/592#issuecomment-5654991466) the continuing implementer returned corrections to holder-authored records, and they were right. A fresh installer does not challenge unprompted; it checks what its dispatch names, and that dispatch is written by the party whose claims are being checked. The remedy is that the instruction is generic — *verify every claim in what you are installing against the tree and the pull request, and return what you cannot verify* — rather than naming the errors the holder expects, since a holder anticipating its own error is the thing that does not happen. **Whether that substitutes for the resumed agent's unprompted challenge is not settled by this change**; it is what the next runs measure.

Every documented instance of that challenge was, on inspection, checkable from the tree and the pull request rather than from the conversation — a diff, an arithmetic check against a finding count, and a claim about what an external reviewer returned. That is what made the fresh route defensible rather than merely cheaper.

## The effort split, and the seat the owner put back

The owner set the standing default himself: *"can we save opus max for the judge and use x-high for the rest?"*, then *"I want that as the default."* The holding session countered once, on the roster's own grounds — its concentration sentence names two places to put scarce top tier, the `cold-read` and the judge, and his first wording named one. He ruled: *"keep the cold seat at max."* The roster's concentration sentence therefore stands unedited, which is the outcome a session should notice: the collision was resolved by the owner moving rather than by rewriting the rule.

Two readings were the session's and are reported rather than his. *The judge* is read as **the terminal stage, whichever it is**, because on the routine lane the defense is terminal and a literal reading would leave every routine review with nothing at the top tier. And the cold-seat ruling binds **the class** — both the review's `cold-read` and the artifact's cold seat — because the reason it turned on, open-ended perception with no briefing, is identical for each. The panel's defense is not terminal and therefore takes ordinary effort, which is a distinction the holding session's reported call did not draw — compare its wording in [the affirmed brief](https://github.com/Grimblaz-and-Friends/tradecraft/issues/592#issuecomment-5655702442) against the paragraph that states it in [the settled artifact](https://github.com/Grimblaz-and-Friends/tradecraft/issues/592#issuecomment-5656125476).

## What the run demonstrated about its own subject

**The instruction to capture cost and the instruction to resume were mutually exclusive as written.** `skills/engagement/references/the-stretch.md` told a holder to confirm startup from the header block on stderr and retain its `session id:`. Capturing usage requires `--json`. With `--json` on `codex-cli 0.154.0-alpha.6.2` that header does not appear; the resumable identity arrives on stdout as a `thread.started` event. A holder following the cost half of the material loses the resume half. This was met while performing the change's own first dispatch; the retained streams are published at [the launch evidence comment](https://github.com/Grimblaz-and-Friends/tradecraft/pull/601#issuecomment-5656212213), and the implementer reached the same conclusion independently from the CLI's help.

**The two vendors do not report the same quantity.** Claude returns a monetary field; Codex returns token counts and no money. The record keeps source-native usage and labels a returned monetary value as runtime-reported rather than installing a price table, because a dollar figure this practice computes for a Codex run is a comparison metric and calling it a cost would launder it into an invoice.

## Scope, and what was deliberately not done

No model default moved. The Codex default stays `gpt-6-astra`/`xhigh` and `opus` stays on every judging seat; what this change moves is effort and continuity. The comparison the issue names as the one worth buying — the top Codex tier against the cheaper one **on an artifact**, which is where the spend concentrates and which the owner's pilot explicitly did not test — remains unrun, and nothing here should be read as having answered it.

No historical record is backfilled. The existing review-cost aggregate keeps its population and its exclusions; the dispatch record neither widens that population nor obliges an existing row to change.

**The holding session's own cost is not captured and is the largest single item in a run of this shape.** The record this change builds covers dispatches, and the holder is not one. [#586](https://github.com/Grimblaz-and-Friends/tradecraft/issues/586) deferred it and measured it once; it is still deferred.
