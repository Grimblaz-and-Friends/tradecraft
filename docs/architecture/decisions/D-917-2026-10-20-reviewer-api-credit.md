# The connected reviewer runs on an API key and falls back to the subscription token (#917)

**Purpose:** retain why the connected reviewer now starts each review on an Anthropic API key, when it moves to the subscription token, and how each reply was recognised. **Audience:** maintainers of `lib/connected_review.py`, its workflows and its replay, and the Steward releasing it. **Success:** a maintainer can change credential selection or the reply classifier knowing which replies were observed, which calls were made inside the affirmed rows, and what remains live-only.

The owner bought #917 and affirmed its brief on 2026-10-20 ("affirm"), ruling at turn 1: "Fall back to the subscription token when the credit runs out, and record it on the review." Before it, the reviewer passed only `CLAUDE_CODE_OAUTH_TOKEN` into its scrubbed environment and refused without it, so every review drew on the owner's plan. The settled artifact is [6298324381](https://github.com/Grimblaz-and-Friends/tradecraft/issues/917#issuecomment-6298324381); the holder's reading before the build amended its guide sentence and criterion 15.

## The route

- **Selection.** `review_credentials` reads `ANTHROPIC_API_KEY` and `CLAUDE_CODE_OAUTH_TOKEN`; an empty or blank value is unset, because a workflow's missing secret expands to `""`. Each review starts on the key. `_runtime_environment` sets exactly the one credential the pass runs on, and `verify_claude_version` now runs with the allowlisted environment and no credential, where it used to inherit the job's whole environment.
- **Recognition.** `_claude_failure` tells a key's spent budget apart before today's ladder, whose `usage limit` marker would otherwise read a spend limit as the plan's own limit: `credit balance is too low` or `credit balance too low` (credit balance too low); `you have reached your specified api usage limits` or its workspace form (spend limit reached); `api_error_code` `enforced_spend_limit_reached` or `you have reached your api usage limits` (monthly spend cap reached). The test runs only on key passes. Other key failures keep the ladder with `Claude API key` in the cause; token passes keep today's causes unchanged.
- **Fallback.** `run_credentialed_pass` re-runs a pass whose key budget is spent on the token, renames the key attempt's directory to `<root>.api-key-attempt`, and keeps the token pass at the pass's own root; the rest of the review stays on the token. With no token, the review skips naming the spent budget. Both secrets are redacted (`[redacted-key]`, `[redacted-token]`) from every failed pass's cause and every recorded reply, and a review or coverage payload containing either publishes nothing.
- **The record.** Each pass is recorded under `finder:<name>` or `checker:<batch>`. A completed review carries one `Credential:` line between `Usage:` and `Reviewer:`; a skip whose attempt ran a pass carries it after the cause. The record travels in the review job's existing `usage` output under `credential`, which the reporter pops before printing usage.
- **Workflows.** The template and the shared workflow pass `ANTHROPIC_API_KEY` to the `Run connected review` step only; the shared workflow declares it `required: false` and keeps the token `required: true`. Tradecraft's stub passes both; the releases page's carrier stub carries the key line for the five carriers row 5 files after the tag moves.
- **Replay.** `tools/connected_review_replay.py` builds fresh credentials for every case, so each case starts on the key as a live review does, and records `credential` on every case result, errors included.

## Calls inside the affirmed rows

The artifact's calls C1 to C10, accepted by the holder's reading, are kept: each replay case starts on the key (C1); the key attempt's directory is renamed and the token pass keeps the root (C2); recognition runs only on key passes (C3); the CLI's retry count is unchanged, so a spend cap reaches the fallback only after the CLI's own retries (C4); the record rides the existing `usage` output (C5) as one `Credential:` line, keeping the key attempt's usage in the job output (C6); row 7's check is recorded on the PR, on #683 and in `tools/connected-review-live-checks.md`, not as a standing release rule, because late-cycle fallback is normal (C7); the version check gets no credential (C8); the token stays required in the shared workflow (C9); `gh` and `git` still inherit the step's environment (C10).

Two calls the build added:

- **C11, the short exhaustion rendering.** The credit page documents that the CLI can display `Credit balance too low · Add funds: …` for a request the credits do not cover. The classifier accepts it as the same spent balance, so an uncovered run falls back rather than stalling; row 7's live check is what tells an uncovered run from an exhausted credit.
- **C12, no new authentication marker.** The invalid-key reply (`Invalid API key · Fix external API key`) is already caught by its 401 status, so no text marker was added to the shared ladder, keeping token causes byte-identical.

## Evidence

All on Windows 11 with Claude Code 2.1.280, the pin, using fake credentials only. The artifact's spikes S1 to S3 established that the CLI tries the key in the reviewer's fresh profile, that the result event carries the reply text and `api_error_code`, and the documented reply texts. The build re-ran them against the built `run_credentialed_pass`:

- **Criterion 2, real endpoint.** A fake key alone, and a fake key with a fake token, each ran one process holding only `ANTHROPIC_API_KEY` (`apiKeySource` `ANTHROPIC_API_KEY`) and ended `Claude API key authentication failed: … Invalid API key · Fix external API key`, with neither secret in the cause.
- **Criterion 4, local mock API.** With each documented error body, the built pass classified credit too low, both spend limits and the spend cap as a spent budget, and the passing rate limit and invalid key as `Claude API key rate limit reached` and `Claude API key authentication failed`. A key whose budget was spent with a token set re-ran once on a process holding only the token, left `finder-coverage.api-key-attempt` beside the pass root, and recorded the switch. The mock saw `x-api-key` on key passes and `authorization` only on the token pass.
- **Committed tests** carry the rest: fixtures under `lib/tests/fixtures/connected_review_claude_key_*.json` hold the result fields those runs produced, and `lib/tests/test_connected_review.py`, `tools/tests/test_connected_review_replay.py` and `tools/tests/test_connected_review_packaging.py` hold the selection, fallback, record, redaction, workflow placement and guide criteria.

**Live-only.** Whether the plan's credit pays for the reviewer's `claude --print` is settled by row 7's first post-merge tradecraft review on the key, after the owner claims the credit and sets the organization secret. No raw run output is retained.
