# D-186: Windows text-mode defaults, decided once — two complementary rules for the encoding half, and one with no mechanism for the newline half

**Status:** Accepted 2026-08-25 (PR #186)

## Context

Python's text mode on Windows does two silent things whichever way the obvious call is written: it encodes `stdout` and `stderr` to the platform's locale codepage — cp1252, *including when the destination is a pipe* — and it translates `\n` to `\r\n` on writes. A pipe is what a CI log, an agent harness and a captured command all are, so the encoding half fires precisely where the output is machine-read.

Three issues had accumulated against the pair. [#147](https://github.com/Grimblaz-and-Friends/tradecraft/issues/147) was the encoding half, filed after the fix had been applied per-script three times: `skills/authoring/scripts/figures.py` crashed printing an arrow and was fixed on stdout, the same script's stderr was found unreconfigured afterwards by a review's defense seat, and `hooks/emit_charter.py` carried a third, separate hand-rolled reconfiguration that #147 did not count. [#162](https://github.com/Grimblaz-and-Friends/tradecraft/issues/162) and [#163](https://github.com/Grimblaz-and-Friends/tradecraft/issues/163) were the newline half filed twice from different ends — one from a session that spent four steps reaching a wrong recorded cause, one from a mutation harness whose CRLF rewrite made `git diff --numstat` report zero content change.

There is a **fourth** ad-hoc site, which none of those filings counted and which the original draft of this entry also missed: `skills/persist-changes/scripts/persist.py` wraps its one line of output in a `try`/`except UnicodeEncodeError` that re-encodes with `errors="replace"`. Not a reconfiguration — a lossy fallback, and a third distinct mechanism. It matters because what it protects is *interpolated runtime data*, which is the half the ASCII rule below explicitly does not reach.

They were worked as one change because they share a substrate default and because #162's own text invited it. The decision below is four rulings, not one.

## Decision

**1. The encoding half takes two rules, not one, because it has two surfaces.** This is the ruling that changed under review, and the change is the load-bearing part of this entry.

- **Machine-read output stays ASCII.** No Python file in the repository states a non-ASCII character in a string constant that is not a docstring. Guarded exactly by `check_emitted_ascii`.
- **A stream is set to UTF-8 with LF endings before anything is written to it.** `lib/winio.py` carries `utf8_stdio()`, and every script with a `main()` imports it and calls it as that function's first statement. Guarded exactly by `check_stdio_wired`. **It pins the line ending as well as the encoding**, which changes what every caller emits — on Windows a redirected script wrote CRLF before and writes LF now. That is wanted, one byte sequence from every script on every platform being what a consumer comparing or hashing a captured stream needs, and the charter hook's byte-for-byte comparison depending on it. It is recorded because the first draft of the helper documented the opposite, and a reader who noticed their redirected output had changed would have been sent to their editor and their version-control settings by the one file that owns the behaviour.

**The original ruling had only the first, and rejected the second.** It argued the choice as *helper versus rule* on guardability: *"the helper was called on this entry path" can only be checked approximately, while "these bytes are ASCII" is exact.* The review falsified the premise underneath that argument — **the two were never alternatives, because they protect disjoint things.**

- The rule reaches **source literals**. It cannot reach a path handed over by `git`, a filename a consumer chose, or a subprocess's stderr, and its own docstring said so.
- The helper reaches **the stream**, which is the only place that runtime data can be protected.

Probed, on the tree the review ran against: with a shipped file named `caf—.md`, `tools/check_version_bump.py` put the cp1252 byte `0x97` on stdout — #147's own recorded byte, reproduced by the change that claimed to close it. With one named `中.md`, outside cp1252 entirely, it did not garble but *raised*, killing the report before the offending path printed, so the message naming the problem was the message that went missing. `tools/lint.py` did the same. Meanwhile stripping `utf8_stdio()` out of `figures.py` made *it* garble and crash on the same inputs — so the helper was not protecting the script that needed it least; it was the only thing protecting the one script that had it.

**The guardability objection is answered rather than accepted, and that is what made the second rule admissible.** "Was the helper called on this entry path" is a reachability question and reachability is not decidable from an AST. That is not the question `check_stdio_wired` asks. It asks whether the **first statement** of `main()` is the call — a *position*, and a position is exact. Ordering is not incidental to it: a call placed after `parse_args` is a call that `--help` has already outrun, which is how one script here kept a helper and leaked anyway.

`lib/` is therefore created, and the zone question the original ruling deferred is answered rather than deferred. It holds one module. `PYTHONIOENCODING` in CI stays rejected as measured-insufficient rather than weaker: it reaches neither a consumer running a shipped script from a plugin cache nor a session running one locally.

**2. A docstring is not exempt when argparse pipes it.** `ArgumentParser(description=__doc__)` — or `epilog=__doc__`, the same defect by the keyword that is the conventional home for long-form prose — writes the module docstring to stdout on `--help`. Three scripts did exactly that: `tools/check_version_bump.py`, `tools/doctrine_callout.py`, and the **shipped** `skills/persist-changes/scripts/persist.py`, each emitting `0x97`. **The warrant is the exemption, not the encoding**, and stating it the other way round did not survive the change that introduced it: the first draft gave the reason as *`--help` exits inside `parse_args` before any stream setup runs*, which ruling 1's own guard falsified in the same commit by putting the setup before `parse_args`. What survives is that the ASCII rule exempts docstrings **because a docstring is read as prose and never written to a stream** — so piping one falsifies the premise the exemption rests on. Help text is written as help text, in ASCII, and the module docstring is kept for readers of the source.

**3. The newline half is prose, in the `substrate` cell.** A file that will later be compared, restored or measured is written and read as bytes, with byte-identity asserted on restore. The operative failure is not encoding at all: a text-mode write turns LF into CRLF, version control reports the tree clean against an LF blob, and a validator asked about the same content can answer differently — so a harness can measure a tree its own commit does not contain.

Its warrant is narrower than #163 claimed, and this entry says so rather than inheriting the filing's framing. `claude plugin validate` does flip on line endings, confirmed on this change's tree, but only in **conjunction** with an unquoted `: ` inside a frontmatter value:

```
description: Not a cell: it decides nothing.     LF rc=0    CRLF rc=1
description: A simple description, no colon      LF rc=0    CRLF rc=0
description: "Not a cell: it decides nothing."   LF rc=0    CRLF rc=0
```

Across all eight shipped `SKILL.md` frontmatters there are **zero** such values. The rule is therefore preventive against a mutation seat introducing a colon into a description — which is what mutation testing does to prose — and not a response to a firing defect.

**4. Nothing guards the newline half, and the decline is the recorded part.** The surface is scratchpad scripts a session writes, runs once and discards; the repository owns no file-writing Python outside its tests, so no guard aimed at repo scripts can reach it. The only candidate is a `PostToolUse` hook matched on Bash, and the hooks documentation warns such a hook must not modify files — so it could report but not fix.

This is consciously against [#137](https://github.com/Grimblaz-and-Friends/tradecraft/issues/137)'s thesis that a rule with no mechanism does not bind. The price of the mechanism is a hook firing on every Bash call to police a harm measured at one incident and four steps; the price of the decline is that the rule rests on prose. The second was judged cheaper, and it is recorded here so a later session finds a weighed decline rather than an omission.

**5. The recorded fact is separate from the rule, and lives on the always-on surface.** `AGENTS.md` states that CRLF on disk here is expected, that `.gitattributes` normalises it on the way in, and that the committed bytes are unaffected. This is not the rule restated: the rule stops harnesses from lying, and the fact stops sessions from investigating — the actual cost of the 2026-08-24 incident, which was budget spent on a false lead plus a wrong cause recorded as settled. It sits in `AGENTS.md` rather than in a cell or in this entry because the moment it must be found is mid-task, when a session notices CRLF and has no reason to open the decision log.

It names the symptom rather than the reassuring command. The first draft said only that `git diff` stays empty, which is true and useless: `git diff` is not what a session runs. `git status` reports ` M` on a file whose diff is empty and which `git commit -a` refuses as having nothing to commit, and that pair — not the empty diff — is the second surprise #162's autopsy names as consuming a step.

## What the guard covers, stated as a bound rather than implied

`check_emitted_ascii` reads **string literals**. Two consequences follow and both are stated in its own message now, because the first version claimed a property it never computed and the claim cost something:

- It flags strings that cannot reach a stream — a filename, a regex source, a dict key. The message says "in a non-docstring string constant" for that reason. Saying "in a string that can reach a stream" caused a session to meet a lawful fixture, be told a false thing about it, and reason correctly from the falsehood into rewriting a regression test so that it pinned nothing.
- It cannot see a character built at runtime — `chr()`, `str.format`, `%`, `__str__`, `unicodedata.lookup`. Eleven such constructions were probed and every one emitted `0x97` while the check stayed silent. **Extending it to chase constructions is priced out**, because a guard doing that is the approximate check ruling 1 rejected, rebuilt to buy partial coverage. The burden for a deliberately constructed character sits on review, which is a true statement of where it already sat.

`chr()` is also the idiom this repository *uses* where a fixture must carry a non-ASCII character, which is a live tension rather than a resolved one: the sanctioned route to "I need this character" is the route the guard cannot see. Nine test functions across three files need it, and they say so at the site — per-site in `skills/authoring/tests/test_figures.py` and `tools/tests/test_check_version_bump.py`, and once above the shared constant in `tools/tests/test_lint.py`, which covers six.

## What the change's own work turned up

- **The guard produced 44 findings across six files on the pre-change tree.** The independent AST census run before the check existed returned **41 across four**, and the difference is not a discrepancy: the census scanned only the four non-test scripts, and the guard adds three findings in two test files it never looked at. Re-derivable as `git archive 9018f56` plus `check_emitted_ascii`; the census's convention was emitted-string *lines*, so a third convention — every non-ASCII character — returns a third number again. State the convention with the number or the number is not reproducible.
- **The escape form cannot evade it.** One rewritten message spelled its em dash as the six-character source escape `\u2014` rather than as the character — invisible to a search for the character, reaching the stream as the character regardless. The check reads decoded values and caught it. (This bullet was itself destroyed once, by a rewrite that replaced the escape with the character it denotes, leaving the sentence calling a one-character token six characters long.)
- **The check would have crashed the lint.** `rglob("*.py")` matches *directories* named `*.py`, and an existing delivery test creates exactly that shape, taking every other check down with it. It bit twice more while the review's fixes were being written, so the third walk got a shared iterator rather than the same patch a third time.
- **The check walked the whole repository root**, which every sibling check does not: it scoped to a zone, this one did not, and a linked worktree's `.git` is a *file* so the obvious exclusion missed it. In the owner's own checkout it produced findings in the low thousands across a few hundred files, nearly all in sibling worktrees — three seats measured 1,807, 1,835 and 1,941 within hours of each other, and the number is not reproducible by construction, because each dispatch this review made added a worktree and every worktree adds another forty-odd. That the figure moves while being measured is the finding, not a defect in the measuring; breaking a mandated step of the flow on the one surface where the flow is actually run — while CI stayed green on a clean checkout. It now asks `git check-ignore`, which is self-maintaining where a hardcoded skip list would silently exempt every future top-level directory, and which still sees a new script that has not been added yet.
- **Two unprompted instances during this change's own work.** Two throwaway probe scripts died — a `charmap` decode error reading a subprocess's output, and an encode error printing an arrow — neither of them testing for it. The affirmed artifact records one of the two, in its section 7; the second happened after it was written. That is #162's recurrence claim observed rather than argued, at two instances rather than the three an earlier draft of this entry claimed.
- **`tools/doctrine_callout.py`'s label description and callout comment lost their em dashes**, and they reach GitHub as subprocess arguments rather than a stream, so the rule's stated warrant does not apply to them. Non-ASCII survives Windows argv intact — probed. `_ensure_label` passes `--force`, so merging rewrites the live label description, and D-81's callout, the surface built for the owner's merge-time read, now renders `--` mid-sentence. Restoring them needs an exemption mechanism this decision did not build, so the cost is recorded here rather than paid.
